# REQ-002 여정 — 좌석 선점 → 무통장 예약 → 입금 확인 → 예매 확정

입력: `BRIEF_REQ-002.json`(목표·AC-1~9·범위 외·D1~D6), `docs/product/product.md` §3 역할, `docs/product/design.md` §1·§5.
feature 문서 §2-2 참조 서비스는 이 요청에 없다 — 국내 공연 예매 앱의 일반 골격(좌석도 → 선점 → 결제 수단 → 예매 완료 → 내 예매)을 기본값으로 따른다.

## 1. 사람 카드

### 관객 (예매자) — 정민지 · 핵심 사람
- **누구**: 29세 여성, 회사원. 폰으로 예매하고, 회사에서는 PC 로도 띄운다. 일행 2명과 셋이 간다.
- **처음 오는 이유**: 기다리던 공연 「새벽공방 단독 콘서트 〈밤의 정원〉」 좌석을 붙여서 3장 잡고 싶다.
- **그때 마음**: 조급하다. 고른 자리가 정말 내 것인지, 몇 분 안에 무엇을 해야 하는지 모르면 불안하다.
- **알고 싶은 것**
  1. 내가 고른 자리가 지금 내 것인가, 얼마 동안인가 → `hold` (남은 시간이 가장 큰 숫자), `seats`
  2. 어디로 얼마를 언제까지 보내야 하나 → `reserved`, `booking`
  3. 입금하면 확정은 언제 어떻게 알 수 있나 → `reserved`(다음에 일어나는 일), `bookings--confirmed`, `booking--confirmed`
  4. 자리를 놓쳤으면 왜, 이제 무엇을 하면 되나 → `seats--taken`, `seats--expired`, `booking--cancelled`
  5. 몇 장까지 한 번에 잡을 수 있나 → `seats`(선택 수 3/4), `seats--limit`
- **성공한 순간**: 내 예매에서 〈밤의 정원〉 옆에 「예매 확정」이 보일 때.
- **주로 쓰는 화면**: `seats` · `hold` · `reserved` · `bookings` · `booking`

### 운영/관리자 — 한도윤
- **누구**: 34세 남성, 서비스 운영 담당. 통장 입금 내역을 보고 입금 확인 API 를 부른다(D2 — ADMIN 역할, 화면 없음).
- **처음 오는 이유**: 들어온 입금을 예약과 맞춰 확정해 줘야 한다.
- **그때 마음**: 기계적으로 빨리 끝내고 싶다. 기한 지난 예약을 실수로 확정하면 안 된다.
- **알고 싶은 것**: 이 입금이 어느 예약인가(예매번호·입금자명·금액) → 화면 없음, API 응답 · 기한이 지났나 → API 거절(AC-9)
- **성공한 순간**: 확인 요청 한 번에 관객 쪽이 「예매 확정」으로 바뀐다.
- **주로 쓰는 화면**: 없음 — 이 요청에서 운영자 화면은 범위 밖(BRIEF out_of_scope). 관객 화면의 「입금 확인」 기록 시각으로만 드러난다.

### 주최자 (판매자) — 이번 요청에서 새 화면 없음
- 이미 있는 공연 관리 화면의 남은 좌석 수가 선점·확정·자동 취소에 따라 움직인다. 새 할 일 없음.

**핵심 사람**: 정민지(관객). 이 요청의 모든 화면이 관객 화면이고, 목표 문장의 주어도 관객이다.

## 2. 여정표

| 시기 | 사람 | 할 일 | 궁금해지는 것 | 막히는 순간 → 푸는 화면 |
|---|---|---|---|---|
| 쓰기 전 | 관객 | 공연 상세에서 예매 시작(기존 화면) | 붙은 자리가 남았나 | 등급별 남은 좌석을 몰라 헤맨다 → `seats`(등급 전환·남은 좌석 수) |
| 쓰는 중 | 관객 | 좌석 3개 고르고 선점 | 고른 자리가 내 것인가 | 누가 먼저 잡았다 → `seats--taken` / 5장째를 눌렀다 → `seats--limit` |
| 쓰는 중 | 관객 | 7분 안에 무통장 예약 | 몇 분 남았나, 얼마인가 | 7분이 지났다 → `seats--expired` |
| 쓰는 중 | 관객 | 예약 후 은행 앱으로 이체 | 계좌·금액·기한 | 계좌번호를 옮겨 적기 번거롭다 → `reserved`(계좌 복사) |
| 쓴 뒤 | 운영/관리자 | 입금 내역 보고 입금 확인 API 호출 | 기한 안인가 | 기한 지난 입금 → API 거절(AC-9, 화면 없음) |
| 쓴 뒤 | 관객 | 내 예매에서 확정 확인 | 입금이 반영됐나 | 언제 반영됐는지 모른다 → `booking--confirmed`(입금 확인 시각) |
| 쓴 뒤 | 관객 | (입금을 잊음) | 왜 사라졌나 | 예약이 취소됐다 → `booking--cancelled`(이유·좌석 다시 고르기) |
| 쓴 뒤 | 주최자 | 기존 현황 화면 | 남은 좌석 | 새 화면 없음 |

## 3. 범위

- **다룬다**: 좌석 1~4개 선점(7분) · 이미 선점·판매된 좌석 거절 · 5장 이상 거절 · 선점 만료 · 무통장 예약(계좌·금액·기한) · 내 예매 목록·상세 · 입금 확인 후 예매 확정 표시 · 입금 기한 경과 자동 취소 표시.
- **다루지 않는다 (이미 쓰는 앱이 하는 일)**: 실제 이체(은행 앱) · 입금 알림 문자/푸시(이 요청에 발송 수단 없음).
- **다루지 않는다 (BRIEF out_of_scope)**: 대기열 · 매수 지정 연석 자동 선점 · 관객 직접 취소·양도 · 카드·간편결제 · ADMIN 화면 · 모바일 티켓. 화면에는 D6 대로 취소·양도를 「후속 요청에서 다룸」 한 줄로만 적는다(버튼 없음).
- **경계**: 입금 확인은 운영자가 API 로 한다 — 관객 화면은 결과(예매 확정)만 본다. 만료는 조회 시점 판정(D5)이라 화면은 다음 조회 때 바뀐 상태를 보여 준다(ADR-0026 — 선점 타이머는 클라이언트가 0 에서 좌석 화면으로 전환).
- BRIEF `out_of_scope` 와 어긋나는 것 없음.

## 4. 흐름 고리

**대상 1 — 좌석 선점**
- 만들기: `seats`(고르기) → 「좌석 선점하기」 → `hold`
- 보기: `hold`(남은 시간·좌석·금액)
- 고치기: `hold` 의 「좌석 다시 고르기」 → `seats` (선점 풀림)
- 끝: 예약하면 `reserved` / 7분 지나면 `seats--expired` / 남이 먼저 잡으면 `seats--taken` / 5장째 → `seats--limit`

**대상 2 — 무통장 예약 (예매)**
- 만들기: `hold` → 「무통장 예약하기」 → `reserved` (결과 화면)
- 보기: `bookings` → `booking`
- 고치기·취소: 관객 직접 취소는 후속 요청(범위 밖) — 입금하지 않으면 기한에 자동 취소된다는 것을 `hold`·`reserved`·`booking` 에 적는다
- 끝: 입금 확인 → `booking--confirmed` · `bookings--confirmed` / 기한 경과 → `booking--cancelled`
- 첫 사용: `bookings--empty`

**결과 화면의 세 가지**

| 화면 | 무엇이 정해졌나 | 누구에게 어떻게(언제) 전해졌나 | 다음에 무슨 일 (되돌릴 수 있나) |
|---|---|---|---|
| `reserved` | R석 3석 예약, 입금 대기 | 관객 본인 — 이 화면과 내 예매에 저장(알림 발송 없음) | 오늘 오후 11:59 까지 입금 확인되면 예매 확정, 안 되면 자동 취소·좌석 다시 판매. 직접 취소는 후속 요청 |
| `booking--confirmed` | 예매 확정 3석 | 운영자가 11월 24일 오후 4:20 에 입금 확인 → 내 예매에 바로 표시 | 공연 당일 입장. 모바일 티켓·취소·양도는 후속 요청 |
| `booking--cancelled` | 예약 자동 취소 | 입금 기한 11월 21일 (금) 오후 11:59 경과 → 다음 조회 때 내 예매에 표시 | 좌석은 다시 판매 중. 같은 공연을 다시 고를 수 있다(되돌리기 없음) |

함께 쓰기 고리: 해당 없음 — 관객 혼자 예매하고, 운영자는 화면 없이 API 로만 관여한다.

## 6. 가정 로그

- 좌석도 부품이 키트에 없다 → 화면 `<style>` 에 토큰 변수만으로 좌석 칸(`.seatmap`)을 짠다. 좌석 칸 상태 표시는 기존 선택 규칙을 따른다: 고를 수 있음 = 흰 칸 + 선, 내가 고름 = 브랜드 채움(design.md §2 「지금 고를 수 있는 것」), 고를 수 없음 = 비활성 회색.
- 선점·판매된 좌석은 관객에게 구분할 이유가 없어 「고를 수 없음」 하나로 묶었다(AC-2 거절 문구도 「다른 관객이 먼저 골랐어요」 하나).
- 7분 남은 시간은 판촉 부품 `countdown` 이 아니라 머리글의 큰 숫자(`.num`)로 — design.md §6 이 남은 시간 띠를 막고, §2 가 숫자를 주인공으로 둔다.
- 입금자명 입력 칸을 두지 않고 예약자 이름(User.name)으로 안내한다 — 사용자 결정 질문 Q2.
- 예매번호를 화면에 보인다 — 운영자가 입금과 예약을 맞추는 데 필요. 예약 테이블이 새로 생기므로(V10) 새 필드 — Eng 리뷰에 넘김.
- 입금 계좌는 서비스 하나의 고정 계좌로 둔다(설정값) — 공연별·주최자별 계좌는 정산 문제라 범위 밖.
- 자동 취소는 design.md §5 의 「끝난 상태는 평문」 규칙대로 배지 없이 「입금 기한이 지나 취소됨」.
- 알림(문자·푸시·메일)은 없다 — 확정은 내 예매에서 확인한다(목표 문장 그대로). 사용자 결정 질문 Q3.
- 관객에게 보이는 범위 외 표기는 내부 말(「후속 요청」) 대신 「아직 할 수 없어요」로 쓴다 — D6 의 「후속 요청에서 다룸」은 문서·캔버스 정책 줄에 남긴다.
- 화면 유형: `bookings` = 행 목록(국내 예매 앱 「예매 내역」 관례), `booking` = 진행 추적형(선점 → 예약 → 입금 확인 → 확정 단계).
- 데스크톱은 앱 안 목적지가 2곳(공연·내 예매)이라 사이드 내비 없이 본문 + 보조 열로 짠다.
