# 릴리스 · 배포 — 확장 지점 (현재 미구현)

이 디렉터리는 **배포 런북과 롤백 기준**을 두는 자리다. 지금은 비어 있고,
워크플로우는 머지(`/wf-ship`)까지만 담당한다.

---

## 어디까지 되어 있나

배포 계층은 **git-flow + GitHub Actions** 기준으로 5단계를 설계했고, 1단계만 구현했다.

| 단계 | 무엇 | 상태 |
|---|---|---|
| 1 | Ship + 신선도 검사 | **구현됨** (`/wf-ship`, `check_freshness.py`, `ship_preflight.py`) |
| 2 | 릴리스 문서 — 런북 · 롤백 기준 · 버전 규칙 | 설계만 |
| 3 | `/wf-release` + 릴리스 노트 생성 | 설계만 |
| 4 | GitHub Actions 게이트 | 설계만 |
| 5 | 배포 트리거 · 관측 | 설계만 |

**설계 전문**: https://claude.ai/code/artifact/eb495010-4d84-41e7-b711-8ba6195e128c

브랜치 대응, hotfix 축약 경로, CI 워크플로우 구성이 그 문서에 있다.
이어서 작업할 때 그것부터 읽으면 된다.

---

## 언제 이어서 하나

각 단계마다 **선행 조건**이 있다. 조건이 충족되기 전에 만들면 써보지 않은 것을 문서로
확정하는 셈이 된다.

| 단계 | 시작 조건 | 없으면 생기는 일 |
|---|---|---|
| **2. 릴리스 문서** | **배포 방식이 정해졌을 때** (어디에·어떻게 배포하는지) | 사고 한가운데서 "롤백할까요?"를 논의하게 된다 |
| **3. `/wf-release`** | 태스크 **3~5건**이 기준 브랜치에 쌓였을 때 | 그 전에는 릴리스 노트를 손으로 쓰는 게 30초다 |
| **4. GitHub Actions** | 협업자가 생기거나 **로컬 검사를 건너뛴 사례**가 나왔을 때 | 혼자 쓰는 동안은 로컬 스크립트가 CI와 같은 일을 한다 |
| **5. 배포 트리거** | 배포가 **반복 작업**이 됐을 때 | 첫 몇 번은 손으로 하며 런북을 다듬는 편이 낫다 |

2번이 나머지와 성격이 다르다 — 자동화가 아니라 **사람이 읽는 판단 기준**이라 첫 배포
*전에* 있어야 한다. 3~5번은 배포를 몇 번 해본 뒤가 낫다.

---

## 어떻게 재개하나

새 세션에서 이렇게 말하면 된다.

```
docs/release/README.md 를 읽고 배포 설계 2번(릴리스 문서)을 진행해줘
```

그러면 이 문서 → 설계 Artifact 순으로 읽고 이어서 작업한다.
설계를 다시 설명하지 않아도 된다.

2번을 시작할 때 필요한 정보:

- 배포 대상 (어떤 환경에, 무엇을 올리나)
- 스테이징이 있나
- 롤백 수단 (이전 버전 재배포? 트래픽 전환? DB 마이그레이션은?)
- 버전 규칙 (SemVer 를 쓴다면 major 를 언제 올리나)

## 만들 때 무엇이 생기나

```
docs/release/
├── runbook.md            배포 절차 — 단계별 명령과 확인 지점
├── rollback-criteria.md  무엇이 관찰되면 롤백하나. 판단을 미리 내려둔다
└── versioning.md         버전 규칙, 태그 형식, CHANGELOG 규약
```

3번 이후로는 `/wf-release` 커맨드, `release_notes.py`, `.github/workflows/` 3개가 더해진다.

---

## 지금 하지 않는 이유

이 스타터는 아직 실제 태스크를 완주해본 적이 없다. 배포 설계를 지금 굳히면 **써보지 않은
것을 문서로 확정**하게 된다.

원본 저장소에서 그 일이 실제로 벌어졌다 — Linear/Asana 잔재 3건이 실행 불가 상태로
남았고, `task-order-planner.md` 228줄은 아무 규칙도 참조하지 않는 고아 파일이 되었다.
쓰지 않는 규칙은 낡는다.
