# [관객/주최자] 이메일 인증과 비밀번호 찾기

**상태**: 초안
**최종 갱신**: 2026-11-12

---

## 1. 요구사항

### 1-1. 배경

이메일로 가입한 계정에는 두 가지 구멍이 있다. 하나는 **그 이메일이 정말 가입자 것인지 확인하는 수단이 없다**는
것이다. 누구나 남의 이메일로 가입할 수 있고, 그래서 소셜 로그인 자동 연결은 이메일 소유가 확인된 계정에만
하도록 좁혔다([ADR-0020](../../decisions/ADR-0020-auto-link-only-to-email-verified-accounts.md)). 다른 하나는
**비밀번호를 잊으면 되찾을 방법이 없다**는 것이다. 같은 이메일로 다시 가입하면 중복(409)이라 계정을 영영 잃는다.

두 문제가 이 문서에서 함께 풀리는 이유는 같은 재료를 쓰기 때문이다 — 이메일로 **일회용 링크**를 보내고, 링크를
누른 사람이 그 메일함의 주인이라고 본다. 지금은 메일을 보낼 수단이 없어 두 기능을 `user-authentication.md` §7 이
범위 밖으로 뒀다. 이 문서가 그 수단(메일 발송, 일회용 토큰)을 만들고 두 기능을 얹는다.

| AS-IS | TO-BE |
|---|---|
| 이메일 가입은 메일 소유 확인이 없다 — 남의 이메일로 가입할 수 있다 | 가입하면 인증 메일을 보내고, 링크를 눌러야 이메일(비밀번호) 로그인이 된다 |
| 가입 직후 자동 로그인되어 가입 완료 화면(`/joined`)으로 간다 | 가입 직후에는 「인증 메일을 보냈어요」 안내로 간다. 인증한 뒤 로그인한다 |
| 비밀번호를 잊으면 복구 수단이 없다 | 로그인 화면의 「비밀번호 찾기」 → 메일의 링크 → 새 비밀번호 |
| 소셜 전용 계정(비밀번호 없음)은 이 문제와 무관하다 | 비밀번호 찾기를 요청해도 비밀번호를 만들어 주지 않고, 소셜 계정으로 로그인하라는 안내 메일만 받는다 |

**이번에 정한 것** (2026-11-12, 사용자 결정)

- 메일 발송은 `MailSender` 인터페이스 뒤에 SMTP(Spring Mail)를 둔다. 발송 서비스는 배포 설정으로 정하고,
  개발·테스트는 로그 출력으로 대체한다. 새 외부 의존이므로 ADR 로 남긴다
- 인증하지 않은 이메일 계정은 **이메일(비밀번호) 로그인을 막는다**
- 소셜 전용 계정의 비밀번호 찾기는 안내 메일만 보낸다 — 소셜 전용 계정에 비밀번호를 추가하지 않는
  기존 결정(`user-authentication.md` §7)을 유지한다
- 차단은 **이메일(비밀번호) 로그인에만** 건다. 소셜 로그인은 제공자 계정으로 이미 확인된 것이라 막지 않는다.
  제공자가 이메일을 검증하지 않은 소셜 계정(카카오 미검증·네이버)의 이메일 인증은 이번 범위 밖이다(§7)
- 기존 이메일 가입자(`email_verified=false`)는 **재인증을 요구**한다. 확인하지 않은 이메일을 인증된 것으로
  표시하지 않는다 — ADR-0020 의 신뢰 조건이 유지된다. 비밀번호가 맞으면 인증이 필요하다고 알리고 인증 메일을
  자동으로 보낸다
- 남용 방지는 **같은 이메일의 재발송 간격 제한**만 둔다(60초). IP 기준 제한은 범위 밖이다

**분리 이유**: 메일 발송과 일회용 토큰은 인증과 재설정이 함께 쓰는 기반이라 먼저 떼어(A) 두 기능을 병렬로 얹는다. 이메일 인증(B)은
가입·로그인 동작이 바뀌어 기존 테스트 19개 파일의 Given 이 흔들리는 일이라 위험이 따로 있고, 비밀번호 재설정(C)은 새 경로
두 개뿐이라 가볍다. 프론트는 B·C 각각의 화면(D·E)에 붙이고, 「비밀번호 찾기」 링크는 갈 화면이 생기는 E 에 둬 갈 곳 없는
링크가 D 에 남지 않게 한다. 새 화면 시안이 없어 **시안 추가가 D·E 의 선행**이다(주최자 흐름과 같다).

```
흐름
  A(메일·토큰 기반) ──┬──► B(이메일 인증 API) ──► D(인증 화면)
                      └──► C(비밀번호 재설정 API) ──► E(재설정 화면)
          [새 화면 시안 out/screens/ — D·E 를 만들기 전에 추가한다]
```

### 1-3. 상세

데이터·API 규칙은 §3 이 정본이다. 요점만:

- **인증 전 차단 범위** — 이메일(비밀번호) 로그인만. 소셜 로그인은 막지 않는다
- **기존 가입자** — 마이그레이션이 `email_verified` 를 바꾸지 않는다. 로그인하면 403 과 인증 메일을 받고, 인증한 뒤 로그인한다
- **토큰** — 해시로 저장, 1회용, 인증 24시간·재설정 30분. 링크는 URL fragment, 확인은 POST
- **응답 일관성** — 재발송·비밀번호 찾기는 계정 유무와 무관하게 같은 200 이고, 간격 제한은 429 가 아니라 조용히 건너뛴다
- **자동 로그인 없음** — 가입·인증·재설정 어느 쪽도 로그인 토큰을 주지 않는다
- **소셜 연결과의 관계** — 소셜 로그인 코드는 바뀌지 않는다. 인증된 이메일 계정이 처음 생기므로 ADR-0020 의 자동 연결 조건이 이메일 가입 계정에도 성립한다(Task B 의 회귀 확인)

## 2. 화면 설계

**UI 라이브러리**: MUI (ADR-0002)
**디자인 정본**: `docs/product/design.md` · `design-tokens.css`
**시안**: 이 문서의 새 화면(2-5)에는 `out/screens/` 시안이 없다 — 프론트 태스크 전에 추가한다(ADR-0022)

### 2-1. 이 화면에서 사용자가 하려는 일

이메일 소유를 증명해 계정을 쓸 수 있게 하고, 비밀번호를 잊었을 때 같은 방법으로 새 비밀번호를 정한다.

### 2-2. 참조

상용 티켓 서비스(인터파크·멜론티켓·예스24)의 가입·비밀번호 찾기 도움말을 찾아봤지만 검색으로 확인하지
못했다. 이 영역은 계정 복구라 도메인 특수성이 작고, 확인된 표준 지침을 참조로 삼는다. 서비스 화면을 대조하고
싶으면 스크린샷이나 URL 을 받아 이 표에 행을 더한다.

| 참조 | 이 화면에 해당하는 부분 | 우리에게 없는 것 |
|---|---|---|
| OWASP Forgot Password Cheat Sheet | 재설정 요청은 계정이 있든 없든 같은 응답을 주고 응답 시간도 맞춘다. 토큰은 암호학적 난수로 만들고 1회용이며 만료되고 사용 뒤 무효화한다. 비밀번호가 바뀌면 메일로 알린다(비밀번호는 담지 않는다). 기존 세션을 무효화할지 묻는다. 계정 단위 속도 제한. 링크는 요청 Host 를 믿지 않고 고정 주소로 만들고, 재설정 페이지에는 no-referrer 를 둔다 | 일회용 토큰 저장소, 메일 발송, 변경 알림 메일, 기존 세션 무효화 수단(JWT 는 서버에 세션이 없다), 재설정 화면 |
| OWASP Authentication Cheat Sheet | 가입 중에 이메일을 검증한다. 가입 응답도 계정 존재를 드러내지 않는다 — 「이미 사용 중」 대신 「활성화 링크를 보냈다」로 답한다. 로그인 실패는 원인을 구분하지 않는 일반 문구로 답하고, 「비활성 계정」 같은 사유 노출은 잘못된 예로 든다 | 이메일 검증 단계, 가입 응답의 중복 노출(지금은 409 와 「이미 가입된 이메일이에요」), 인증 전 계정의 로그인 응답 |

**대조 결과**

- **넣는 것:** 일회용 토큰(해시로 저장·1회용·만료), 인증 메일·재설정 메일·비밀번호 변경 알림 메일, 재설정 요청의
  동일 응답, 같은 이메일 재발송 간격 제한, 링크는 고정 주소와 URL fragment(ADR-0021)로 만든다
- **OWASP 와 다르게 가는 것 세 가지** (2026-11-12, 사용자 결정)
  1. 가입 응답은 **이메일 중복(409)을 계속 드러낸다** — OWASP 는 같은 응답을 권하지만 기존 화면·승인 테스트를
     유지한다. 계정 존재 노출은 수용하고 §7 에 남긴다. 재설정 요청 쪽은 같은 응답을 준다
  2. 이미 있는 **미인증** 이메일로 다시 가입하면 **나중 가입이 덮어쓴다** — 비밀번호·이름·역할을 새 값으로 바꾸고
     이전 토큰을 모두 무효로 한다. 메일함 주인만 인증할 수 있어 선점 가입이 의미를 잃는다
  3. 비밀번호를 바꿔도 **이미 발급된 로그인 토큰(최대 24시간)은 그대로 둔다** — 변경 알림 메일로 알리는 데까지
     하고 §7 에 남긴다(ADR-0012·0029 의 「필터가 DB 를 읽지 않는다」 유지)
- **로그인 응답:** 인증 전 계정은 **비밀번호가 맞은 경우에만** 「인증이 필요해요」를 알린다. 비밀번호를 모르는
  사람에게는 계정 상태가 드러나지 않는다. OWASP 가 말하는 사유 노출과 달리 자격 증명을 가진 사람에게만 알려 주는
  선택이고, 인증 메일 자동 발송이 이 응답에 달려 있어 일부러 택한다

| 2 | 「가입된 이메일이면 재설정 메일을 보냈어요」 | 계정 유무와 무관하게 같은 문구(계정 존재 비노출) | 고정 문구 |
| 3 | 「로그인으로」 | 되돌아가기 | — |

**⑤ 비밀번호 재설정** (`/reset-password#token=…`)

| 우선 | 요소 | 왜 필요한가 | 데이터 출처 |
|---|---|---|---|
| 1 | 새 비밀번호 · 확인 칸(8자 이상 72자 이하) | 2-1 의 목적. 가입과 같은 규칙 | ⚠ `POST /api/auth/password-reset/confirm` |
| 2 | 「비밀번호를 바꿨어요」 + 「로그인하기」 | 성공 뒤 다음 행동. 자동 로그인은 하지 않는다 | — |
| 3 | 「링크가 올바르지 않거나 만료됐어요」 + 「다시 요청하기」 | 만료·사용된 링크의 출구 | — |

**메일 네 종류**(화면 밖이지만 문구를 §3-4 에서 정한다): 인증 · 재설정 · 비밀번호 변경 알림(비밀번호는 담지
않는다) · 소셜 안내(소셜 전용 계정이 비밀번호 찾기를 요청했을 때 재설정 대신 보낸다).

### 2-4. 배치

화면이 모두 한 열의 짧은 안내·폼이라 세로로 쌓는다. 가입·로그인과 같은 인증 화면 문법(`Page plain`, 전역 헤더 없음 —
TASK-018 결정)을 쓴다.

```
① 인증 메일 안내          ② 인증 결과               ④ 비밀번호 찾기          ⑤ 재설정
┌────────────────┐      ┌────────────────┐      ┌────────────────┐     ┌────────────────┐
│ ‹              │      │                │      │ ‹              │     │                │
│  [메일 그림]   │      │  [그림]        │      │ 비밀번호를     │     │ 새 비밀번호를  │
│ 인증 메일을    │      │ 인증됐어요     │      │ 잊으셨나요     │     │ 정해요         │
│ 보냈어요       │      │ 이제 로그인할  │      │ 이메일  [____] │     │ 비밀번호 [____]│
│ a@b.com        │      │ 수 있어요      │      │                │     │ 확인     [____]│
│ 메일의 링크를  │      │                │      │                │     │ 8자 이상 72자… │
│ 누르세요       │      │ ┌────────────┐ │      │ ┌────────────┐ │     │ ┌────────────┐ │
│ 스팸함도 확인  │      │ │ 로그인하기 │ │      │ │ 메일 보내기│ │     │ │ 바꾸기     │ │
│ ┌────────────┐ │      │ └────────────┘ │      │ └────────────┘ │     │ └────────────┘ │
│ │다시보내기 52s│ │      └────────────────┘      └────────────────┘     └────────────────┘
│ └────────────┘ │
│ 로그인으로     │      ③ 로그인(변경)  비밀번호 칸 아래에 「비밀번호 찾기」, 맨 위에 인증 필요 안내
└────────────────┘
```

**이 배치인 이유**: 사용자가 하는 일이 화면마다 하나(메일 확인·인증·이메일 입력·새 비밀번호)라 한 열에 하나의 주
행동을 둔다. 주 버튼은 하단 한 줄, 되돌아가기는 상단 `‹` 로 가입·로그인과 같다.

### 2-5. 상태별로 무엇이 보이나

| 화면 | 상태 |
|---|---|
| ① 인증 메일 안내 | 기본(재발송 간격 중) · 재발송 가능 · 재발송 중 · 재발송 접수 · 재발송 오류 · 이메일 없이 직접 진입 |
| ② 인증 링크 결과 | 확인 중 · 성공 · 링크 무효(잘못됨·만료·이미 사용) · 서버 오류 · 토큰 없이 진입 |
| ③ 로그인 | 기존 상태 + 인증 필요(403) · 인증 필요 + 재발송 접수 |
| ④ 비밀번호 찾기 | 기본 · 이메일 형식 오류 · 제출 중 · 접수(항상 같은 문구) · 서버 오류 |
| ⑤ 재설정 | 기본 · 검증 오류(길이·불일치) · 제출 중 · 성공 · 링크 무효 · 서버 오류 · 토큰 없이 진입 |

- **① 기본** — 보낸 주소와 「다시 보내기」가 비활성으로 남은 초(60초부터)를 센다. 0이 되면 활성화된다
- **① 재발송 접수** — 「메일을 다시 보냈어요」, 버튼은 다시 60초 비활성. 서버가 간격 안이라 보내지 않았어도 같은 문구다
- **① 이메일 없이 직접 진입** — 새로고침으로 이동 상태가 사라지면 주소를 모른다. `/login` 으로 보낸다
- **② 확인 중** — 진행 표시. 토큰은 읽는 즉시 주소에서 지운다(ADR-0021)
- **② 성공** — 「인증됐어요」 + 「로그인하기」. 자동 로그인은 하지 않는다
- **② 링크 무효** — 잘못됨·만료·이미 사용을 구분하지 않고 「링크가 올바르지 않거나 이미 사용했어요」. 버튼은 「로그인하기」
  하나이고 아래에 「아직 인증하지 않았다면 로그인하면 인증 메일을 다시 보내 드려요」를 둔다 — 두 번 눌러 이미 인증된
  사람도, 만료된 사람도 같은 길로 간다
- **② 토큰 없이 진입** — 링크 무효와 같은 화면
- **③ 인증 필요(403)** — 맨 위 안내 「이메일 인증이 필요해요. 인증 메일을 보냈어요」 + 「메일 다시 보내기」. 비밀번호가 틀린
  경우에는 지금처럼 「이메일 또는 비밀번호가 올바르지 않아요」만 보인다(계정 상태 비노출)
- **④ 접수** — 가입된 이메일이든 아니든, 소셜 전용이든 같은 문구 「가입된 이메일이면 재설정 메일을 보냈어요」
- **④ 서버 오류** — 요청 자체가 실패했을 때(5xx·네트워크)만 「요청하지 못했어요. 잠시 후 다시 시도해 주세요」. 입력한 이메일은 남긴다. 메일 발송 실패는 사용자에게 알리지 않는다(§3-3)
- **⑤ 검증 오류** — 가입과 같은 규칙·같은 문구(「8자 이상 72자 이하로 정해요」, 「비밀번호가 일치하지 않아요」)
- **⑤ 성공** — 「비밀번호를 바꿨어요」 + 「로그인하기」. 열어 둔 다른 로그인은 그대로다(§7)
- **⑤ 링크 무효·토큰 없이 진입** — 「링크가 올바르지 않거나 만료됐어요」 + 「다시 요청하기」(→ ④)

**이 상태 목록이 그대로 §5 완료 조건이 된다.** **2-3 의 「데이터 출처」 ⚠ 가 그대로 §3 API 명세가 된다.**

## 3. 데이터·API 명세

### 3-1. 마이그레이션

번호는 구현 시점의 다음 번호를 쓴다(TASK-023 이 V8 을 쓴다).

```sql
-- 일회용 이메일 링크 토큰. 원문은 저장하지 않고 SHA-256 해시만 둔다(DB 가 새도 링크를 만들 수 없다)
CREATE TABLE email_token (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    purpose     VARCHAR(20) NOT NULL,          -- 'VERIFY_EMAIL' | 'RESET_PASSWORD'
    token_hash  CHAR(64)    NOT NULL UNIQUE,   -- SHA-256(원문) 16진 소문자
    expires_at  TIMESTAMPTZ NOT NULL,
    used_at     TIMESTAMPTZ,                   -- 사용한 시각. NULL 이면 아직 쓸 수 있다
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_email_token_user_purpose ON email_token (user_id, purpose);

-- 계정으로 나가는 메일(인증·재설정·소셜 안내)의 마지막 발송 시각. 60초 간격 제한의 기준이다
ALTER TABLE users ADD COLUMN account_mail_sent_at TIMESTAMPTZ;
```

- `users.email_verified` 는 이미 있다(V4). 기존 이메일 가입 행은 전부 `false` 로 두고 **바꾸지 않는다** — 재인증을 요구한다
- 토큰 원문은 32바이트 난수(`SecureRandom`)를 URL-safe Base64 로 쓴 43자다. 만료는 `VERIFY_EMAIL` 24시간,
  `RESET_PASSWORD` 30분이다. OWASP 는 기간을 정하지 않아 우리가 정한 값이다

### 3-2. API

모두 인증 없이 호출한다(`SecurityConfig` 의 `permitAll` 에 추가). 오류 본문은 기존 `{ "code", "message" }` 형식이다.

| 메서드 · 경로 | 요청 | 응답 | 비고 |
|---|---|---|---|
| `POST /api/auth/signup` | 기존 `SignUpRequest` | 201 `UserResponse`(기존) | **동작이 바뀐다** — §3-3. 자동 로그인에 쓰던 흐름은 프론트가 없앤다 |
| `POST /api/auth/login` | 기존 | 200 `LoginResponse` / 401 `INVALID_CREDENTIALS` / **403 `EMAIL_NOT_VERIFIED`** | 403 은 **비밀번호가 맞은 뒤에만**. 그때 인증 메일을 보낸다 |
| `POST /api/auth/email-verification/resend` | `{ "email" }` | 200 `{}` | 항상 같은 응답 |
| `POST /api/auth/email-verification/confirm` | `{ "token" }` | 200 `{}` / 400 `TOKEN_INVALID` | 잘못됨·만료·이미 사용을 구분하지 않는다 |
| `POST /api/auth/password-reset/request` | `{ "email" }` | 200 `{}` | 항상 같은 응답 |
| `POST /api/auth/password-reset/confirm` | `{ "token", "password", "passwordConfirm" }` | 200 `{}` / 400 `TOKEN_INVALID` / 400 `INVALID_REQUEST` | 비밀번호 규칙은 가입과 같다 |

```java
// api/dto — 검증 애노테이션은 SignUpRequest 와 같은 것을 쓴다
record EmailRequest(@NotBlank @Email @Size(max = 255) @Pattern(regexp = NoLoneSurrogate.REGEX, ...) String email) {}
record ConfirmEmailRequest(@NotBlank @Size(max = 200) String token) {}
record ResetPasswordRequest(
    @NotBlank @Size(max = 200) String token,
    @NotBlank @Size(min = 8, max = 72) @Pattern(regexp = NoLoneSurrogate.REGEX, ...) String password,
    @NotBlank String passwordConfirm) {}
```

- `token` 의 길이는 검증하지 않는다(상한만). 메일 앱이 링크를 잘라 짧아진 토큰도 400 `INVALID_REQUEST` 가 아니라
  `TOKEN_INVALID` 로 답해 화면이 「링크 무효」 한 가지만 다루게 한다
- 비밀번호 72바이트 검사(`exceedsBcryptLimit`)와 확인란 일치는 서비스가 한다(가입과 같다)
- **429 를 쓰지 않는다.** 간격 제한은 조용히 건너뛴다 — 응답이 같아야 계정 존재가 드러나지 않는다

### 3-3. 동작 규칙

**메일은 응답과 무관하게 보낸다.** 요청 처리와 발송을 분리해(커밋 뒤 비동기) 응답과 응답 시간이 메일 발송 성공·실패와
무관하다. 발송이 실패하면 로그만 남긴다. 그래서 응답으로는 메일이 갔는지 알 수 없고, 화면 문구도 「보냈어요」가 아니라
「가입된 이메일이면 보냈어요」(④)나 간격 카운트다운(①)으로 쓴다.

**간격 제한.** `users.account_mail_sent_at` 이 60초 안이면 메일을 보내지 않는다. 비교와 갱신은 한 번의 조건부 `UPDATE`
(`… WHERE id = ? AND (account_mail_sent_at IS NULL OR account_mail_sent_at < :now - 60초)`)로 해 동시 요청에도 한
통만 나간다. 인증·재설정·소셜 안내 메일이 같은 기준을 쓴다. 변경 알림 메일은 유효한 토큰으로만 일어나므로 제한하지 않는다.

**가입(`/signup`)**

| 이메일의 상태 | 동작 |
|---|---|
| 없음 | `users` 행을 `email_verified=false` 로 만들고 인증 토큰을 발급해 메일을 보낸다. 201 |
| 있음 · 인증됨 | 지금처럼 409 `EMAIL_ALREADY_EXISTS` |
| 있음 · **미인증 · 비밀번호 있음 · 소셜 연결 없음** | 비밀번호·이름·역할을 새 값으로 **덮어쓰고**, 이전 인증 토큰을 모두 지우고, 새 토큰으로 메일을 보낸다(간격 안이면 메일만 건너뛴다). 201 |
| 있음 · 미인증 · 비밀번호 없음 또는 소셜 연결 있음 | 409 — 소셜 계정을 이메일 가입이 덮어쓰지 못한다 |

**로그인(`/login`)** — 이메일·비밀번호가 맞고 `email_verified=false` 이면 인증 토큰을 새로 발급해 메일을 보내고(간격
안이면 건너뜀) 403 `EMAIL_NOT_VERIFIED`. 비밀번호가 틀리거나 계정이 없거나 소셜 전용이면 지금처럼 401 이다. 소셜
로그인에는 영향이 없다.

**인증 재발송(`/email-verification/resend`)** — 이메일이 있고, 비밀번호가 있고, 미인증이면 새 토큰(이전 것은 지운다)으로 메일을
보낸다. 그 밖(없음·이미 인증됨·소셜 전용)은 아무것도 하지 않는다. 항상 200.

**인증 확인(`/email-verification/confirm`)** — 토큰 해시가 있고 `VERIFY_EMAIL` 이고 쓰지 않았고 만료 전이면
`used_at` 을 채우고 `email_verified=true` 로 바꾼다. 토큰 소모는 `UPDATE … WHERE used_at IS NULL AND expires_at > now`
가 한 행을 바꿨는지로 판단한다(동시 클릭에도 한 번만 성공). 로그인 토큰은 발급하지 않는다.

**비밀번호 찾기(`/password-reset/request`)** — 이메일이 있으면:
- 비밀번호가 있으면 재설정 토큰(이전 것은 지운다)으로 재설정 메일을 보낸다. 미인증 계정도 보낸다
- 소셜 전용(비밀번호 없음)이면 재설정 토큰 없이 「소셜 계정으로 로그인해 주세요」 안내 메일만 보낸다

없으면 아무것도 하지 않는다. 항상 200.

**비밀번호 재설정(`/password-reset/confirm`)** — 토큰이 유효하면 비밀번호 해시를 바꾸고, `email_verified=true` 로
바꾸고(메일함 주인이 확인됐다), 토큰을 쓴 것으로 하고, 그 사용자의 남은 재설정 토큰을 지우고, 변경 알림 메일을 보낸다.
이미 발급된 로그인 토큰은 무효화하지 않는다(§7).

### 3-4. 메일 네 종류

| 메일 | 제목 | 본문 요지 | 링크 |
|---|---|---|---|
| 인증 | 이메일 인증을 해 주세요 | 가입을 마치려면 링크를 눌러요. 직접 가입하지 않았다면 무시해 주세요. 24시간 안에 눌러 주세요 | `{FRONTEND_BASE_URL}/verify-email#token={원문}` |
| 재설정 | 비밀번호를 다시 정해 주세요 | 링크를 눌러 새 비밀번호를 정해요. 요청하지 않았다면 무시해 주세요. 30분 안에 눌러 주세요 | `{FRONTEND_BASE_URL}/reset-password#token={원문}` |
| 변경 알림 | 비밀번호를 바꿨어요 | 방금 바꿨다는 알림. 본인이 아니라면 다시 비밀번호 찾기를 해 주세요(비밀번호는 담지 않는다) | — |
| (소셜 안내) | 소셜 계정으로 로그인해 주세요 | 이 이메일은 카카오·구글 등 소셜 계정으로 가입돼 있어 비밀번호가 없어요 | `{FRONTEND_BASE_URL}/login` |

링크의 주소는 **요청의 Host·헤더를 쓰지 않고** `FRONTEND_BASE_URL` 로 만든다. 지금은 소셜 제공자가 설정돼 있을 때만 필요한
값인데, 이제 항상 필요하다(기동 시 검증).

### 3-5. 설정

| 이름 | 용도 |
|---|---|
| `MAIL_TRANSPORT` | `smtp` 또는 `log`. 운영에서 비어 있으면 기동 실패(조용히 메일이 안 나가는 일을 막는다) |
| `SPRING_MAIL_HOST` · `_PORT` · `_USERNAME` · `_PASSWORD` | SMTP 접속 정보(`smtp` 일 때) |
| `MAIL_FROM` | 보내는 사람 주소 |
| `FRONTEND_BASE_URL` | 링크의 기준 주소(기존 값 — 이제 항상 필수) |

## 4. 흐름

**이메일 가입 → 인증 → 로그인**

```
가입 폼 ──POST /signup──► 서버: users 행(미인증) + 토큰 발급 ──(커밋 뒤)──► 인증 메일
   │                        └ 이미 있는 미인증 이메일이면 값을 덮어쓰고 이전 토큰을 지운다
   ▼ 201
① 인증 메일 안내 ──「다시 보내기」(60초 뒤)──► POST /email-verification/resend ──► 200(항상)
   │
   │  메일함에서 링크를 누른다
   ▼
② /verify-email#token=… ──POST /email-verification/confirm──► 200 → 「인증됐어요」
   │                                                        400 → 「링크가 올바르지 않거나 이미 사용했어요」
   ▼
/login ──POST /login──► 200 → 홈(또는 가려던 화면)
```

**인증 전에 로그인할 때 (기존 가입자 · 메일을 놓친 사람)**

```
/login ──POST /login──► 비밀번호가 틀림 ──► 401 INVALID_CREDENTIALS (지금처럼, 계정 상태 비노출)
                    └─► 비밀번호가 맞고 미인증 ─► 서버가 인증 메일을 보냄 + 403 EMAIL_NOT_VERIFIED
                                                   └─► ③ 「인증이 필요해요」 → 메일의 링크 → ②
```

**비밀번호 찾기**

```
/login 「비밀번호 찾기」 ──► ④ ──POST /password-reset/request──► 200(항상) ──► 「가입된 이메일이면 보냈어요」
                                       서버(커밋 뒤)
                                       ├ 비밀번호 있음 ──► 재설정 메일
                                       ├ 소셜 전용     ──► 소셜 안내 메일
                                       └ 없음          ──► 아무것도 하지 않음

메일의 링크 ──► ⑤ /reset-password#token=… ──POST /password-reset/confirm──► 200 → 「바꿨어요」 → /login
                                                                         400 → 「링크 무효」 → ④
```

**메일이 나가는 모든 요청의 서버 처리 순서**

```
요청 ──► 대상 계정 조회 ──► 간격 확인(조건부 UPDATE) ──► 토큰 발급(이전 것 삭제) ──► 커밋 ──► (비동기) 메일 발송
         │                                                                        └ 응답은 이미 나갔다
         └ 계정이 없거나 조건이 맞지 않으면 여기서 끝 — 응답은 같다
```

## 5. 완료 조건

모든 거부 경로의 「DB 변경 없음」과 토큰의 「한 번만」은 **클래스 레벨 `@Transactional` 없이** 리포지토리로 새로 읽어 확인한다.
이메일은 가입과 같은 정규화(대소문자·앞뒤 공백)로 찾는다. 시각은 `Clock` 을 고정해 만료 경계(정각 포함)를 확인한다.

### Task A (백엔드 — 메일 발송 기반·일회용 이메일 토큰)

- [ ] `MAIL_TRANSPORT=log` 이면 메일(받는 사람·제목·링크)이 로그로 남고, `smtp` 이면 SMTP 로 나간다. 테스트는 보낸 메일을 모아 단언한다
- [ ] 운영에서 `MAIL_TRANSPORT` 가 비었거나 `FRONTEND_BASE_URL` 이 올바르지 않으면 기동이 실패한다
- [ ] 발급한 토큰의 원문은 43자이고, DB 에는 SHA-256 해시만 있다(DB 조회로 원문이 없음을 확인)
- [ ] 만료는 인증 24시간, 재설정 30분이다. 만료 시각 정각에는 이미 만료다
- [ ] 유효한 토큰은 한 번만 소모된다 — 동시에 두 요청을 보내면 한 쪽만 성공한다
- [ ] 같은 사용자·용도로 새 토큰을 발급하면 이전 토큰은 사라진다
- [ ] 마지막 메일 발송 60초 안의 요청은 메일을 보내지 않고, 60초가 지나면 보낸다(동시 요청에도 한 통)
- [ ] 메일의 링크는 `FRONTEND_BASE_URL` 로 만들어지고, 위조한 `Host` 헤더를 실어도 바뀌지 않는다
- [ ] 마이그레이션이 기존 `users` 행(이메일 가입·소셜 가입)을 그대로 두고 적용된다 — `email_verified` 값이 바뀌지 않는다
- [ ] `architecture.md` §5 에 메일 발송 행이 있고, 메일 발송 방식을 정한 ADR 이 있다

### Task B (백엔드 — 이메일 인증 API·인증 전 로그인 차단)

- [ ] 가입하면 201 이고 `email_verified=false` 행이 생기고 인증 메일이 한 통 나간다. 응답에 로그인 토큰은 없다
- [ ] 인증 전 계정이 비밀번호를 맞게 로그인하면 403 `EMAIL_NOT_VERIFIED` 이고 인증 메일이 나간다. 비밀번호가 틀리거나 없는 이메일이거나 소셜 전용이면 지금처럼 401 `INVALID_CREDENTIALS` 이고 메일이 나가지 않는다
- [ ] 인증 확인에 성공하면 200 이고 `email_verified=true` 가 되고 이후 로그인이 200 이다. 로그인 토큰은 이 응답으로 주지 않는다
- [ ] 없는 토큰 · 만료 · 이미 사용 · 재설정용 토큰 · 빈 값 · 짧게 잘린 토큰은 모두 같은 400 `TOKEN_INVALID` 이고 DB 가 바뀌지 않는다
- [ ] 재발송은 미인증이면 새 토큰(이전 것 무효)으로 메일을 보내고, 인증됨·없는 이메일·소셜 전용·간격 안이면 보내지 않는다. 모두 같은 200 본문이다
- [ ] 미인증 이메일로 다시 가입하면 비밀번호·이름·역할이 새 값이 되고(옛 비밀번호로는 로그인 불가) 이전 토큰이 무효가 되고 새 메일이 나간다
- [ ] 인증된 이메일 · 소셜 전용 · 소셜 연결이 있는 미인증 이메일로 가입하면 409 이고 행이 바뀌지 않는다
- [ ] 마이그레이션 전부터 있던 이메일 가입 행(`email_verified=false`)이 로그인하면 403 과 메일을 받고, 인증한 뒤 로그인된다
- [ ] 소셜 로그인은 막히지 않는다. 인증된 이메일 계정과 제공자가 검증한 같은 이메일의 소셜 로그인은 자동 연결되고, 제공자가 검증하지 않았으면 연결되지 않는다(ADR-0020 회귀)
- [ ] 기존 백엔드 테스트가 모두 통과한다 — 가입 뒤 바로 로그인하던 `AuthTestHelper` 사용 테스트가 인증 단계를 거친다
- [ ] `docs/release/first-deploy-checklist.md` 에 SMTP 환경변수·`FRONTEND_BASE_URL` 필수화·기존 가입자 재인증 안내가 있다

### Task C (백엔드 — 비밀번호 찾기·재설정 API)

- [ ] 요청하면 비밀번호가 있는 계정(미인증 포함)에는 재설정 메일이 한 통, 소셜 전용에는 소셜 안내 메일이 한 통(재설정 링크 없음), 없는 이메일에는 메일이 없다. 응답은 모두 같은 200 본문이다
- [ ] 마지막 메일 발송 60초 안의 요청은 메일을 보내지 않는다
- [ ] 유효한 토큰과 올바른 비밀번호로 확인하면 200 이고 새 비밀번호로 로그인되고 옛 비밀번호는 401 이다. `email_verified=true` 가 되고, 남은 재설정 토큰이 사라지고, 변경 알림 메일이 한 통 나간다(본문에 비밀번호가 없다)
- [ ] 같은 토큰으로 두 번째 확인은 400 `TOKEN_INVALID` 이다. 만료 · 인증용 토큰도 같다. 동시에 두 번 보내면 한 번만 성공한다
- [ ] 비밀번호가 7자 · 73자 · 72바이트 초과 · 확인란 불일치 · NUL·짝 없는 서로게이트이면 400 `INVALID_REQUEST` 이고 토큰이 소모되지 않는다(DB 변경 없음)
- [ ] 재설정 전에 발급한 로그인 토큰은 재설정 뒤에도 쓸 수 있다(§7 에서 수용한 동작을 고정한다)

### Task D (프론트 — 인증 메일 안내·인증 결과·로그인 인증 필요)

- [ ] 가입이 201 이면 `/verify-email/sent` 로 가고 이메일이 보인다. 자동 로그인 요청은 가지 않는다
- [ ] ① 「다시 보내기」는 60초부터 줄어들다 0 에서 켜진다. 누르면 재발송 요청이 가고 「메일을 다시 보냈어요」와 함께 다시 60초 비활성이 된다. 요청이 실패하면 오류 문구가 보인다. 새로고침해 주소를 잃으면 `/login` 으로 간다
- [ ] ② 링크의 토큰을 읽는 즉시 주소에서 지우고, 확인 중 → 성공(「로그인하기」) 또는 무효(같은 버튼과 안내)로 간다. 토큰이 없어도 무효 화면이다. 요청이 서버 오류·네트워크 오류로 실패하면 「확인하지 못했어요. 잠시 후 다시 시도해 주세요」와 「다시 시도」가 보인다. 자동 로그인은 하지 않는다
- [ ] ③ 로그인이 403 `EMAIL_NOT_VERIFIED` 이면 「이메일 인증이 필요해요」 안내가 맨 위에 보인다. 안내의 「메일 다시 보내기」를 누르면 재발송 요청이 가고 접수 문구가 보인다. 401 이면 지금 문구 그대로다
- [ ] 소셜 가입·로그인과 가입 완료 화면(`/joined`)은 지금처럼 동작한다
- [ ] 화면을 떠난 뒤 도착한 응답은 이동·표시에 쓰이지 않는다(ADR-0018)
- [ ] 인증 화면은 시안과 같다(Phase 4 화면 확인 — 상태를 실제로 만들어)

### Task E (프론트 — 비밀번호 찾기·재설정 화면)

- [ ] 로그인 화면의 「비밀번호 찾기」가 `/forgot-password` 로 간다
- [ ] ④ 이메일을 제출하면 계정 유무와 무관하게 같은 접수 문구가 보인다. 형식이 틀리면 칸 아래 오류가 보이고 요청이 가지 않는다. 제출 중에는 다시 누를 수 없다. 요청 자체가 실패하면 오류 문구와 입력한 이메일이 남는다
- [ ] ⑤ 토큰을 읽는 즉시 주소에서 지운다. 비밀번호가 8자 미만·72자 초과이거나 확인란이 다르면 가입과 같은 문구의 오류가 보이고 요청이 가지 않는다
- [ ] ⑤ 성공하면 「비밀번호를 바꿨어요」와 「로그인하기」가 보이고 자동 로그인은 하지 않는다. 링크가 무효이거나 토큰이 없으면 「다시 요청하기」(→ ④)가 보인다. 요청이 서버 오류·네트워크 오류로 실패하면 오류 문구가 보이고 입력한 비밀번호는 남는다
- [ ] 인증·재설정 화면은 `Referrer-Policy: no-referrer` 를 적용한다
- [ ] 인증 화면은 시안과 같다(Phase 4 화면 확인 — 상태를 실제로 만들어)

## 7. 범위 외

**하지 않기로 한 것**

- 가입 응답에서 이메일 중복을 숨기는 것 — OWASP 는 권하지만 기존 화면과 승인 테스트를 유지한다(§8)
- 비밀번호를 바꾼 뒤 이미 발급된 로그인 토큰의 무효화 — 최대 24시간 남는다. 하려면 「이 시각 이전 토큰은 무효」 값을 두고 필터가
  요청마다 DB 를 읽어야 하므로 ADR-0012·0029 를 다시 열어야 한다
- IP 기준 속도 제한·CAPTCHA·로그인 시도 횟수 제한 — 같은 이메일의 메일 간격 제한만 한다
- 제공자가 이메일을 검증하지 않은 소셜 계정(카카오 미검증·네이버)의 이메일 인증 — 비밀번호가 없고 소셜로 로그인하므로 이번에는 막지 않는다
- 인증·재설정 완료 뒤 자동 로그인 — 링크만 가진 사람이 로그인되지 않게 한다(§8)
- 메일 발송 실패의 재시도·알림·발신 기록(outbox) — 로그만 남긴다
- HTML 메일 디자인·다국어 — 텍스트 메일 한 벌
- 이메일 변경·계정 삭제·소셜 전용 계정에 비밀번호 추가(기존 결정 유지 — `user-authentication.md` §7)
- 운영자의 수동 인증 처리 — 운영자 기능은 범위 밖(`product.md` §4)

**나중에 할 수도 있는 것**

- 인증하지 않은 가입 행을 일정 기간 뒤 정리(선점으로 쌓이는 행)
- 메일 발송 실패 모니터링·알림
- 소셜 계정의 이메일 인증(마이페이지가 생기면)

**열린 질문**

- 이메일 가입자가 「내 티켓온 아이디」를 처음 보는 곳 — 가입 완료 화면(`/joined`)을 거치지 않으므로 별도로 정해야 한다
- 발송 서비스(SES·Resend·Gmail SMTP 등)와 발신 도메인(SPF·DKIM 설정) — 배포 설정이라 Task A 의 Phase 1 에서 정한다

## 8. 주요 결정 사항

| 결정 | 이유 | 범위 | ADR |
|---|---|---|---|
| 메일은 `MailGateway` 인터페이스 뒤에서 SMTP 로 보내고, 개발·테스트는 로그로 대체한다 | 새 외부 의존을 한 곳에 가둔다(`QueueStore` 와 같은 방식). 발송 서비스는 배포 설정이라 1인 운영 부담이 작다 | **전체** | ADR 신규 (작성 필요) |
| 일회용 링크 토큰은 해시로 DB 에 저장하고, 링크는 URL fragment 로 만들고, 확인은 POST 로 한다 | 원문이 DB 에 없다. 서버 로그·Referer 로 새지 않고(ADR-0021), 메일 보안 검사기가 링크를 먼저 열어도 토큰이 소모되지 않는다 | **전체** (이후 이메일 링크 전부) | ADR 신규 (ADR-0021 확장) |
| 이메일(비밀번호) 로그인은 이메일 인증 전에 막고, 기존 가입자는 재인증을 요구한다 | 확인하지 않은 이메일을 인증된 것으로 표시하지 않는다 — ADR-0020 의 신뢰 조건이 이메일 가입 계정에도 성립하게 된다 | **전체** | ADR 신규 (ADR-0020 보완) |
| 미인증 이메일로 다시 가입하면 나중 가입이 덮어쓴다 | 선점 가입으로 진짜 주인이 막히지 않게 한다. 메일함 주인만 인증할 수 있어 선점 행은 쓸 수 없다. **남는 틈**: 피해자 가입 직후·인증 전에 공격자가 다시 가입하면 피해자가 누른 링크가 공격자의 비밀번호로 계정을 인증한다. 이전 토큰을 지우고, 메일에 「직접 가입하지 않았다면 무시」를 넣고, 인증 뒤 자동 로그인을 하지 않아 피해자가 비밀번호 불일치를 알고 비밀번호 찾기로 복구하게 한다 — 완전히 막지는 못하고 수용한다. 기존 미인증 가입자의 비밀번호를 그 이메일을 아는 누구나 덮어쓸 수 있는 부작용도 수용한다(비밀번호 찾기로 복구) | 이 기능만 | 위 ADR 에 함께 |
| 소셜 로그인은 인증 전 차단 대상이 아니다 | 제공자 계정으로 이미 확인했다. 이메일 인증 없는 소셜 계정은 비밀번호도 없다 | 이 기능만 | — |
| 가입 응답은 이메일 중복을 계속 드러낸다(409) | 기존 화면·승인 테스트를 유지한다. 계정 존재 노출은 수용한다(OWASP 와 다름) | 이 기능만 | — |
| 비밀번호 찾기·인증 재발송은 계정 유무와 무관하게 같은 응답을 준다 | 계정 존재를 드러내지 않는다 | 이 기능만 | — |
| 메일은 응답과 무관하게 커밋 뒤 비동기로 보내고, 실패는 로그만 남긴다 | 응답 내용·시간이 계정 존재와 SMTP 상태를 드러내지 않는다. 대가: SMTP 장애를 사용자가 모른다(운영 알림으로 본다) | 이 기능만 | — |
| 메일 간격 제한은 `users.account_mail_sent_at` 조건부 `UPDATE` 로 하고 429 를 쓰지 않는다 | 한 컬럼으로 모든 계정 메일을 덮고 동시 요청에도 한 통이다. 429 는 계정 존재를 드러낸다 | 이 기능만 | — |
| 비밀번호 재설정이 이메일 인증도 겸한다 | 링크를 누른 사람이 메일함의 주인이다. 아니면 재설정 뒤 로그인할 때 인증 메일을 또 받아야 한다 | 이 기능만 | — |
| 재설정 뒤 이미 발급된 로그인 토큰은 무효화하지 않는다 | JWT 는 서버에 세션이 없고 필터가 DB 를 읽지 않는 구조를 유지한다(ADR-0012·0029). 변경 알림 메일로 알린다 | **전체** (JWT 무효화 정책) | ADR-0012·0029 — §7 에 남김 |
| 인증·재설정이 끝나도 자동 로그인하지 않는다 | 메일을 가진 사람이 곧 로그인되지 않게 한다. 선점 가입 때 피해자가 비밀번호 불일치를 알게 한다 | 이 기능만 | — |
| 토큰 만료는 인증 24시간·재설정 30분이다 | OWASP 가 기간을 정하지 않아 우리가 정했다 — 인증은 메일을 늦게 여는 일이 흔하고, 재설정은 탈취 위험이 커 짧게 둔다 | 이 기능만 | — |
| 소셜 전용 계정에는 비밀번호를 추가하지 않고 안내 메일만 보낸다 | 소셜 전용 계정에 비밀번호를 추가하지 않는 기존 결정(`user-authentication.md` §7)을 유지한다 | 이 기능만 | — |
| 새 화면 시안을 프론트 태스크 전에 `out/screens/` 에 추가한다 | 화면은 시안과 같아야 한다(ADR-0022). 인증·재설정·안내 화면에 시안이 없다 | 이 기능만 | — |

**ADR 승격 후보 세 건**: 메일 발송 방식 · 이메일 링크 토큰 설계 · 이메일 소유 확인 정책(인증 전 차단·재인증·선점 덮어쓰기).
태스크를 만들기 전에 `/wf-adr` 로 남기면 Phase 1 이 참조할 수 있다.
