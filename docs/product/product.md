# 프로덕트 정의

**최종 갱신**: 2026-09-02

---

## 1. 한 문장

공연/행사 티켓 예매 서비스.

## 2. 문제

소규모 공연 주최자는 예매를 전화와 메신저로 받는다. 좌석 배정을 수기로 관리해
같은 자리를 두 번 파는 일이 생기고, 오픈·마감 시각은 공지 채널마다 따로 알린다.
관객은 지금 예매가 가능한지 확인하려면 직접 연락해야 한다.

## 3. 사용자

| 역할 | 무엇을 하는 사람 | 이 프로덕트로 무엇을 하나 |
|---|---|---|
| 관객 (예매자) | 공연을 보러 가고 싶은 일반 사용자 | 공연을 검색하고 좌석을 선택·결제해 티켓을 예매한다 |
| 주최자 (판매자) | 공연을 여는 사람 | 공연을 등록하고 좌석 배치·가격·오픈 시각을 설정하며 예매 현황을 관리한다 |
| 운영/관리자 | 서비스 전체를 운영하는 내부 인력 | 주최자 승인, 정산, 신고 처리 등 서비스 운영을 담당한다 |

역할 이름은 태스크의 `sub_categories` 값과 일치시킨다 (→ `docs/workflow/task-schema.md` §3).

## 4. 범위

### 하는 것

- 공연 조회/검색 (관객)
- 좌석 선택 및 선점 (관객) — 결제 전까지 일정 시간 좌석을 잠가 중복 예매를 막는다
- 공연 등록/관리 (주최자) — 좌석 배치·가격·오픈 시각 설정, 예매 현황 확인

### 하지 않는 것

- 결제/환불 — 온라인 결제 연동, 환불·취소 처리는 다음 단계
- 운영/관리자 전용 기능 — 주최자 승인, 정산, 신고 처리 등은 다음 단계 (역할은 §3에 정의했지만 이번 단계 구현 대상 아님)

## 5. 성공 기준

| 기준 | 측정 방법 | 목표 |
|---|---|---|
| 주최자가 시스템만으로 공연 등록~예매 현황 확인을 끝낸다 | 파일럿 주최자 대상 전화·메신저 문의 건수 집계 | 등록~현황 확인 관련 문의 0건 |
| 관객이 문의 없이 예매 가능 여부를 확인한다 | 화면에서 실시간 좌석 상태(가능/선점/매진) 표시 여부 | 모든 공연 상세 화면에서 100% 표시 |
| 동일 좌석 중복 판매가 없다 | 좌석-예매 매핑의 유니크 제약 위반 로그 | 중복 판매 사례 0건 |

## 6. 제약

- 1인 개발 — 운영·유지보수 부담이 큰 구성(다중 서비스, 별도 인프라 운영 등)은 피한다.
  구체적인 기술 선택과 근거는 ADR 로 남긴다.

## 7. 열린 질문

- 좌석 선점(홀드) 유지 시간을 몇 분으로 할지 — 너무 길면 매진처럼 보이는 좌석이 쌓이고,
  너무 짧으면 관객이 결제를 끝내지 못한다.
- 결제 연동은 언제, 어떤 PG로 붙일지 — 이번 단계 범위 밖이지만 좌석 선점 구조가
  결제 단계와 맞물리므로 방향 정도는 미리 가늠해야 한다.
- 좌석이 없는 공연(자유석/스탠딩)은 어떻게 다룰지 — 좌석 지정이 전제인 흐름과
  수량 기반 판매를 같은 모델로 둘지 별도로 둘지.
- 주최자 승인 절차 없이 누구나 공연을 등록하게 둘지 — 이번 단계는 운영자 기능이
  범위 밖이라, 당장은 무검증 등록을 허용할지 판단이 필요하다.

### 데이터 모델에서 빠진 것 (2026-09-09 발견)

기능 문서 템플릿에 `§2-2 참조` 절을 넣고 상용 서비스(NOL)와 대조하면서 드러났다.
셋 다 관객 화면에 필요한데 `performance` 테이블에 없다.

| 빠진 것 | 왜 필요한가 | 지금 상태 |
|---|---|---|
| **가격** | 예매 서비스인데 관객이 가격을 볼 수 없다. §3·§4 는 주최자가 "가격을 설정한다"고 두 번 적어놨다 | 컬럼 없음 |
| **포스터 이미지** | 공연을 식별하는 1차 수단. 제목 텍스트만으로는 어떤 공연인지 모른다 | 컬럼 없음 |
| **공연 기간** | 여러 날 공연(뮤지컬·전시)은 시작~종료가 있다. `start_at` 하나로는 표현이 안 된다 | `start_at` 만 있음 |

가격이 가장 크다 — 관객의 "살 수 있는가" 판단에 직접 들어간다.

포스터는 소규모 주최자에게 없을 수 있다는 점이 대형 예매처와 다르다. 대체 표현을
함께 정해야 한다.
