# ADR-0029: 쓰기 가드를 없애고, API 쓰기는 JWT 역할과 소유권으로만 보호한다

- **상태**: 채택됨
- **날짜**: 2026-11-11
- **관련**: ADR-0017 (대체), ADR-0025 (입금 확인 보호 수단을 무효화), ADR-0016, ADR-0013, ADR-0026, `docs/product/features/organizer-flow.md` §3-3·§3-4·§8

---

## 맥락

ADR-0017 은 쓰기 가드(`X-Write-Key`)를 "공연 쓰기 API 에 인증·소유권 검사가 붙는 태스크"에서
제거하기로 했다. 주최자 흐름 문서(`organizer-flow.md`)가 그 태스크를 만든다 —
`performance.owner_id`, 공연 쓰기의 주최자 전용 인가, 수정·취소의 소유권 검사가 들어온다.
제거 조건이 채워지는 시점이라 가드를 어떻게 할지 다시 정해야 한다.

다시 보며 확인한 사실:

- 가드는 **경로를 가리지 않고** 모든 쓰기 메서드에 걸린다 (`WriteGuardFilter.doFilter()`).
  가입·로그인·소셜 가입 완료도 키가 있어야 통과하고, 그래서 프론트는 모든 쓰기에
  `VITE_WRITE_KEY` 를 실어 보낸다. 그 키는 번들에 들어가 누구에게나 보인다 (ADR-0016)
- **ADR-0025 가 이 가드를 재사용하기로 했다** — 입금 확인 `POST /internal/bookings/{id}/deposit-confirmed`
  를 `X-Write-Key` 로 보호한다. 그 API 는 아직 없다 (예매 기능 자체가 없다)
- 인증(ADR-0013, TASK-009~013)은 이미 있다. JWT 에 `role` 클레임이 있지만 `JwtAuthenticationFilter`
  는 권한을 비워 두고(`List.of()`) userId 만 싣는다. 역할로 막는 수단이 아직 없다
- 역할은 가입 시 정해지고 바뀌지 않는다 (`user-authentication.md` 역할 불변성)
- 소유 자원(공연)이 처음 생긴다. 남의 자원에 접근했을 때의 응답을 정한 적이 없다

## 검토한 선택지

### A. 가드를 `/internal/**` 로 좁혀 남긴다

- 장점: ADR-0025 를 건드리지 않는다. 입금 확인 API 를 만들 때 보호 수단이 이미 있다.
  `/api/**` 에서는 빠지므로 프론트 키 노출은 해소된다
- 단점: 보호할 대상(`/internal/**`)이 하나도 없는데 필터·설정·환경변수 2개·테스트 5개를
  유지한다. 키를 새로 발급해야 한다(지금 키는 이미 번들로 퍼졌다). API 보호 방식이
  "사용자 토큰"과 "공유 비밀" 둘로 갈린다

### B. 가드를 완전히 없애고, 쓰기는 JWT 역할 + 소유권으로 보호한다

- 장점: 보호 방식이 하나다 — 누가 요청했는지(JWT)와 그 사람이 무엇을 할 수 있는지(역할·소유권).
  쓰지 않는 코드와 배포 환경변수(`WRITE_GUARD_ENABLED`·`WRITE_API_KEY`·`VITE_WRITE_KEY`)가 사라진다.
  가입·로그인이 키 없이 동작한다
- 단점: ADR-0025 의 보호 수단이 사라진다. 입금 확인 API 를 만들 때 운영자 계정·역할을
  먼저 마련해야 한다 — 그 기능이 그만큼 커진다

### C. 이번에는 가드를 그대로 두고 JWT·소유권만 더한다

- 장점: 변경이 가장 작다. 방어가 이중이 된다
- 단점: 이중 방어의 한쪽(키)은 번들에 공개돼 방어가 아니다. ADR-0017 이 정한 제거 조건이
  채워졌는데 지우지 않으면 임시 방어가 영구화된다 — ADR-0017 이 "감수하는 것"으로 적은 바로 그 위험이다

## 결정

**B — 쓰기 가드를 모두 지운다. `/api/**` 의 쓰기는 `SecurityConfig` 에서 JWT `role` 클레임으로
만든 `ROLE_*` 권한으로 막고, 자원 단위 권한은 서비스가 소유권으로 판정한다.**

1. **역할** — `JwtAuthenticationFilter` 가 `role` 클레임을 `ROLE_<role>` 권한으로 싣는다.
   경로별 `hasRole` 은 `SecurityConfig` 한 곳에 둔다 (ADR-0013 단일 지점). 요청마다 DB 에서
   역할을 다시 읽지 않는다 — 역할은 바뀌지 않는다
2. **응답** — 토큰 없음·만료는 401, 역할이 맞지 않으면 403 `FORBIDDEN_ROLE`
3. **소유권** — 남의 자원·소유자 없는 자원·없는 자원은 **모두 같은 404** 로 응답한다.
   403 으로 구분하지 않는다 — 남의 자원이 존재한다는 사실을 드러내지 않는다.
   공연에 처음 적용하고, 이후 소유 자원(예매 등)에도 같은 규칙을 쓴다
4. **입금 확인 내부 API (ADR-0025)** — 공유 비밀 키 대신 **운영자(ADMIN) 역할 + JWT** 로
   보호하는 방향으로 간다. 운영자 계정을 어떻게 만드는지(가입 경로에서 막고 시드·운영 SQL 로
   만드는지 등)는 그 API 를 만드는 기능에서 정한다. **보호 수단이 정해지기 전에는 그 API 를 열지 않는다**

### 이유

A 를 고르지 않은 것은 **보호할 대상이 없는 장치를 유지하기 때문**이다. 입금 확인 API 는 예매
기능 뒤에야 생기고, 그때까지 필터·환경변수·테스트를 끌고 가야 한다. 게다가 그때 가드를 쓰려면
번들로 퍼진 키를 교체해야 해서 "이미 있는 수단"이라는 장점도 반쯤 사라진다.

더 근본적으로는 **보호 방식을 하나로 통일하려는 것**이다. 인증이 생긴 뒤에는 "누가 이 일을 할 수
있나"를 사용자 단위로 답할 수 있다. 공유 비밀 키는 누가 호출했는지 남기지 못하고, 키가 새면
모두가 그 권한을 갖는다. 입금 확인처럼 돈과 관련된 동작일수록 사용자 단위 기록이 필요하다.

C 는 ADR-0017 의 결정을 지키지 않는 선택이다. 그때 가드를 남긴 이유는 "대신할 검사가 먼저
있어야 한다"였고, 이제 그 검사가 생긴다.

ADR-0025 의 판단(입금 확인은 운영자 화면 없이 보호된 내부 API 로)은 그대로 둔다. 바뀌는 것은
보호 **수단**뿐이다. ADR-0025 를 쓸 때는 사용자 인증이 막 생겨 역할 기반 보호가 선택지가 아니었고,
이미 있던 키를 재사용하는 것이 가장 쌌다 — 그때는 맞았고, 조건이 바뀌었다.

## 결과

- 좋아지는 것:
  - API 보호 방식이 하나(JWT + 역할 + 소유권)다. 새 쓰기 API 는 `SecurityConfig` 에 경로 규칙 하나,
    서비스에 소유권 검사 하나로 끝난다
  - 프론트 번들에서 비밀이 사라진다. 가입·로그인이 키 없이 동작한다
  - 배포 환경변수 3개가 사라진다
- 감수하는 것:
  - **입금 확인 API 를 만드는 기능이 커진다.** 운영자 역할(`UserRole.ADMIN`)과 그 계정을 만드는
    경로가 먼저 있어야 한다. 지금 `UserRole` 은 `AUDIENCE`·`ORGANIZER` 둘뿐이고 가입 화면이 역할을
    고르게 하므로, ADMIN 을 가입으로 고를 수 없게 막는 일도 따라온다
  - 역할을 토큰 클레임으로 믿으므로, **역할을 바꾸는 기능이 생기면** 이미 발급된 토큰이 만료될
    때까지 옛 역할로 동작한다. 그때는 DB 재조회나 토큰 무효화를 다시 정해야 한다
  - 소유권 위반을 404 로 숨기므로 주최자가 "왜 안 보이지"를 구분할 수 없다 — 남의 공연 링크를 연
    주최자는 없는 공연과 같은 안내를 본다
  - 기존 공연 쓰기 테스트 전부에 토큰 픽스처가 필요해진다 (organizer-flow Task A)
- 되돌리려면: 이 ADR 을 대체하는 새 ADR 을 쓴다. 가드 코드는 git 이력(`WriteGuardFilter.java`,
  `WriteGuardConfig.java`)에서 되살릴 수 있다. 키를 새로 발급하고 백엔드·프론트 환경변수를 다시
  넣어야 하며, 프론트 `request()` 의 키 주입을 복구해야 한다 — 반나절 규모

## 검사 가능한 제약

- **AUTH-001** — `X-Write-Key`·`WRITE_API_KEY`·`VITE_WRITE_KEY` 를 백엔드 main·프론트 src 에 쓰지 않는다.
  도입 시점에는 위반이 있어 `warn`, 백엔드(Task A, TASK-022)와 프론트(Task C, TASK-024)에서
  모두 지운 뒤 `error` 로 올린다 (`promote_after: TASK-024`)
- 소유권 위반의 404 통일은 코드 패턴으로 검사할 수 없다 — 각 태스크의 시나리오(남의 자원·소유자 없음·없는 자원 3종이 같은 응답)로 확인한다
