# ADR-0019: 문자열 입력 검증은 서버가 정본이고, 제어문자는 거부하며 이메일 외에는 정규화하지 않는다

- **상태**: 채택됨
- **날짜**: 2026-10-22
- **관련**: ADR-0006(테스트 DB), TASK-009 (RC-1), TASK-010 (OOS-1, SC-07~09), `.claude/skills/wf-scenario/references/coverage-policy.md`

---

## 맥락

문자열 필드는 저장되거나 저장값과 비교된다. TASK-009 는 PostgreSQL 이 무손실로 저장하지 못하는
문자열(NUL, 짝 없는 서로게이트)이 `?` 로 치환돼 409 오보·다른 값과의 충돌·비밀번호 매칭(200)이
되는 결함으로 Phase 4 에서 네 번 FAIL 했다. 서버는 이를 필드마다 막는 대신 API 경계에서 400 으로
거부하도록 고쳤다.

TASK-010 은 같은 입력을 폼에서 받는다. 그때 한 차이가 남아 있다는 것을 알게 됐다 — 서버는
이메일을 Java `trim()`(U+0000~U+0020 전부 제거)으로 정규화한 뒤 검증하고, 클라이언트는 JS
`trim()`(NUL 은 그대로)으로 판단한다. 앞에 NUL 이 붙은 이메일은 서버에서 NUL 이 지워진 주소로
가입이 201 로 성공하고 저장된다(TASK-010 OOS-1). 입력이 "거부"가 아니라 "조용한 변형"으로 처리되는
경로가 남아 있다는 뜻이다. TASK-011~013 이 입력 엔드포인트와 폼을 더 늘린다.

## 검토한 선택지

### A. 서버가 정본 — 제어문자·짝 없는 서로게이트는 거부, 이메일은 앞뒤 공백만 제거

- 장점: 판정이 한 곳(서버)이라 폼이 늘어도 같은 규칙이다. 조용한 변형이 없다(이메일의 앞뒤 일반
  공백 제거만 유일한 변형). 클라이언트는 그대로 보내므로 TASK-010 시나리오 SC-08·09 와 일치한다
- 단점: 서버 `trim()` 을 일반 공백만 지우도록 고치는 후속 작업이 필요하다. 사용자는 거부 사유를
  필드 단위로 못 본다(서버 400 은 일반 실패 문구)

### B. 클라이언트도 같은 규칙으로 사전 거부

- 장점: 거부 사유를 입력 즉시 필드 아래에 보여줄 수 있다
- 단점: 같은 규칙이 두 곳에 있어 어긋나면 한쪽이 거짓 통과·거짓 거부를 낸다. 서버가 어차피 최종
  판단이라 우회 입력은 서버에서 막아야 한다. SC-08·09(변환 없이 전송)가 바뀐다

### C. 제어문자를 조용히 제거해 정규화한다

- 장점: 사용자 입장에서 오류가 나지 않는다
- 단점: 비밀번호·이름이 입력과 다른 값으로 저장되고, 이메일은 서로 다른 입력이 같은 주소가 돼
  충돌이나 계정 혼동의 통로가 된다. 사용자가 입력한 값과 저장값이 달라지는 것을 보이지 않게 만든다

## 결정

A 를 쓴다.

1. 모든 문자열 입력 필드에서 NUL 등 제어문자와 짝 없는 서로게이트는 서버가 **원문에 대해** 400 으로
   거부한다. 검증은 `trim()` 보다 먼저, 원문에 한다
2. 이메일만 앞뒤 일반 공백(U+0020)을 제거해 검증·저장한다. 그 밖의 필드(비밀번호·이름 등)는 변환 없이
   그대로 검증·저장·비교한다
3. 클라이언트는 이메일 앞뒤 공백 제거 외에는 입력을 변환하거나 거부하지 않고 그대로 보낸다. 길이·필수
   검증은 UX 용 미러링일 뿐 판정은 서버가 한다(서버 `@Size` 와 같게 UTF-16 코드 유닛 수)

### 이유

저장·비교되는 값은 서버가 알고 있는 한 가지 규칙으로만 판정돼야 한다. B 는 규칙을 둘로 나눠
어긋남의 위험을 만들고, C 는 문제를 "거부"에서 "보이지 않는 변형"으로 바꿔 더 고치기 어렵게 만든다.
A 는 이미 TASK-009 가 구현한 거부 규칙에 이메일 trim 의 범위 하나만 좁히는 것이다.

## 결과

- 좋아지는 것: 폼·엔드포인트가 늘어도 문자열 입력의 규칙이 하나다. coverage-policy 의 "문자열 필드
  전수" 행이 이 정책을 검증한다
- 감수하는 것: 현재 서버는 아직 이 정책과 한 곳이 다르다 — `email.trim()`(U+0000~U+0020 제거)이
  거부보다 먼저 일어나 앞 NUL 이메일이 통과한다. 후속 태스크로 고친다. 사용자는 거부 사유를 필드
  단위로 보지 못한다
- 되돌리려면: 클라이언트 사전 거부(B)로 바꾸려면 SC-08·09 를 고치고 서버 규칙을 문서로 한 번 더 복제한다
