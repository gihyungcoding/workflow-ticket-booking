# ADR-0016: 프론트와 백엔드를 따로 배포하고, 교차 출처 직접 호출과 임시 쓰기 가드를 둔다

- **상태**: 채택됨 (쓰기 가드 제거 시점은 ADR-0017 로 대체됨)
- **날짜**: 2026-10-14
- **관련**: ADR-0003, ADR-0006, ADR-0013, ADR-0015, `docs/release/README.md`, `TASK-014`, `TASK-015`

---

## 맥락

첫 배포를 연습으로 해보려 한다. 서비스 운영이 목적이 아니라 **배포 절차에서 겪는 마찰을
기록하는 것**이 목적이고, 조건은 둘이다.

- 과금이 생기면 안 된다 — 카드를 등록하지 않아도 되는 무료 인프라만 쓴다
- 프론트엔드를 백엔드에 포함시키지 않고 **따로** 배포한다 (사용자 결정)

지금까지 이 문제는 미뤄져 있었다. `frontend/vite.config.ts` 의 주석이 *"배포 환경의
CORS/리버스 프록시 전략은 별도로 정한다"* 로 남아 있고, 프론트 코드는 `fetch('/api/...')`
상대 경로만 쓴다. 개발 환경에서는 Vite 프록시가 그것을 `localhost:8080` 으로 넘긴다.

두 가지가 더 걸린다.

1. **인증이 아직 없다.** 배포하면 공개 주소가 생기고, 누구나 공연을 등록·수정·취소할 수
   있다. 인증(`TASK-009`)이 들어오기 전까지 임시 방어가 필요하다.
2. **인증 설계가 이미 있다.** ADR-0013(Spring Security)과 ADR-0015(accessToken 을
   localStorage 에, `Authorization` 헤더로 전달)가 채택돼 있어서, 이번 결정이 그것과
   충돌하지 않아야 한다.

## 검토한 선택지

### A. 프론트를 백엔드 이미지에 포함 (단일 서비스)

- 장점: 같은 출처라 CORS 가 없다. 무료 서비스 하나로 끝난다. 프론트 코드 변경이 없다
- 단점: 프론트만 바꿔도 백엔드를 다시 배포한다. 사용자가 원하지 않는 구성이다

### B. 프론트 분리 + 정적 호스트의 프록시로 `/api` 전달

- 장점: 브라우저에는 같은 출처로 보인다. 프론트 코드 변경이 없다
- 단점: Cloudflare Pages 의 `_redirects` 는 외부 도메인 프록시를 지원하지 않아 별도
  Function 이 필요하다. 부품이 하나 늘고, 무료 한도 조건을 확인하지 못했다. 백엔드의
  1분짜리 콜드스타트가 프록시 계층의 타임아웃과 겹친다

### C. 프론트 분리 + 브라우저가 백엔드를 직접 호출 (CORS)

- 장점: 부품이 늘지 않는다. 콜드스타트 대기를 브라우저가 직접 견딘다. ADR-0015 의
  `Authorization` 헤더 방식이 교차 출처에서 그대로 동작한다 (쿠키를 쓰지 않는다)
- 단점: 백엔드에 CORS 설정이 필요하다. API 주소가 빌드 시점에 프론트 번들에 박힌다.
  쓰기 요청마다 사전 요청(`OPTIONS`)이 한 번 더 간다

## 결정

**C.** 프론트는 Cloudflare Pages, 백엔드는 Render 무료 웹 서비스(Docker), DB 는 Neon
무료 PostgreSQL 에 둔다. 프론트는 `VITE_API_BASE_URL` 로 백엔드 주소를 받아 직접
호출하고, 백엔드는 허용 출처만 CORS 로 통과시킨다.

배포 기간 동안 **쓰기 가드**를 둔다. `POST`·`PUT`·`PATCH`·`DELETE` 요청에
`X-Write-Key` 헤더가 맞아야 통과하고, 조회는 열어둔다. `TASK-009`(인증)가 들어오면 제거한다.

### 세부

| 항목 | 결정 |
|---|---|
| CORS 허용 출처 | `CORS_ALLOWED_ORIGINS` 환경변수(쉼표 구분). 와일드카드 금지 |
| CORS 허용 헤더 | `Content-Type`, `Authorization`, `X-Write-Key`. 자격증명(쿠키)은 허용하지 않는다 |
| CORS 구현 위치 | **서블릿 필터 수준**(`CorsFilter` 빈, 최우선 순서). Spring Security 가 들어와도 사전 요청이 보안 필터에서 거부되지 않게 한다 |
| 쓰기 가드 활성화 | `WRITE_GUARD_ENABLED=true` 일 때만. 켜졌는데 `WRITE_API_KEY` 가 비어 있으면 **기동에 실패**한다 (열린 채로 뜨지 않는다) |
| 쓰기 가드 통과 | `GET`·`HEAD`·`OPTIONS` 는 키 없이 통과 (사전 요청은 커스텀 헤더를 싣지 않는다) |
| 프론트 키 | `VITE_WRITE_KEY` 를 빌드 시 주입한다. 쓰기 요청에만 `X-Write-Key` 를 붙인다 |
| 서버 포트 | `PORT` 환경변수를 `server.port` 로 받는다 (Render 가 주입) |
| DB 접속 | Spring 표준 환경변수(`SPRING_DATASOURCE_URL` 등). 설정 파일에 접속 정보를 두지 않는다 |

### 이유

A 는 사용자가 배제했다. B 를 고르지 않은 이유는 **얻는 것이 프론트 코드를 안 고치는 것
하나뿐인데 비용이 크기** 때문이다 — 외부 프록시를 위한 Function 이 하나 더 필요하고,
첫 요청이 콜드스타트와 프록시 타임아웃의 조합이 된다. 연습의 목적이 배포 마찰을 보는
것이므로, 변수가 적은 C 가 마찰의 원인을 가리기 쉽다.

CORS 를 서블릿 필터 수준에 두는 이유는 인증 때문이다. `WebMvcConfigurer` 기반 CORS 는
Spring Security 필터 체인이 먼저 요청을 처리하면 사전 요청이 401 로 끝난다. 지금은
Security 가 없어서 드러나지 않지만, `TASK-009` 이후에 깨질 수 있는 결정을 지금 피한다.

쓰기 가드를 `WRITE_GUARD_ENABLED` 로 켜고 끄게 한 이유는 로컬 개발과 기존 테스트가 키
없이 그대로 돌아야 하기 때문이다. 대신 **켜졌는데 키가 없으면 기동 실패**로 두었다.
키 검사를 하지 않는 채로 배포되는 사고를 가장 싸게 막는 방법이다.

## 결과

- 좋아지는 것: 프론트와 백엔드를 독립적으로 배포한다. 배포 구조가 코드와 문서에 한 곳에
  기록된다. 인증이 들어와도 CORS 설정을 다시 뜯지 않는다
- 감수하는 것:
  - **쓰기 가드의 키는 프론트 번들에 들어가므로 누구에게나 보인다.** 이것은 보안이
    아니라 "주소를 우연히 알게 된 요청"과 스크립트성 오남용을 거르는 수준이다.
    연습용 데이터라는 전제에서만 정당하다
  - 프론트와 백엔드가 따로 배포되므로 **API 가 바뀔 때 배포 순서**가 생긴다. 지금
    워크플로우에는 이에 대한 규칙이 없다
  - 백엔드 주소를 바꾸면 프론트를 다시 빌드해야 한다
- 되돌리려면: 프론트를 백엔드 이미지에 포함(A)하고 `VITE_API_BASE_URL` 을 비운다.
  쓰기 가드는 `WRITE_GUARD_ENABLED` 를 끄면 된다

### 첫 배포에서 확인할 가설 (확인되지 않음)

아래는 공식 문서나 실행으로 확인한 것이 **아니다.** 첫 배포에서 맞는지 본다.

1. Render 가 콜드스타트 중 브라우저에 보여주는 로딩 페이지 응답에는 CORS 헤더가 없어서,
   첫 요청이 서버 장애가 아니라 **CORS 오류처럼** 보일 수 있다. 맞다면 프론트에 깨우기
   요청과 재시도가 필요하다
2. Render 무료 인스턴스의 메모리(블로그 기준 512MB)에서 Spring Boot 가 기동하는지.
   안 되면 JVM 옵션을 줄이거나 호스트를 바꿔야 한다
3. Cloudflare Pages 가입 과정에서 카드 입력을 요구하지 않는지 (공식 한도 문서에 언급이
   없었다). 요구하면 거기서 멈추고 다른 정적 호스트로 바꾼다

- `DEPLOY-002` — CORS 허용 출처에 와일드카드를 쓰지 않는다 (error)
