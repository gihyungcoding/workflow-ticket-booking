# ADR-0028: 사용자가 입력하는 URL 은 https 이고, 권한 부분을 직접 나눠 하위 요소마다 판정한다

- **상태**: 채택됨
- **날짜**: 2026-11-11
- **관련**: ADR-0019, ADR-0027, TASK-019 (VERIFY RC-1, 회고 ADR 후보 2), `docs/product/features/booking-ux-02-browse.md` §3-3,
  `backend/.../service/PerformanceService.java#validatePosterUrl`

---

## 맥락

TASK-019 에서 공연 등록에 포스터 URL(`posterUrl`)을 받기 시작했다. 우리는 이미지를 올려 두지 않고, 주최자가 이미
가진 이미지의 주소를 받는다. 화면(홈 카드·머리글·상세)은 이 주소를 `<img src>` 로 그대로 쓴다.

요구사항은 「https 절대 URL, 500자 이하」 한 줄이었다. 이 한 줄을 판정하는 방법이 정해지지 않은 채 구현까지 갔다.

- 첫 구현은 `java.net.URI` 의 `getHost()` 가 null 이면 거부했다. `java.net.URI` 는 밑줄이나 비 ASCII 글자가 든 호스트를
  등록 기반 권한으로 분류하고 `getHost()` 에 null 을 준다. 그래서 정상적인 CDN 주소(`cdn_1.example.com`)가 거부됐다
- 직접 분해로 고치자, 리뷰할 때마다 하위 요소의 변종이 하나씩 새로 나왔다. 호스트에 `:` 가 여럿인 주소, 포트가 전각
  숫자인 주소, userinfo 안에 `@` 가 또 있는 주소가 그랬다. 시나리오 롤백 2회, Phase 4 FAIL 1회였다

흐름 4 이후에도 사용자 입력 URL 이 더 생긴다(공연장 지도 링크, 주최자 홈페이지). 같은 질문을 다시 풀지 않으려면
규칙이 한 곳에 있어야 한다.

## 검토한 선택지

### A. `java.net.URI` 의 판정을 그대로 쓴다 (`getScheme`·`getHost`)

- 장점: 표준 라이브러리 한 번 호출. 직접 짤 코드가 없다
- 단점: RFC 2396 시절 문법이라 밑줄·비 ASCII 호스트를 「호스트 없음」으로 본다. 반대로 빈 userinfo(`https://@a.com`)나
  빈 포트(`a.com:`)는 통과시킨다. 우리가 원하는 판정과 양쪽으로 어긋난다

### B. 정규식 하나로 URL 전체를 판정한다

- 장점: 규칙이 한 줄에 보인다
- 단점: URL 전체 문법을 정규식으로 옮기면 읽을 수 없게 길어지고, 이번에 나온 변종(IPv6 리터럴, 퍼센트 인코딩)마다
  예외가 붙는다. 경로·쿼리의 파싱 오류까지 직접 다뤄야 한다

### C. `java.net.URI` 로 파싱만 하고, 권한 부분은 직접 나눠 하위 요소마다 판정한다

- 장점: 경로·쿼리·인코딩의 문법 오류는 `URI` 가 거부한다. 우리가 직접 정하는 것은 권한 부분(userinfo·호스트·포트)뿐이고,
  하위 요소마다 받을지 거부할지가 이 ADR 과 시나리오 규약 표에 적힌다
- 단점: `hasValidAuthority` 를 직접 유지한다. 판정을 다시 구현한 코드라, 새 표기 변종이 나오면 이 함수와 표를 함께 고쳐야 한다

### D. 허용한 호스트(CDN 목록)만 받는다

- 장점: 판정이 가장 단순하고, 이상한 주소가 화면에 그려질 일이 없다
- 단점: 우리에게는 운영하는 CDN 이 없고, 주최자마다 이미지를 두는 곳이 다르다. 목록을 운영할 사람도 없다(1인 개발).
  업로드 기능을 만들 때 다시 볼 선택지다

## 결정

**C — 사용자가 입력하는 URL 은 `java.net.URI` 로 파싱되고 스킴이 `https`(대소문자 무관)여야 한다. 권한 부분은 직접 나눠
아래 규칙으로 판정한다.** 판정에 통과한 값은 바꾸지 않고 받은 그대로 저장한다(ADR-0019).

| 하위 요소 | 받는다 | 거부한다 |
|---|---|---|
| 스킴 | `https`, `HTTPS` | 그 밖의 모든 스킴, 스킴 없음, 상대 경로 |
| userinfo | 있으면 비어 있지 않은 값 | 빈 값(`https://@host`), 안에 `@` 가 또 있는 값 |
| 호스트 | 밑줄·비 ASCII 글자, IPv6 리터럴(`[…]`, `URI` 가 해석한 경우) | 빈 값, `%XX`, IPv6 가 아닌데 `:` 가 남은 값 |
| 포트 | ASCII 숫자 `0`~`9` | 빈 값(`host:`), 그 밖의 글자(아랍-인도·전각 숫자 포함) |
| 문자열 전체 | 500 UTF-16 코드 유닛 이하 | 제어문자, 짝 없는 서로게이트, 앞뒤 공백(→ `URI` 파싱 실패) |

포트 범위(0~65535)는 검사하지 않는다. 브라우저가 연결에 실패할 뿐 화면이 깨지지 않는다.

### 이유

A 는 판정 기준이 우리 의도와 양쪽으로 어긋나고, 그것이 TASK-019 RC-1 이었다. B 는 같은 일을 읽을 수 없는 형태로
한다. D 는 운영 조건이 맞지 않는다. C 는 직접 정해야 하는 부분(권한)만 직접 정하고, 나머지 문법은 표준 파서에 맡긴다.
하위 요소를 표로 정해 두면, 시나리오가 칸으로 펼칠 수 있다(`coverage_matrix.py` 의 `url` kind).

## 결과

- 좋아지는 것:
  - URL 입력이 새로 생겨도 같은 함수와 같은 표를 쓴다
  - 2a 가 `url` kind 로 하위 요소 칸을 처음부터 덮는다
- 감수하는 것:
  - 판정을 다시 구현했으므로, 표에 없는 표기가 나오면 결함이 될 수 있다. TASK-019 에서 확인하지 않은 것은 경로·userinfo
    의 `%XX`(받는다)와 `#frag`(받는다)다
  - 함수가 지금은 `PerformanceService` 의 private 메서드다. 두 번째 URL 입력이 생기면 공용 검증기로 옮겨야 한다
  - 포트 범위를 검사하지 않는다
- 되돌리려면: A 로 돌아가려면 `hasValidAuthority` 를 `uri.getHost() != null` 로 바꾸면 된다. 그러면 TASK-019 의
  SC-05 p·q·u~y 와 SC-06 j·k 가 실패하므로, 시나리오와 테스트를 함께 고쳐야 한다

## 검사 가능한 제약

- 없음 — 「URL 입력은 이 함수를 쓴다」는 어느 문자열이 URL 인지 정적으로 가릴 수 없다. 2a 의 `url` kind 가 필드마다
  확인하게 한다(TASK-019 회고 반영, `scripts/coverage_matrix.py`)
