# ADR-0031: 계정 메일은 MailGateway 인터페이스 뒤에서 SMTP 로 보낸다

- **상태**: 채택됨
- **날짜**: 2026-11-12
- **관련**: ADR-0023 (대기열 저장소를 인터페이스 뒤에 둔 방식), ADR-0020, `docs/product/features/email-verification-password-reset.md` §3-3·§3-5·§8

---

## 맥락

이메일 인증과 비밀번호 찾기는 이메일로 일회용 링크를 보내야 한다. 지금 백엔드에는 메일을 보낼 코드도 의존성도 없고,
`architecture.md` §5 외부 의존에도 메일 서비스가 없다. 기존 인증 문서가 두 기능을 범위 밖에 둔 이유가 이것이었다.

- 새 외부 의존이 생긴다. 메일 서비스가 느리거나 죽어도 가입·로그인은 동작해야 한다
- 1인 개발이라 운영 부담이 큰 구성은 피한다(`product.md` §6)
- 비밀번호 찾기 응답은 계정이 있든 없든 같아야 하는데, 발송이 응답에 묶이면 응답 내용·시간이 계정 존재와 메일 서비스
  상태를 드러낸다
- 테스트와 개발에서는 실제로 메일을 보내면 안 되고, 보낼 메일의 받는 사람·링크는 확인할 수 있어야 한다

## 검토한 선택지

### A. 인터페이스(`MailGateway`) 뒤에 SMTP — 개발·테스트는 로그 구현 (채택)

- 장점: 메일 서비스(SES·Resend·Gmail SMTP 등)를 배포 설정으로 바꾼다. 코드는 한 인터페이스만 안다. 테스트는 보낸 메일을
  모아 단언한다. 대기열 저장소(`QueueStore`, ADR-0023)와 같은 방식이라 익숙하다
- 단점: 인터페이스와 구현 둘, 설정 값(`MAIL_TRANSPORT`·SMTP 접속 정보)이 늘어난다

### B. 특정 서비스의 HTTP API 를 직접 호출

- 장점: 구현이 짧다. 서비스 대시보드(발송 기록·반송)를 바로 쓴다
- 단점: 코드가 그 서비스에 묶인다. 서비스를 바꾸려면 호출 코드를 고쳐야 하고, 테스트가 그 서비스의 응답 형태에 기댄다

### C. 메일 없이 다른 수단으로 소유를 확인(문자·소셜 재인증)

- 장점: 메일 인프라가 필요 없다
- 단점: 비밀번호 찾기·이메일 인증의 표준 경로가 아니고 문자는 비용·본인 확인 계약이 따른다. 이번 요구(이메일 소유 확인)를
  충족하지 못한다

## 결정

A. `service/MailGateway` 인터페이스를 두고 운영은 SMTP(Spring Mail), 개발·테스트는 로그 구현을 쓴다. 구현은
`MAIL_TRANSPORT`(`smtp` | `log`)로 고르고, 운영에서 비어 있으면 기동이 실패한다. 메일은 요청 처리와 분리해 커밋 뒤 비동기로
보내고 실패는 로그만 남긴다.

### 이유

- B 는 지금은 가장 짧지만 서비스를 바꾸는 날 호출 코드와 테스트가 함께 바뀐다. 발송 서비스는 아직 정하지 않은 열린 질문이라
  (기능 문서 §7) 코드가 그 선택에 묶이지 않는 편이 맞다
- 발송을 응답과 분리하면 응답 본문·시간이 계정 존재와 SMTP 상태를 드러내지 않는다. 비밀번호 찾기와 재발송이 계정 유무와
  무관하게 같은 응답을 줄 수 있는 전제다
- 비어 있을 때 기동을 실패시키는 것은 「운영에서 메일이 조용히 안 나가는」 사고를 막는다. `log` 가 기본값이면 설정을
  빠뜨려도 서비스가 정상으로 보인다

## 결과

- 좋아지는 것:
  - 발송 서비스를 코드 변경 없이 바꾼다
  - 가입·로그인은 메일 서비스 장애와 무관하게 동작한다
  - 테스트가 실제 메일 없이 받는 사람·링크를 단언한다
- 감수하는 것:
  - 비동기라 응답으로는 메일이 갔는지 알 수 없다. SMTP 장애를 사용자가 모르고, 운영이 로그·알림으로 봐야 한다
  - 발송 실패의 재시도·발신 기록(outbox)은 없다. 필요해지면 `MailGateway` 뒤에서 추가한다(기능 문서 §7)
  - 발신 도메인의 SPF·DKIM 설정이 운영 작업으로 남는다
- 되돌리려면: `SmtpMailGateway` 를 다른 구현으로 바꾼다. 인터페이스 위쪽(서비스)은 바뀌지 않는다

## 검사 가능한 제약

- 없음 — 「서비스는 `JavaMailSender` 를 직접 쓰지 않는다」를 코드 패턴으로 검사할 수 있으나 구현이 한 곳뿐이라 지금은 두지
  않는다. 서비스 계층 의존 규칙(ARCH-002)이 이미 HTTP 관심사를 막는다
