# ADR-0004: 좌석 선점 동시성 제어는 DB 트랜잭션(유니크 제약 + 조건부 UPSERT)만으로 처리한다

- **상태**: 채택됨
- **날짜**: 2026-09-02
- **관련**: `docs/architecture/architecture.md` §4, §7, ADR-0003

---

## 맥락

공연 오픈 시 동일 좌석에 대한 동시 요청이 몰리면 같은 좌석이 두 번 팔리는 문제가
생긴다(`docs/product/product.md` §2). 이를 막는 정합성 보장 방식을 정해야 한다.
아직 실측 트래픽이 없으므로 규모를 가정해야 한다: **좌석 100~500석, 동시 접속
100명 이하, 오픈 순간 10배 스파이크** (근거 없음 — 실측 전까지의 작업 가정).

## 검토한 선택지

### A. 진입 제한(대기열) + 인메모리 선점 계층(Redis 등) + 비동기 저장

- 장점: 대규모 동시 접속에서도 DB 부하를 분산시키고 응답 지연을 줄일 수 있다.
- 단점: 이 가정 규모(동시 접속 100명 이하)에서는 검증할 트래픽 자체가 없어
  올바르게 동작하는지 확인할 방법이 없다. 추가 인프라(Redis, 큐)를 1인 개발이
  운영해야 한다. 지금 도입하면 복잡도만 늘고 이득은 실현되지 않는다.

### B. PostgreSQL 트랜잭션만으로 처리 (유니크 제약 + 조건부 UPSERT)

- 장점: 추가 인프라가 필요 없다. 좌석-예매 매핑 테이블에 좌석당 활성 선점 1건이라는
  유니크 제약을 걸고, 조건부 UPSERT(이미 선점된 좌석이면 실패)로 동시 요청 중 하나만
  성공시킨다. 정합성이 DB 제약으로 보장되므로 애플리케이션 로직에 버그가 있어도
  깨지지 않는다.
- 단점: 오픈 순간 요청이 가정을 크게 초과하면(§재검토 트리거) DB 커넥션 풀이
  포화되거나 응답 지연이 커질 수 있다.

## 결정

**B — PostgreSQL 트랜잭션(유니크 제약 + 조건부 UPSERT)만으로 좌석 선점 동시성을
제어한다.**

### 이유

A는 검증할 수 없는 복잡도다 — 가정한 규모에서는 인메모리 계층이 실제로 무엇을
개선하는지 관측할 트래픽이 없다. B는 정합성을 DB 제약이라는 가장 신뢰할 수 있는
지점에서 보장하면서, 1인 개발이 추가로 운영할 인프라가 없다. 규모 가정이 틀렸다는
것이 관측되면(아래 재검토 트리거) 그때 A의 요소를 순서대로 도입한다.

## 결과

- 좋아지는 것: 인프라가 PostgreSQL 하나로 유지된다. 정합성 보장 지점이 하나(DB 제약)
  라 추론하기 쉽다.
- 감수하는 것: 트래픽이 가정을 넘으면 선점 API 응답 지연이나 DB 부하 문제가 생길 수
  있다. 그 시점까지는 의도적으로 감수한다.
- 되돌리려면: 재검토 트리거가 관측되면 진입 제한(대기열) → 메모리 선점 계층 →
  비동기 저장 순서로 도입한다. DB 트랜잭션 계층은 그대로 두고 앞단에 계층을
  추가하는 방식이라 기존 정합성 보장은 유지된다.

### 재검토 트리거

아래 중 하나라도 관측되면 이 결정을 다시 본다.

- 동시 접속 1,000명 초과
- 오픈 순간 DB 커넥션 풀 포화
- 좌석 선점 API p99 응답 시간 > 1초

## 검사 가능한 제약

- 없음 (동시성 보장은 DB 스키마 제약(유니크 인덱스)으로 강제되며, 이는
  애플리케이션 코드가 아니라 마이그레이션에 속하므로 `constraints.yaml`
  대상이 아니다)
