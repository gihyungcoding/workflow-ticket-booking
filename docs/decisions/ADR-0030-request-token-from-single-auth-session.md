# ADR-0030: 프론트 요청 토큰은 앱에 하나뿐인 AuthProvider 의 세션에서 읽는다

- **상태**: 채택됨
- **날짜**: 2026-11-12
- **관련**: ADR-0015 (토큰은 localStorage), ADR-0018 (늦은 응답), ADR-0029 (쓰기는 JWT 역할·소유권), TASK-024, `docs/product/features/organizer-flow.md` §3-7

---

## 맥락

ADR-0029 로 쓰기 가드가 사라졌다. 이제 프론트의 쓰기 요청은 로그인 토큰(`Authorization: Bearer`)이 있어야
통과한다. TASK-024 는 그 토큰을 `request()`(`frontend/src/api/http.ts`)에서 싣는다.

토큰이 있는 곳은 두 군데다.

- **저장소(`localStorage`, ADR-0015)** — 새로고침 뒤 복원에 쓴다. 쓰기·지우기가 실패할 수 있다(사생활 보호
  모드, 쿼터 초과). 같은 브라우저의 다른 탭과 공유된다
- **화면의 로그인 세션(`AuthProvider`)** — 가드(`RequireOrganizer`)와 전역 헤더가 이것을 본다.
  저장에 실패해도 "이번 방문 동안은 메모리로 로그인을 유지"한다(`AuthContext.writeToken`)

처음 구현은 `request()` 가 저장소만 읽었다. Phase 4 1회차 리뷰에서 두 정본이 갈라지는 결함(RC-1)이 나왔다.
저장에 실패하면 가드는 주최자로 통과시키는데 쓰기 요청엔 토큰이 없어 401 → 로그아웃이 반복됐다. 다른 탭이
저장소를 다른 계정 토큰으로 바꾸면, 이 탭 화면은 주최자인데 요청은 관객 명의로 나갈 수 있었다.

요청을 세션에서 읽도록 고치자 마지막 변종이 남았다. `request()` 는 React 트리 밖의 모듈 함수라 **어느
`AuthProvider` 의 요청인지 모른다.** `AuthProvider` 가 둘 이상 동시에 올라와 있으면 나중에 올라온 쪽의 세션이
요청에 실리고, 먼저 올라온 쪽 화면과 갈라진다. 지금 앱은 `main.tsx` 에 `AuthProvider` 를 하나만 둔다.

## 검토한 선택지

### A. 세션을 모듈 하나에 두고, 앱에 AuthProvider 는 하나라고 정한다

`http.ts` 에 세션 토큰을 두고 `AuthProvider` 가 로그인·로그아웃·복원 때 알린다. 세션이 정해지기 전이나
`AuthProvider` 가 내려간 뒤에는 저장소를 읽는다.

- 장점: `request()` 의 호출부 10곳(auth.ts 5·performances.ts 5)을 바꾸지 않는다. 화면과 요청이 같은 값을 본다
- 단점: `AuthProvider` 가 둘이면 맞지 않는다. 이 전제를 코드가 강제하지 않는다

### B. 토큰을 호출부가 넘긴다 — `request(path, init, token)` 또는 `useApi()` 훅

요청을 보내는 화면이 자기 `AuthProvider` 의 토큰을 넘긴다.

- 장점: Provider 가 여럿이어도 요청이 자기 화면의 토큰을 쓴다. 모듈 전역이 없다
- 단점: `api/*.ts` 함수 전부와 그 호출부를 바꾼다. 복원(`fetchMe`)처럼 아직 세션이 없는 요청과 공개 조회까지
  토큰 인자를 들고 다닌다. 지금 Provider 가 하나라 얻는 것이 없다

### C. 두 번째 AuthProvider 를 개발 모드에서 막는다

A 에 더해, 두 번째 `AuthProvider` 가 올라오면 개발 모드에서 오류를 낸다.

- 장점: 전제를 코드가 알려 준다
- 단점: TASK-024 시나리오에 없는 동작이라 시나리오부터 다시 돌아야 한다. 테스트는 파일마다 Provider 를
  새로 렌더하는데, 언마운트 없이 다시 렌더하는 테스트가 있으면 막힌다

## 결정

A. 프론트 요청 토큰의 정본은 앱에 하나뿐인 `AuthProvider` 의 세션이다. 세션이 정해지기 전과 `AuthProvider`
밖에서만 저장소를 읽는다. `AuthProvider` 가 둘 이상인 구성은 지원하지 않는다.

### 이유

- 결함의 뿌리는 "화면이 보는 로그인 상태와 요청이 보는 토큰이 다르다" 였다. 세션 하나를 둘 다의 정본으로
  두면 저장 실패·쿼터·다른 탭·소셜 로그인 경로가 한꺼번에 사라진다
- B 는 여러 Provider 를 지원하지만, 그런 구성이 없는 지금은 호출부 전부를 바꾸는 비용만 든다
- C 는 전제를 알려 줄 뿐 갈라짐을 고치지는 않는다. 시나리오를 다시 돌 만큼의 이득이 없다. Provider 가 둘
  필요해지면 그때 B 로 간다

## 결과

- 좋아지는 것:
  - 저장소에 쓰지 못하는 브라우저에서도 로그인한 주최자의 쓰기가 통과한다
  - 다른 탭의 로그인·로그아웃이 이 탭 요청의 명의를 바꾸지 않는다
- 감수하는 것:
  - `AuthProvider` 를 둘 이상 두면 요청이 한쪽 화면과 갈라진다(TASK-024 RC-1 변종 — 수용)
  - 세션 토큰이 모듈 전역이라, 테스트가 Provider 를 렌더한 뒤 언마운트하지 않고 Provider 없는 `request()` 를
    부르면 앞 세션이 남는다. `AuthProvider` 가 내려갈 때 세션을 끝내(`setSessionToken(undefined)`) 줄였다
  - 다른 탭의 로그아웃이 이 탭 화면에 반영되지 않는다(storage 이벤트 미구독 — 범위 밖)
- 되돌리려면: `http.ts` 의 `sessionToken`·`setSessionToken` 과 `AuthContext` 의 `adopt`·마운트 효과를 지우고
  `request()` 가 저장소만 읽게 한다. RC-1(저장 실패 시 401 반복)이 돌아온다. 여러 Provider 가 필요하면 B 로 간다

## 검사 가능한 제약

- 없음 — "AuthProvider 는 `main.tsx` 에 하나" 를 기계로 검사할 패턴이 아직 없다(테스트 파일은 여럿 렌더한다).
  위반은 화면·요청 불일치로 드러난다
