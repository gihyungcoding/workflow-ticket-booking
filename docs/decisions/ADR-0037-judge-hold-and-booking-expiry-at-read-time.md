# ADR-0037: 좌석 선점과 예약의 만료는 만료 시각을 저장하고 조회·쓰기 시점에 판정한다 (스케줄러를 두지 않는다)

- **상태**: 채택됨
- **날짜**: 2026-11-25
- **관련**: ADR-0004, ADR-0005, ADR-0026, `workflow_design/01_brief/BRIEF_REQ-002.json` D5·D15·D26·D35·D36·D40, `docs/product/product.md` §7

---

## 맥락

REQ-002 에는 시간이 지나면 저절로 바뀌어야 하는 상태가 둘 있다.

- **선점** — 7분 안에 예약하지 않으면 좌석이 다시 판매된다(AC-8)
- **입금 대기 예약** — 입금 기한(예약 당일 오후 11:59, Asia/Seoul)까지 입금이 확인되지 않으면 예약이
  취소되고 좌석이 다시 판매된다(AC-6). 기한 뒤의 입금 확인 요청은 거절된다(AC-9)

그리고 이 두 상태에 따라 **공연의 남은 좌석 수**가 움직여야 한다(D40). 지금은 `performance.available_seats`
저장 컬럼이 그 값이고, 공연 상태(`PerformanceStatusRules` 의 OPEN/SOLD_OUT)·공개 목록 매진 필터
(`PerformanceRepositoryImpl`)·주최자 응답이 이 컬럼을 읽는다. 선점·예약이 생기고 만료될 때마다 이 값도 맞아야 한다.

지금 사실:

- 백엔드에 `@Scheduled` · `@EnableScheduling` 이 없다. 주기 작업을 돌리는 장치가 하나도 없다
- 배포는 단일 인스턴스이고 1인 개발이다(product.md §6)
- 시각 판정은 주입된 `Clock` 으로 한다(ADR-0005). DB `now()` 를 직접 쓰지 않는다
- 좌석 선점 정합성은 유니크 제약 + 조건부 UPSERT 로 지킨다(ADR-0004). 「좌석당 살아 있는 잠금 1건」을
  DB 가 보장해야 한다
- 클라이언트는 기한이 되면 다시 조회하지 않고 화면을 전환하고, 판정은 다음 요청에서 서버가 한다(ADR-0026)

만료를 「언제 누가 반영하는가」를 정해야 한다.

## 검토한 선택지

### A. 만료 시각을 저장하고, 읽거나 쓸 때 판정한다

- 장점: 주기 작업 장치를 새로 들이지 않는다. 판정이 요청 안에서 `Clock` 하나로 이루어져
  테스트에서 시각을 옮겨 경계를 그대로 검증할 수 있다. 만료 직후에도 상태가 늦게 반영되는 틈이 없다 —
  읽는 순간이 곧 판정 순간이다
- 단점: 「만료됐다」는 사실이 행에 기록되지 않는다. 모든 읽기·쓰기 쿼리가 `expires_at` 조건을
  빠짐없이 가져야 하고, 하나라도 빠지면 만료된 선점이 살아 있는 것처럼 보인다. 만료된 행이 지워지지 않고 쌓인다

### B. 스케줄러가 주기적으로 만료 행을 정리한다

- 장점: 행의 상태가 실제와 맞춰져 조회 쿼리가 단순하다. 만료 시점에 알림 같은 후속 동작을 붙이기 쉽다
- 단점: 주기 사이에는 이미 만료된 선점이 좌석을 막는다 — 7분 선점에 1분 주기면 최대 1분 동안
  다시 팔 수 없다. 이를 피하려면 결국 조회에도 시각 조건을 걸어야 한다. 스케줄링 장치, 다중 인스턴스가
  되면 중복 실행 방지까지 새로 필요하다

### C. 둘 다 — 조회 시점 판정 + 스케줄러 정리

- 장점: 정확성은 A 로, 행 정리는 B 로 얻는다
- 단점: 판정 경로가 둘이라 같은 상태를 두 곳에서 정의한다. 이번 요청의 완료 조건 중 정리 작업이
  필요한 것이 없다

## 결정

**A — 선점·예약 모두 만료 시각(`seat_lock.expires_at`)을 저장하고, 상태는 읽거나 쓸 때 판정한다.
스케줄러는 두지 않는다.**

1. **유효의 정의** — 잠금이 유효하다 = `now < expires_at` 하나로 정의한다. `now` 는 앱 `Clock`.
   판매 확정은 `expires_at = NULL`(만료 없음). 입금 대기 예약의 잠금 만료 = 입금 기한(D26, D36)
2. **입금 기한** — 예약 당일 23:59:00 Asia/Seoul 을 `Instant` 로 바꿔 저장한다(D36)
3. **예매 상태는 저장하지 않는다** — `CONFIRMED` / `PENDING_DEPOSIT` / `CANCELLED` 를 만료 시각에서 파생한다(D15)
4. **상태를 바꾸는 쓰기는 모두 조건부 한 문장** — 영향 행 수가 좌석 수와 같을 때만 성공으로 본다(D35, D36)
   - 선점: `ON CONFLICT (seat_id) DO UPDATE … WHERE seat_lock.expires_at <= :now` — 만료된 잠금만 덮어쓴다
   - 예약 전환: `UPDATE seat_lock SET expires_at = :deadline WHERE hold_id = :h AND 본인 AND expires_at > :now`
   - 선점 해제: `DELETE … WHERE hold_id AND 본인 AND 예약 없음` — 이미 예약된 hold 는 204 no-op
   - 입금 확인: `UPDATE … SET expires_at = NULL WHERE hold_id AND expires_at > :now` — 기한 뒤면 409
     `DEPOSIT_DEADLINE_PASSED` 만 반환하고 아무것도 쓰지 않는다
5. **남은 좌석 수도 저장값이 아니라 조회 시점에 계산한다** (D40) — 남은 좌석 = 전체 좌석 − 유효한 잠금
   (만료 전 선점·입금 대기 예약, 입금 확인된 좌석). 공연 상태(`PerformanceStatusRules` 의 OPEN/SOLD_OUT)·
   공개 목록 필터(`PerformanceRepositoryImpl`)·주최자 응답이 모두 이 계산을 쓴다. `performance.available_seats`
   저장 컬럼은 더 쓰지 않는다 — 컬럼 자체를 지울지·남길지, 마이그레이션은 PLAN 에서 정한다

### 이유

B 는 주기 사이의 지연이 바로 「다시 판매된다」(AC-6·AC-8)를 늦추고, 그 지연을 없애려면 결국 A 의
시각 조건을 조회에도 걸어야 한다 — B 만으로는 완료 조건을 정확히 만족하지 못한다. C 는 그 위에 판정 경로를
하나 더 두는데, 이번 요청에서 정리 작업이 필요한 완료 조건이 없다. A 는 ADR-0004 의 조건부 UPSERT 와
ADR-0005 의 `Clock` 을 그대로 확장하고, 새 인프라가 없다.

## 결과

- 좋아지는 것:
  - 만료 경계를 `Clock` 으로 정확히 테스트한다. 동시성(ADR-0004)과 만료가 같은 조건부 쓰기 한 문장에서 함께 지켜진다
  - 운영할 주기 작업이 없다
  - 남은 좌석 수·매진 표시가 선점·만료와 같은 기준으로 바로 맞는다 — 저장값을 따로 늘리고 줄이는 쓰기가 없다
- 감수하는 것:
  - **모든 쿼리가 `expires_at` 조건을 가져야 한다.** 빠뜨리면 만료된 선점·취소된 예약이 살아 있는 것처럼
    보인다 — 리뷰·테스트로만 막는다
  - 만료·취소된 `seat_lock` 행이 지워지지 않고 남는다. 다음 선점이 덮어쓸 때까지 그대로다
  - 「취소됨」이 기록된 사건이 아니라 파생 값이라, 취소 시점에 알림(메일·문자)을 보내려면 이 결정을 다시 봐야 한다
  - 남은 좌석 수가 공연 목록·상세·주최자 응답마다 `seat_lock` 집계를 요구한다. 목록에서는 공연마다 집계가
    붙어 조회가 무거워진다 — 느려지면 집계 쿼리·인덱스를 먼저 보고, 저장값으로 돌아가는 것은 그다음이다
  - 단일 인스턴스의 앱 `Clock` 을 전제한다. 인스턴스가 늘어 시계가 어긋나면 경계 판정이 인스턴스마다 다를 수 있다
- 되돌리려면:
  - 만료 알림이나 행 정리가 필요해지면 C 로 간다 — 스케줄러를 더해 만료 행을 정리·통지하되, 판정은 A 를 유지한다.
    스케줄링 장치 도입과 중복 실행 방지가 비용이다(하루 규모)
  - 남은 좌석 수를 다시 저장값으로 하려면 선점·예약·입금 확인·만료마다 컬럼을 고쳐야 하는데, 만료는 쓰기 사건이
    아니라서 결국 스케줄러(B 또는 C)가 함께 필요하다
  - 상태를 저장하는 쪽(B)으로 완전히 바꾸려면 `booking.status` 컬럼과 마이그레이션, 모든 파생 판정의 교체가 필요하다

## 검사 가능한 제약

- `ARCH-005` — 백엔드에 `@Scheduled` · `@EnableScheduling` 을 두지 않는다
- 「쿼리마다 `expires_at` 조건」은 정적 검사로 잡기 어렵다 — 태스크 A1·A2·B 의 경계 테스트로 지킨다
- 「`available_seats` 저장 컬럼을 읽지 않는다」는 컬럼 처리가 PLAN 에서 정해진 뒤에 검사 가능 여부를 본다
