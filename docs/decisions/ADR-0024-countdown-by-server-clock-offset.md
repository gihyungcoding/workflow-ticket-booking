# ADR-0024: 오픈 카운트다운은 서버 시각과의 차이(오프셋)로 계산하고, 오픈 판정은 서버만 한다

- **상태**: 채택됨
- **날짜**: 2026-11-04
- **관련**: ADR-0005, ADR-0023, `out/prd.md` FR-1·2·5, 시안 `out/screens/concert.html`

---

## 맥락

같은 공연인데 웹이 앱보다 2.5~3초 빨랐다 (`out/prd.md` §1). 각 기기가 자기 시계로
카운트다운을 계산했기 때문이다. PRD 는 모든 기기에서 같은 시점에 0이 되고 같은 시점에
예매 버튼이 켜지기를 요구하고(FR-1·2), 어떤 기기에서도 기준 시각보다 먼저 예매를 시작할
수 없어야 한다고 한다.

## 검토한 선택지

### A. 기기 시계로 계산 (지금)

- 장점: 서버 호출이 없다.
- 단점: 바로 이 PRD 의 문제다. 기기 시계를 바꾸면 버튼이 먼저 켜진다.

### B. 서버가 매초 남은 시간을 내려준다 (폴링·SSE)

- 장점: 기기 시계와 완전히 무관하다.
- 단점: 오픈 직전 10만 명이 매초 연결을 유지한다 — 진입 보장(FR-5)과 부딪힌다.
  네트워크 지연이 그대로 표시 오차가 된다.

### C. 서버 시각 오프셋 — 화면 진입 시 서버 시각을 몇 번 받아 차이를 구하고, 그 뒤는 로컬에서 센다

- 장점: 호출이 화면 진입 시 몇 번뿐이다. 왕복 시간의 절반을 보정하면 기기 간 오차가 수십 ms
  안으로 들어온다. 기기 시계를 바꿔도 오프셋이 같이 보정된다.
- 단점: 탭이 오래 백그라운드에 있으면 다시 맞춰야 한다 (화면 복귀 시 재측정).

## 결정

**C — 프론트는 `GET /api/time` 응답으로 서버 시각 오프셋을 구해 카운트다운을 표시한다.
예매 시작(대기열 진입) 허용 여부는 서버가 주입된 `Clock`(ADR-0005)으로만 판정한다.**
버튼이 켜지는 것은 표시일 뿐이고, 0초 전에 들어온 요청은 서버가 거부한다.

### 이유

B 는 진입 보장과 부딪히고, A 는 문제 그 자체다. C 는 표시 일치(FR-1)를 싸게 얻고, 공정성
(FR-2)은 서버 판정으로 보장한다 — 표시가 어긋나도 먼저 들어갈 수는 없다.

## 결과

- 좋아지는 것: 기기 시계와 무관하게 같은 순간 0. 공정성의 최종 판정이 한 곳(서버 Clock).
- 감수하는 것: 오프셋 측정 로직과 화면 복귀 시 재측정. 오픈 정각 경계 테스트는 Clock 주입으로 쓴다.
- 되돌리려면: 오프셋 계산을 훅(`useServerClock`) 하나에 둔다. 바꿀 때 그 훅만 고친다.

## 검사 가능한 제약

- 없음 (프론트에서 `Date.now()` 를 카운트다운에 직접 쓰지 않는 규칙은 forbidden_pattern 으로
  잡기에 오탐이 많다 — 시나리오 테스트로 확인한다)
