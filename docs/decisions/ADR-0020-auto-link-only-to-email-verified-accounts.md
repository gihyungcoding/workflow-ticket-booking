# ADR-0020: 자동 연결은 이메일 소유가 확인된 계정에만 한다

- **상태**: 채택됨 (ADR-0014 의 "이메일이 같으면 이메일 가입 계정에도 연결" 부분을 대체)
- **날짜**: 2026-10-23
- **관련**: ADR-0014, ADR-0019, TASK-011 (Phase 4 FAIL RC-1), `docs/product/features/user-authentication.md`

---

## 맥락

ADR-0014 는 "제공자가 이메일을 검증했다(`email_verified=true`)면 같은 이메일의 기존 계정에 자동 연결한다"로
정했다. 그 전제는 **기존 계정의 이메일도 실제 주인의 것**이라는 것인데, 이 서비스에는 그것을 보장하는 수단이 없다.

- 이메일 가입은 메일 소유 확인이 없다 — 누구나 남의 이메일로 가입할 수 있다
- 제공자가 이메일을 검증하지 않아도(카카오 미검증, 네이버는 플래그 자체가 없다) 소셜 가입은 `/complete` 로 완료되고
  그 이메일로 `users` 행이 만들어진다

TASK-011 Phase 4 에서 임시 테스트로 재현했다(선점 계정 탈취).

1. 공격자가 피해자 이메일로 이메일 가입 → 피해자가 구글(검증됨)로 로그인 → 자동 연결, 공격자의 비밀번호 로그인 유지
2. 공격자가 카카오(미검증) 이메일로 가입 완료 → 피해자의 구글 로그인이 그 계정에 연결, 공격자의 카카오 로그인 유지
3. 네이버로 만든 계정도 같은 경로

## 검토한 선택지

### A. 소유가 확인된 계정에만 자동 연결 (채택)

`users.email_verified` 를 두고, 제공자가 검증한 이메일로 소셜 가입을 완료한 계정만 `true` 로 둔다.
자동 연결은 (제공자 플래그 true) **그리고** (대상 계정 `email_verified=true`) 일 때만.

### B. 미검증 소셜 가입만 차단

이메일 가입 계정은 계속 연결 대상. 위 경로 1 이 남는다.

### C. 이메일 가입에 메일 인증 도입

가장 근본적이지만 메일 발송 수단이 없는 이 태스크의 범위를 넘는다. 후속 태스크.

## 결정

A 를 채택한다.

- `pendingToken` 에 제공자의 `emailVerified` 를 싣고, `/complete` 가 `users.email_verified` 로 저장한다
- 이메일 가입(`/signup`)으로 만든 계정은 `email_verified=false` 다
- 자동 연결(`loginWithSocial`)은 대상 계정의 `email_verified` 가 `true` 일 때만 한다. 아니면 신규 가입과 같이
  `pendingToken` 을 발급하고, 그 가입 완료는 이메일 중복으로 409 가 된다

## 결과

- 좋아지는 것: 선점 계정에 피해자의 소셜 로그인이 붙지 않는다
- 감수하는 것
  - 이메일로 먼저 가입한 사용자가 같은 이메일의 소셜 로그인을 하면 연결되지 않고 409 에 이른다. 연결 수단
    (이메일 인증 후 연결, 로그인 후 "소셜 연결")은 후속 태스크다
  - 제공자가 검증하지 않은 이메일로 먼저 소셜 가입을 끝내면 그 이메일의 정당한 사용자가 가입하지 못한다(409).
    이메일 가입 선점과 같은 부류의 잔여 위험이며 메일 인증으로 해소된다
- 되돌리려면: `email_verified` 조건을 제거하면 ADR-0014 의 동작으로 돌아간다 — 취약점이 되살아나므로 권하지 않는다

## 검사 가능한 제약
