# ADR-0005: 시각 기준 판정은 주입된 Clock 을 쓰고 DB now() 를 직접 쓰지 않는다

- **상태**: 채택됨
- **날짜**: 2026-09-03
- **관련**: `docs/product/features/performance-availability.md` §1-3, §2, §7

---

## 맥락

이 프로덕트는 시각을 기준으로 상태가 바뀌는 판정이 여러 곳에 반복된다. 공연 예매
상태(`performance-availability` 기능, §1-3)가 첫 사례다 — `now < openAt` 이면
예정, `openAt <= now <= closeAt` 이면 예매가능·매진, `now > closeAt` 이면 마감으로
나뉜다. 곧 만들 좌석 선점(홀드) 기능도 "홀드 만료 시각이 지났는가"를 같은 방식으로
판정하게 된다(`docs/product/product.md` §7 열린 질문).

이런 경계 조건(오픈 정각, 마감 1초 전, 홀드 만료 순간)은 실서비스에서 버그가 가장
자주 나는 지점이면서, 테스트에서 재현하기 가장 어려운 지점이기도 하다. "지금부터
1초 뒤"를 테스트가 실제로 기다리게 만들 수는 없다 — 기준 시각을 코드가 통제할 수
있어야 한다.

## 검토한 선택지

### A. DB 의 now() / CURRENT_TIMESTAMP 를 쿼리에서 직접 사용

- 장점: 애플리케이션 서버와 DB 서버의 시각 차이(clock skew)를 신경 쓸 필요가 없다.
  쿼리 하나로 필터링과 판정을 끝낼 수 있어 코드가 짧다.
- 단점: 테스트에서 "지금이 오픈 정각 1초 전"이라는 상태를 만들려면 테스트 DB에
  그 시각에 맞춰 데이터를 심거나(테스트 실행마다 값을 다시 계산해야 함), 실제로
  그 시각이 될 때까지 기다려야 한다. 둘 다 CI에서 재현 가능한 결정적 테스트를
  만들 수 없다. 이 프로젝트는 TDD 워크플로우(`docs/README.md`)를 쓰므로 이
  단점은 특히 크다 — Red 단계에서 경계값 테스트를 아예 쓸 수 없다.

### B. 애플리케이션 계층에서 `java.time.Clock` 을 주입받아 사용

- 장점: 서비스가 "지금"을 직접 `Instant.now()` 로 구하지 않고 주입된 `Clock` 에서
  얻는다. 프로덕션에서는 `Clock.systemUTC()`, 테스트에서는 `Clock.fixed(...)` 로
  원하는 시각을 고정할 수 있다 — 오픈 정각·마감 1초 전 같은 경계값을 결정적으로
  테스트할 수 있다. Spring 이 `Clock` 빈 주입을 표준으로 지원해 도입 비용이 낮다.
- 단점: 쿼리 필터링(`start_at >= now`)에도 애플리케이션이 구한 시각을 바인드
  파라미터로 넘겨야 한다 — DB 가 스스로 계산하지 않으므로 코드 한 줄이 더
  필요하다. 애플리케이션 서버 시각이 DB 서버와 어긋나면(clock skew) 판정이
  미세하게 어긋날 수 있다 — 다만 단일 서버 구성(ADR-0003)이라 이 프로젝트에서는
  실질적 위험이 낮다.

## 결정

**B — `java.time.Clock` 을 주입받아 모든 시각 기준 판정에 사용한다.** SQL 의
`now()`/`CURRENT_TIMESTAMP` 는 감사용 타임스탬프(`created_at` 등, 판정에 쓰이지
않는 기록용 값)에만 허용하고, 상태 판정이나 만료 여부처럼 **분기가 갈리는 로직**
에는 쓰지 않는다.

### 이유

이 프로젝트는 Red(실패 테스트 작성)를 먼저 쓰는 TDD 워크플로우를 강제한다
(`CLAUDE.md` 절대 규칙 6). A를 선택하면 경계 시나리오의 Red 테스트 자체를 쓸 수
없어 워크플로우와 정면으로 충돌한다. B의 단점(clock skew, 쿼리에 파라미터 추가)은
단일 서버 구성에서 감수할 만한 수준이지만, A의 단점(경계값을 테스트할 수 없음)은
이 프로젝트의 개발 방식과 양립할 수 없다.

## 결과

- 좋아지는 것: 오픈 정각·마감 1초 전·홀드 만료 순간 같은 경계 조건을 `Clock.fixed`
  로 고정해 결정적으로 테스트할 수 있다. 시각 기준 판정 로직이 한 군데(주입된
  `Clock`)를 거치므로 추론하기 쉽다.
- 감수하는 것: 시각을 쓰는 쿼리마다 애플리케이션이 구한 시각을 파라미터로 넘겨야
  한다 — SQL이 한 줄 더 필요하다. 애플리케이션 서버 시각이 시스템 시각과
  어긋나면(NTP 미동기화 등) 판정이 그 오차만큼 영향을 받는다.
- 되돌리려면: 판정 로직이 `Clock` 하나를 통해서만 시각을 구하도록 강제되어 있으므로
  (검사 가능한 제약 참고), 되돌릴 때는 그 주입 지점들을 DB 쿼리로 바꾸면 된다.
  판정 지점이 늘어날수록(좌석 홀드 등) 되돌리는 비용도 함께 늘어난다 — 지금
  되돌리는 것이 가장 싸다.

## 검사 가능한 제약

- 없음 — 이번 결정 시점에는 아직 `PerformanceService` 코드가 없어 강제할 대상이
  없다. `performance-availability` 기능의 Phase 3(구현) 이후, Service 계층에서
  `Instant.now()`/`LocalDateTime.now()` 를 직접 호출하지 못하게 하는 제약을
  `docs/architecture/constraints.yaml` 에 추가하는 것을 다음 아키텍처 갱신에서
  검토한다.
