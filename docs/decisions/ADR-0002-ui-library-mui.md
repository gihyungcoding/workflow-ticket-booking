# ADR-0002: UI 라이브러리로 MUI(Material UI)를 쓴다

- **상태**: 채택됨
- **날짜**: 2026-09-02
- **관련**: `docs/product/product.md`, `docs/architecture/architecture.md`

---

## 맥락

이 프로젝트는 공연/행사 티켓 예매 서비스로, 관객이 공연을 조회하고 좌석을 선택·선점하는
화면과 주최자가 공연·좌석·가격을 등록·관리하는 화면이 필요하다. Figma 등 시안은 없다.

시안 없는 프로젝트에서 UI 라이브러리를 정하지 않고 화면 작업을 시작하면 화면마다
간격·색·타이포가 달라지고, 되돌리는 비용이 커진다. 프론트엔드는 React 로 정했고
(백엔드는 Java/Spring, DB는 PostgreSQL), 개발자는 1인이라 유지보수 부담이 큰 선택은
피해야 한다.

## 검토한 선택지

### A. shadcn/ui

- 장점: 컴포넌트 코드를 프로젝트에 직접 복사해 오는 방식이라 커스터마이즈가 완전히
  자유롭다. Radix 기반이라 접근성 기본기가 탄탄하다.
- 단점: "라이브러리"가 아니라 복사된 코드이므로 버튼·모달·테이블 등 예매 화면에
  필요한 컴포넌트를 하나하나 직접 조립·유지보수해야 한다. 1인 개발에서는 화면을
  만드는 속도보다 컴포넌트를 다듬는 데 시간이 더 들 위험이 있다.

### B. MUI (Material UI)

- 장점: 버튼·입력·모달·테이블·날짜선택 등 예매 서비스에 필요한 완성형 컴포넌트가
  이미 갖춰져 있어 "무엇을 보여줄지"만 결정하면 화면이 나온다. 간격·색·타이포가
  기본값으로 일관되게 정해져 있어 시안 없이도 화면 간 통일성이 유지된다. 커뮤니티와
  자료가 많아 1인 개발에서 막힐 때 참고할 자료를 찾기 쉽다.
- 단점: 커스터마이즈 자유도가 shadcn/ui보다 낮다. Material Design 특유의 톤이
  강하게 드러나 이 서비스만의 독자적인 룩앤필을 만들기는 어렵다.

## 결정

**B — MUI (Material UI)** 를 이 프로젝트의 UI 라이브러리로 채택한다.

### 이유

1인 개발이라는 제약에서 가장 비싼 자원은 시간이다. shadcn/ui는 디자인 자유도를 주는
대신 컴포넌트를 직접 조립·유지보수하는 비용을 요구하는데, 이 프로젝트는 화면마다
독자적인 룩앤필이 필요하지 않고(시안 없음, 예매 서비스의 표준적인 화면 구성이면 충분)
빠르게 기능을 완성하는 것이 우선이다. MUI 는 그 반대급부(자유도 감소)를 감수할 만큼
개발 속도와 화면 일관성을 준다.

## 결과

- 좋아지는 것: 컴포넌트를 새로 만들지 않고 조합만으로 화면을 완성할 수 있다.
  화면 간 간격·색·타이포가 자동으로 일관된다.
- 감수하는 것: Material Design 톤에서 크게 벗어난 디자인을 나중에 요구받으면
  MUI 테마 재정의 또는 라이브러리 교체 비용이 든다. 세밀한 커스터마이즈가
  필요한 컴포넌트는 MUI 의 스타일 오버라이드 API 를 학습해야 한다.
- 되돌리려면: 컴포넌트 단위로 점진 교체가 가능하다 (MUI 컴포넌트를 다른 라이브러리로
  하나씩 바꿔도 화면은 동작한다). 전면 교체는 화면 수만큼 비용이 든다 — 화면이
  늘어나기 전(초기)에 되돌리는 것이 가장 싸다.

## 검사 가능한 제약

- 없음 (UI 라이브러리 선택은 코드로 강제할 규칙이 아니라 컨벤션이다)
