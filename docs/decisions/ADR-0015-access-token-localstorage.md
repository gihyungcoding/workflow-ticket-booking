# ADR-0015: accessToken을 프론트 localStorage에 저장한다

- **상태**: 채택됨
- **날짜**: 2026-10-14
- **관련**: ADR-0012, `docs/product/features/user-authentication.md`

---

## 맥락

JWT 기반 인증(ADR-0012)을 쓰기로 하면서, 발급된 `accessToken`을 클라이언트가
어디에 보관할지 정해야 한다. 새로고침이나 브라우저 재시작 후에도 로그인 상태가
유지돼야 한다 — 소셜 로그인으로 가입 마찰을 줄여 사용자 유입을 확보하려는
목표([user-authentication.md](../product/features/user-authentication.md) §1-1)와
맞물려, 로그인을 자주 반복하게 만드는 선택은 피해야 한다.

## 검토한 선택지

### A. 메모리 (React 상태/Context)

- 장점: XSS가 발생해도 페이지를 벗어나면(새로고침) 토큰이 사라져 탈취 가능
  시간이 짧다
- 단점: 새로고침할 때마다 토큰이 사라져 재로그인해야 한다 — 매번 로그인해야
  하는 서비스는 쓰기 불편해, 소셜 로그인으로 가입 마찰을 줄이려는 이번 목표와
  바로 충돌한다

### B. localStorage

- 장점: 새로고침·브라우저 재시작 후에도 로그인이 유지된다. 구현이 가장
  단순하다
- 단점: XSS 공격에 취약하다 — 악성 스크립트가 페이지에서 실행되면
  `localStorage`를 그대로 읽어 토큰을 탈취할 수 있다(HttpOnly 쿠키보다 보호가
  약함)

## 결정

localStorage(B)를 쓴다.

### 이유

이 서비스는 아직 사용자 생성 콘텐츠(댓글, 후기 등)가 없어 XSS 공격 표면이
작고, React가 기본적으로 `innerHTML`을 이스케이프하므로 당장의 위험은 낮다고
판단했다. 반면 메모리 저장(A)의 "새로고침마다 재로그인" 비용은 소셜 로그인으로
가입 마찰을 줄이려는 목표와 바로 충돌한다. JWT 만료를 24시간으로 짧게 잡아
(ADR-0012) 탈취되더라도 피해 기간을 제한한다.

## 결과

- 좋아지는 것: 새로고침·브라우저 재시작에도 로그인이 유지되어 사용자 경험이
  매끄럽다
- 감수하는 것: XSS가 발생하면 토큰이 그대로 탈취된다 — 이후 사용자 생성
  콘텐츠(리뷰, 댓글 등)를 추가할 때는 이 결정을 재검토해야 한다(입력 새니타이징
  강화 또는 HttpOnly 쿠키 전환 고려)
- 되돌리려면: `AuthContext`의 저장 로직만 `localStorage`에서 `sessionStorage`나
  메모리로 바꾸면 된다. 서버 쪽 변경은 필요 없다 — 낮은 비용

## 검사 가능한 제약

- 없음. 사용자 생성 콘텐츠가 추가돼 XSS 표면이 넓어지면 CSP 헤더 도입 여부를
  `architecture-doc` 스킬로 재검토한다.
