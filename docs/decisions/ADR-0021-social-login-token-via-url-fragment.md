# ADR-0021: 소셜 로그인 토큰은 URL fragment 로 프론트에 넘긴다

- **상태**: 채택됨
- **날짜**: 2026-10-26
- **관련**: ADR-0012, ADR-0014, ADR-0015, ADR-0016, ADR-0020, TASK-011 (Phase 4 F-5, 자동 보안 리뷰), TASK-012, TASK-013, `docs/product/features/user-authentication.md` §4

---

## 맥락

소셜 로그인은 제공자 인증이 끝나면 백엔드 콜백(`/login/oauth2/code/{provider}`)이 프론트의 `/oauth2/redirect` 로 302 리다이렉트하면서 토큰을 넘긴다. 명세 §4 는 이것을 쿼리 문자열로 정했고(`?token=<accessToken>`, `?pendingToken=<pendingToken>`) TASK-011 이 그대로 구현했다.

쿼리 문자열에 실린 값은 다음 위치에 남는다.

- 프론트 호스트의 접근 로그와 프록시·CDN 로그 (accessToken 유효기간 24시간)
- 브라우저 히스토리와 주소창 자동완성
- 이 페이지에서 다른 사이트로 나갈 때의 `Referer` 헤더

TASK-011 Phase 4 리뷰가 F-5(medium)로 지적했고, 푸시 뒤 자동 보안 리뷰도 같은 지점을 지적했다. 아직 프론트(TASK-013)와 애플(TASK-012)이 이 규약을 쓰기 전이라 지금 정하면 바꾸는 비용이 가장 작다.

제약은 다음과 같다.

- 프론트와 백엔드는 따로 배포되고 출처가 다르다 (ADR-0016)
- accessToken 은 프론트 localStorage 에 저장한다 (ADR-0015), 서버는 STATELESS 다 (ADR-0012, ADR-0013)
- 토큰 저장소를 둘 인스턴스 간 공유 수단이 없다 (단일 인스턴스 가정, 다중 인스턴스는 DB 가 필요하다)

## 검토한 선택지

### A. URL fragment (`/oauth2/redirect#token=…`) (채택)

- 장점: fragment 는 HTTP 요청에 실리지 않아 접근 로그·프록시 로그·`Referer` 로 가지 않는다. 서버 상태와 새 엔드포인트가 없다. localStorage 저장(ADR-0015)과 그대로 이어진다. 백엔드 변경은 핸들러의 리다이렉트 주소 한 줄이다.
- 단점: 브라우저 히스토리에 잠깐 남고 페이지 JS 가 읽을 수 있다. 프론트가 읽은 직후 `history.replaceState` 로 지워야 하며, 안 지우면 이점이 줄어든다. 명세 §4 와 TASK-013 의 읽는 방식이 query 에서 fragment 로 바뀐다.

### B. 일회용 코드 교환 (`?code=…` → `POST /api/auth/social/exchange`)

- 장점: 토큰이 URL 에 전혀 실리지 않는다. 가로채도 한 번 쓰면 무효이고 짧은 만료를 둘 수 있다.
- 단점: 코드 저장소와 만료 정리가 필요하다(단일 인스턴스면 메모리, 다중이면 DB 테이블). 새 엔드포인트와 시나리오·재검증이 생긴다. accessToken 은 어차피 localStorage 에 저장되므로(ADR-0015) 로그·Referer 노출 외의 XSS 위험은 줄지 않는다. 지금 규모에서는 비용 대비 이득이 작다.

### C. 현행 유지 (쿼리 문자열)

- 장점: 변경이 없다. 명세와 구현이 이미 일치한다.
- 단점: 접근 로그·Referer 노출이 그대로 남고, 프론트가 즉시 URL 을 지우는 것에 전적으로 기댄다.

### D. HttpOnly 쿠키로 전달

- 장점: JS 가 토큰을 읽지 못한다.
- 단점: 출처가 다른 배포(ADR-0016)에서 `SameSite=None`·CORS credentials 설정이 필요하고 ADR-0015(localStorage 저장)를 뒤집어야 한다. 이 결정의 범위를 넘는다.

## 결정

리다이렉트에는 accessToken·pendingToken 을 URL fragment 로 싣는다 (`{FRONTEND_BASE_URL}/oauth2/redirect#token=…`, `#pendingToken=…`). 프론트는 읽은 즉시 `history.replaceState` 로 fragment 를 지우고 저장·이동한다. pendingToken 을 로그인을 시작한 브라우저에 묶지는 않는다(아래 감수).

### 이유

- C 는 노출을 그대로 둔다. D 는 ADR-0015·ADR-0016 을 같이 건드려야 해서 이 결정으로 다룰 수 없다.
- B 는 가장 강하지만 저장소·만료·엔드포인트·시나리오를 새로 만들어야 한다. accessToken 이 localStorage 에 있는 한 페이지 스크립트로 읽히는 위험은 B 로도 줄지 않으므로, 로그·Referer 노출만 막는 A 가 현재 비용에서 맞다.
- A 는 서버 변경이 한 줄이고 단일 인스턴스·다중 인스턴스 모두 같은 방식으로 동작한다.

## 결과

- 좋아지는 것: 토큰이 접근 로그·프록시 로그·`Referer` 에 남지 않는다. 서버 상태가 늘지 않는다.
- 감수하는 것:
  - 브라우저 히스토리와 페이지 JS 에는 토큰이 잠깐 있다. 프론트가 즉시 지우는 구현에 기댄다.
  - pendingToken 을 가로챈 쪽이 5분 안에 `/complete` 를 호출할 수 있다(브라우저 바인딩 없음). 가입이 끝난 뒤 로그인 토큰은 응답 본문으로만 나가 로그인 세션 탈취로 이어지지는 않지만, 다른 사람의 소셜 계정으로 가입을 완료시킬 수는 있다. 이 위험은 수용하고, 다중 출처 쿠키 설정이 정리되면 쿠키 nonce 를 다시 검토한다.
  - 명세 §4 와 TASK-013 의 읽는 방식이 바뀐다. TASK-012(애플)가 같은 핸들러를 쓰므로 함께 따른다.
  - TASK-011 PR(#22) 의 핸들러는 아직 query 를 쓴다. 프론트가 이 규약을 쓰기 전, 그리고 배포 전에 바꿔야 한다. 바꾸는 일은 후속 태스크로 만들어 Phase 를 거친다.
- 되돌리려면: 핸들러의 리다이렉트 주소를 query 로 되돌리고 프론트 읽기를 바꾸면 된다. 서버 저장소가 없어 데이터 이전은 없다. 더 강한 방식(B)으로 가려면 이 ADR 을 대체하는 새 ADR 이 필요하다.

## 검사 가능한 제약

- 없음 (핸들러의 리다이렉트 주소 형식은 후속 태스크의 시나리오로 검증한다)
