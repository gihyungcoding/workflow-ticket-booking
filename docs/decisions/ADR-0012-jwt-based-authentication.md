# ADR-0012: 세션이 아닌 JWT(Bearer 토큰)로 인증한다

- **상태**: 채택됨
- **날짜**: 2026-10-14
- **관련**: ADR-0013, ADR-0015, `docs/product/features/user-authentication.md`

---

## 맥락

지금까지 백엔드는 인증이 필요 없는 공연 조회/등록 API만 있었다. 관객과 주최자를
구분하려면 사용자 식별 수단이 필요하다([user-authentication.md](../product/features/user-authentication.md)).

동시에 이 기능은 카카오·네이버·구글·애플 소셜 로그인 4종을 함께 지원해야 한다.
소셜 로그인은 각 제공자 도메인으로 리다이렉트됐다가 우리 서버로 다시 콜백되는
흐름이라, 그 과정에서 사용자를 어떻게 식별된 상태로 유지할지를 먼저 정해야
나머지(Spring Security 구성, 프론트 상태 관리)를 설계할 수 있다.

프론트(React SPA, Vite 개발 서버)와 백엔드(Spring)는 개발 중 서로 다른 포트에서
뜨고, 아키텍처상(`architecture.md` §1) 별도 캐시·세션 저장 계층을 두지 않는
단일 서비스 구성을 유지해야 한다.

## 검토한 선택지

### A. 서버 세션 (Spring Session + HttpOnly 쿠키)

- 장점: 단일 모놀리식 구조와 자연스럽게 맞고, 서버가 세션을 직접 통제하므로
  즉시 로그아웃·강제 만료가 쉽다
- 단점: 프론트 개발 서버와 백엔드 간 쿠키 공유에 SameSite/CORS 설정이 필요하고,
  세션 저장소를 별도로 관리해야 한다. 소셜 로그인 콜백처럼 여러 외부 도메인을
  오가는 리다이렉트 체인에서 `SameSite=Lax` 쿠키가 누락되는 사례가 흔해, 로그인
  흐름 자체가 깨질 위험이 있다

### B. JWT (Bearer 토큰)

- 장점: 서버가 상태를 갖지 않아 세션 저장소가 필요 없다. 소셜 로그인 콜백 흐름에서
  쿠키 SameSite 정책과 무관하게 URL 파라미터나 `Authorization` 헤더로 토큰을
  주고받을 수 있다
- 단점: 토큰 무효화(즉시 로그아웃, 탈취 시 강제 만료)가 세션보다 어렵다 — 만료
  시간에 의존하거나 별도 블랙리스트가 필요하다. 클라이언트가 토큰을 직접
  보관해야 해 저장 위치에 따라 탈취 위험이 생긴다(→ ADR-0015)

## 결정

JWT(Bearer 토큰) 방식을 쓴다.

### 이유

소셜 로그인 4종의 OAuth2 콜백 흐름이 여러 외부 도메인을 오가는 리다이렉트
체인이라, 세션 쿠키 방식(A)은 SameSite 정책과 충돌할 여지가 크고 1인 개발
체제에서 쿠키 도메인/CORS 문제를 디버깅하는 데 드는 시간이 더 크다고 판단했다.
즉시 토큰 무효화를 포기하는 대신 만료 시간을 24시간으로 짧게 잡아 위험을
완화한다(`user-authentication.md` §8).

## 결과

- 좋아지는 것: 서버가 상태를 갖지 않아 세션 저장소·쿠키 설정이 필요 없고,
  소셜 로그인 리다이렉트 흐름을 쿠키 정책 걱정 없이 구현할 수 있다
- 감수하는 것: 로그아웃이 서버가 아니라 클라이언트의 토큰 삭제에 의존한다 —
  토큰이 탈취되면 만료 전까지 막을 방법이 없다(블랙리스트 없음)
- 되돌리려면: 세션 기반으로 바꾸려면 `JwtTokenProvider`/`JwtAuthenticationFilter`를
  세션 생성/검증 필터로 교체하고, 프론트의 `AuthContext`가 토큰 대신 쿠키 기반
  인증 상태 확인(`/auth/me` 호출)으로 동작하도록 바꿔야 한다. 이미 발급된 토큰을
  쓰는 클라이언트는 전부 재로그인해야 한다 — 인증 관련 파일 범위로 한정되는
  중간 비용

## 검사 가능한 제약

- 없음 (인증 방식 자체는 런타임 동작이라 정적 검사로 강제하기 어렵다)
