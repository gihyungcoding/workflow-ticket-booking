# ADR-0008: 클라이언트 라우팅으로 react-router-dom을 쓴다

- **상태**: 채택됨
- **날짜**: 2026-09-08
- **관련**: ADR-0003, TASK-002

---

## 맥락

TASK-002는 공연 목록 화면과 상세 화면을 만들었고, 목록에서 상세로 이동하는 화면 간
이동이 필요했다. 완료 조건(AC6)은 "존재하지 않는 공연 상세로 **진입**(404)하면
안내와 [목록으로] 버튼이 표시된다"를 요구하는데, 이는 상세 화면에 **URL로 직접
접근**할 수 있어야 한다는 뜻이다(딥링크). React SPA에서 URL과 화면 상태를
동기화하려면 클라이언트 라우팅이 필요하다.

## 검토한 선택지

### A. 라우팅 라이브러리 없이 자체 구현 (useState로 현재 화면 관리)

- 장점: 의존성이 늘지 않는다. 화면이 2개뿐인 지금 규모에서는 코드도 단순하다.
- 단점: URL과 화면 상태가 동기화되지 않아 새로고침·뒤로가기·URL 직접 접근이
  자연스럽게 동작하지 않는다. AC6이 요구하는 "존재하지 않는 id로 진입"은 URL
  기반 딥링크를 전제하므로, 이 방식으로는 애초에 요구사항을 자연스럽게 만족시킬
  수 없다.

### B. react-router-dom

- 장점: React 생태계의 사실상 표준 라우터. URL↔화면 상태가 자동으로 동기화돼
  새로고침·직접 URL 접근·뒤로가기가 기본으로 동작한다. `useParams` 로 `:id` 를
  받아 상세 페이지를 URL과 독립적으로 테스트할 수 있다(`MemoryRouter`).
- 단점: 화면이 2개뿐인 지금 시점에는 기능 대비 다소 무거운 선택일 수 있다.

## 결정

**B — react-router-dom.**

### 이유

완료 조건 자체가 URL 기반 딥링크(존재하지 않는 id로 "진입")를 전제하므로, 자체
구현(A)으로는 이 요구사항을 자연스럽게 만족시킬 수 없다. 이 서비스는 공연·좌석·예매
전 과정에서 화면이 계속 늘어날 예정이라(`docs/product/product.md`), 지금부터
표준 라우터를 쓰는 편이 나중에 되돌리는 비용보다 싸다.

## 결과

- 좋아지는 것: URL 기반 딥링크·새로고침·뒤로가기가 기본으로 동작한다.
  `useParams`/`MemoryRouter` 로 라우트와 독립적인 컴포넌트 테스트 작성이 쉽다
  (`PerformanceDetailPage.test.tsx`에서 실제로 사용).
- 감수하는 것: 화면이 매우 단순한 지금 시점에는 다소 과한 의존성일 수 있다.
  화면이 늘어날 때마다 `App.tsx`의 라우트 정의를 갱신해야 한다.
- 되돌리려면: 화면 수가 이대로 적게 유지된다면 자체 상태 관리로 되돌릴 여지는
  있으나, 딥링크 요구사항이 존재하는 한 실질적으로 되돌리기 어렵다(요구사항 자체가
  라우터를 전제한다).

## 검사 가능한 제약

- 없음 (라우팅 라이브러리 선택은 코드로 강제할 규칙이 아니라 컨벤션이다)
