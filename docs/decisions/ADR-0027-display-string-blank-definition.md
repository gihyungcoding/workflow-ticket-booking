# ADR-0027: 표시 문자열의 「공백 아님」은 유니코드 공백·NBSP·U+200B 를 공백으로 보는 한 판정으로 하고, 서식 문자는 받는다

- **상태**: 채택됨
- **날짜**: 2026-11-11
- **관련**: ADR-0010, ADR-0019, TASK-019 (VERIFY RC-2, 회고 ADR 후보 1), `backend/.../api/dto/ZoneRequest.java`

---

## 맥락

ADR-0019 는 서버가 **거부하는** 문자열을 정했다. 거부 대상은 제어문자와 짝 없는 서로게이트이고, 이메일만 앞뒤
공백을 걷어낸다. 그런데 **「공백 아님」(필수 문자열이 비어 보이지 않아야 한다)은 무엇이 공백인가**를 정하지 않았다.

그 빈자리를 도구가 저마다의 기본값으로 메웠다.

| 판정 수단 | 공백으로 보는 것 | 공백으로 보지 않는 것 |
|---|---|---|
| `@NotBlank` (Hibernate Validator) | ASCII 공백, U+3000, U+2003, U+2028 | NBSP(U+00A0), U+200B |
| 정규식 `\S` (플래그 없음) | ASCII 공백만 | U+3000 등 유니코드 공백 전부 |
| `Character.isDigit` (숫자 판정) | — | 아랍-인도·전각 숫자도 숫자로 본다 |

TASK-019 는 같은 구역 묶음의 `area` 를 `@NotBlank` 로, `note` 를 `\S` 정규식으로 검증했다. 그 결과 전각 공백 하나는
`area` 에서는 거부되고 `note` 에서는 201 로 저장됐다. Phase 4 1회차는 이것으로 FAIL 했다.

화면은 이 값을 그대로 그린다(구역 위치 시트의 묶음 이름·설명). 공백만 있는 값은 빈 줄로 보인다. 같은 질문이 앞으로
들어올 표시 문자열 전부에 있다: 회원 이름, 공연 제목·공연장, 회차 이름(흐름 4).

## 검토한 선택지

### A. `@NotBlank` 를 그대로 쓴다

- 장점: 애노테이션 하나. 이미 회원 가입·로그인·공연 등록 DTO 가 쓰고 있어 바꿀 것이 없다
- 단점: NBSP 와 U+200B 만으로 된 값을 받는다. 둘 다 붙여넣기로 흔히 들어오는 글자다(웹 페이지의 `&nbsp;`, 메신저의
  제로폭 공백). Hibernate Validator 의 판정 기준은 라이브러리 버전이 정하고, 이 프로젝트가 정한 것이 아니다

### B. 정규식 `\S` 로 「공백이 아닌 글자가 있다」를 본다

- 장점: `@Pattern` 하나로 다른 문자 규칙(`\p{Cc}` 거부)과 나란히 적을 수 있다
- 단점: 플래그가 없으면 ASCII 공백만 공백으로 본다. TASK-019 결함이 바로 이것이다. `(?U)` 를 붙여도 NBSP·U+200B 는
  여전히 글자로 본다

### C. 공백 글자 목록을 이 프로젝트가 정하고, 한 상수로 판정한다

- 장점: 필드마다 같은 판정이다. 무엇이 공백인지가 코드 한 곳(`ZoneRequest.NOT_BLANK`)과 이 ADR 에 적혀 있다.
  목록을 바꿀 때 한 곳만 고친다
- 단점: 목록 밖의 보이지 않는 글자는 글자로 본다. 상수를 기존 DTO 에 옮기기 전까지 `@NotBlank` 를 쓰는 필드와
  판정이 다르다

### D. C 에 서식 문자(Cf)·U+2800·U+3164 까지 공백으로 넣는다

- 장점: 「보이지 않는 글자만」인 값을 더 넓게 막는다
- 단점: Cf 에는 글자로 쓰이는 것이 섞여 있다. 이모지 연결자 U+200D, 줄바꿈 위치를 알리는 소프트 하이픈 U+00AD 가
  그렇다. 공백만인지 판정하는 데만 쓰더라도 목록이 계속 늘어난다. 입력 주체가 주최자와 회원이라, 보이지 않는 글자로
  얻을 수 있는 이득(빈 이름으로 보이기)이 이 비용을 넘지 않는다

## 결정

**C — 「공백 아님」은 공백이 아닌 글자가 하나 이상 있다는 뜻이다. 공백으로 보는 글자는 유니코드 공백(분류 Zs·Zl·Zp,
탭·줄바꿈 포함 — NBSP U+00A0 와 전각 공백 U+3000 도 여기에 든다)과 제로폭 공백 U+200B 다.** 판정은 정규식 상수 하나
(`(?s)(?U).*[^\p{Z}\s​].*`)로 하고, 같은 규칙을 쓰는 필드는 같은 상수를 쓴다. 서식 문자(Cf)·U+2800·U+3164 는
글자로 보고 받는다.

숫자도 같은 원칙이다. 포트·번호처럼 ASCII 숫자만 받는 곳은 `Character.isDigit` 가 아니라 `'0'~'9'` 로 판정한다.

### 이유

A 와 B 는 「무엇이 공백인가」를 라이브러리 기본값에 맡긴다. TASK-019 에서 두 기본값이 한 묶음 안에서 서로 다르게
판정했고, 그것이 결함이었다. C 는 목록을 이 프로젝트가 소유하게 한다. D 는 막는 이득이 작은데 목록이 끝나지 않는다.
TASK-019 Phase 4 2회차에서 사용자가 서식 문자를 수용하기로 결정했다(VERIFY `accepted_risk`).

## 결과

- 좋아지는 것:
  - 「비어 보이는 값」의 기준이 필드마다 같다
  - 시나리오가 단언할 글자 목록이 정해져 있다 — `coverage_matrix.py` 의 `string.unicode_blank` 칸
- 감수하는 것:
  - 기존 DTO 의 `@NotBlank` 필드(회원 이름, 공연 title·venue 등)는 아직 이 판정이 아니다. NBSP·U+200B 만인 값을 받는다.
    옮길 때까지 두 기준이 함께 있다
  - 서식 문자만으로 된 값은 받는다. 화면에서는 빈 칸처럼 보일 수 있다
  - 상수가 지금은 `ZoneRequest` 안에 있다. 두 번째 DTO 가 쓰기 전에 `NoLoneSurrogate` 처럼 공용 클래스로 옮겨야 한다
- 되돌리려면:
  - D 로 넓히려면 상수의 문자 클래스에 `\p{Cf}⠀ㅤ` 를 더하면 된다. 비용은 한 줄과 기존 시나리오 표 보강이다
  - A 로 돌아가려면 `@Pattern` 을 지운다. 그러면 TASK-019 SC-08 의 e3·e4·j2~j6 행이 실패하므로 그 테스트도 고쳐야 한다

## 검사 가능한 제약

- 없음 — 「표시 문자열 필드는 NOT_BLANK 상수를 쓴다」는 어느 필드가 표시용인지 정적으로 가릴 수 없다. 대신 2a 의
  `string.unicode_blank` 칸이 필드마다 확인하게 한다(TASK-019 회고 반영, `scripts/coverage_matrix.py`)
