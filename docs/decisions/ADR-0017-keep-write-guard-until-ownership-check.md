# ADR-0017: 쓰기 가드는 공연 쓰기 API 에 소유권 검사가 붙을 때까지 유지한다

- **상태**: 채택됨
- **날짜**: 2026-10-21
- **관련**: ADR-0016 (쓰기 가드 제거 시점을 대체), ADR-0012, ADR-0013, `docs/product/features/user-authentication.md` §7, `TASK-009`, `TASK-014`

---

## 맥락

ADR-0016 은 배포 기간의 임시 방어로 쓰기 가드(`X-Write-Key`)를 두면서 "`TASK-009`(인증)가
들어오면 제거한다"고 적었다. TASK-009 를 계획하며 이 문장이 현재 범위와 맞지 않는 것을 확인했다.

- TASK-009 는 이메일 가입·로그인·`GET /api/auth/me` 와 `SecurityFilterChain`, JWT 를 만든다.
  **기존 `/api/performances/**` 는 `permitAll` 로 유지**하고(회귀 금지), **소유권 검사는 범위
  밖**이다 (`user-authentication.md` §7, §8)
- 즉 TASK-009 가 끝나도 공연 등록·수정·취소는 로그인 여부와 관계없이 누구나 호출할 수 있다.
  인증이 "있는" 것과 쓰기 API 가 인증을 "요구하는" 것은 다르다
- 이 시점에 쓰기 가드가 공연 쓰기 API 의 **유일한 방어**다. 첫 배포 환경(Render·Pages)이 이미
  떠 있어 주소를 아는 누구든 호출할 수 있다
- 소유권 연동(`performance.owner_id`, 쓰기 API 의 소유권 검사)은 요구사항 문서도 태스크도
  아직 없다 — 다음 별도 문서로 분리한다고만 적혀 있다

## 검토한 선택지

### A. 가드를 TASK-009 에서 제거한다 (ADR-0016 의 원래 문장)

- 장점: ADR-0016 의 약속을 그대로 지킨다. 프론트의 `VITE_WRITE_KEY` 주입을 없앨 수 있다
- 단점: 소유권 검사 없이 가드가 사라져 공연 쓰기가 **완전히 열린다.** 로그인이 있어도
  아무도 검사하지 않는다

### B. 가드를 유지하고, 소유권 검사가 붙을 때 제거한다

- 장점: 인증과 소유권이 갖춰지기 전까지 방어가 사라지지 않는다. TASK-009 범위(permitAll
  유지)를 건드리지 않는다
- 단점: 가드와 인증이 한동안 공존한다. 가드 제거 시점이 **아직 없는 태스크**에 걸려 있어,
  그 태스크를 만들지 않으면 임시 방어가 영구화될 수 있다

### C. TASK-009 에서 공연 쓰기 API 를 "로그인한 사용자만"으로 막는다

- 장점: 가드 없이도 익명 쓰기가 막힌다
- 단점: TASK-009 의 "공연 API 는 `permitAll`·회귀 없음" 완료 조건과 충돌한다. 로그인 화면
  (TASK-010)이 없어 프론트에서 등록·수정·취소가 불가능해진다. 소유권 없이 아무 로그인
  사용자가 남의 공연을 지울 수 있어 문제의 일부만 옮긴다

## 결정

**B.** 쓰기 가드는 TASK-009 에서 건드리지 않고 유지한다. 제거 시점은 **공연 쓰기 API 에
인증·소유권 검사가 붙는 태스크**다. ADR-0016 의 "TASK-009 가 들어오면 제거한다"는 이 결정으로
대체한다.

### 이유

가드를 지우는 것은 방어를 줄이는 일이라, 그것을 대신할 검사가 **먼저 있어야** 한다. 소유권
검사가 없는 지금 가드를 지우면 인증 기능이 오히려 보안 수준을 낮춘다. A 는 약속을 지키는 대신
그 대가가 크고, C 는 이 태스크의 범위와 완료 조건을 깬다.

B 의 약점은 제거 조건이 아직 존재하지 않는 태스크라는 점이다. 이를 막으려고 **후속 요구사항
문서와 태스크를 만드는 것을 이 결정의 후속 조치로 기록**한다.

## 결과

- 좋아지는 것: 인증 도입 중에도 공연 쓰기 방어가 유지된다. TASK-009 의 범위가 깨끗하다
- 감수하는 것:
  - 가드와 JWT 인증이 한동안 함께 있다. 인증 API(`/api/auth/signup`·`/login`)가 가드를
    통과해야 하는지는 TASK-009 Plan 에서 정한다 (프론트의 쓰기 요청은 모두 `X-Write-Key` 를
    싣는다)
  - 쓰기 가드 키가 번들에 노출되는 한계(ADR-0016)가 소유권 검사가 들어올 때까지 이어진다
  - **후속 태스크가 없으면 임시 방어가 영구화된다.** 그 태스크가 만들어질 때까지 이 위험이
    열려 있다
- 되돌리려면: 이 ADR 을 대체하는 새 ADR 을 쓴다. 가드는 `WRITE_GUARD_ENABLED` 로 끌 수 있다
- 후속 조치:
  - 공연 소유권과 쓰기 API 인증을 다루는 요구사항 문서를 만들고(`/wf-feature`) 태스크를
    생성한다 (`performance.owner_id`, 쓰기 API 소유권 검사, 쓰기 가드 제거, 등록·수정·취소
    화면 진입점과 역할별 노출)
  - 첫 배포에서 발견된 등록·수정·취소 진입점 공백(`docs/release/first-deploy-checklist.md` §10)을
    그 문서에서 함께 다룬다
