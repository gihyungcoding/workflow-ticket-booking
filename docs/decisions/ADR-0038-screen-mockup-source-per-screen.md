# ADR-0038: 화면 시안 정본을 화면 단위로 나눈다 — 기존 화면은 `out/`, 요청이 새로 만들거나 대체한 화면은 그 요청의 시안

- **상태**: 채택됨
- **날짜**: 2026-11-25
- **관련**: ADR-0022 (화면 시안 정본 부분을 대체), ADR-0011, `docs/product/design.md` §0, `workflow_design/01_brief/BRIEF_REQ-002.json` D41·D42, `workflow_design/01_brief/mockup/REQ-002/`

---

## 맥락

ADR-0022 는 화면 정본을 `out/screens/*.html` 하나로 정했다 — 「화면 코드는 `out/screens/<id>.html` 과 같아야 한다」.
그 뒤 요청마다 `ui-mockup` 스킬로 시안을 만들게 됐고, REQ-002(예매 흐름 최소 경로)가 처음으로 승인된 요청 시안을 갖는다
(`workflow_design/01_brief/mockup/REQ-002/`, rev 6).

지금 사실:

- 두 시안이 **같은 화면을 다르게** 그린다. `out/` 의 `seat`·`seat--error`·`checkout`·`booked`·`my-bookings` 는
  REQ-002 가 새로 그린 좌석·예약·내 예매 화면과 겹친다. `out/` 쪽은 대기열·회차·연석 자동 선점·카드 결제를 전제로 하고,
  REQ-002 는 그것들을 범위 밖으로 둔 최소 경로다
- 토큰 값은 같다 — `docs/product/design-tokens.css` 와 REQ-002 시안 `tokens.css` 를 대조했다(D42)
- 부품 class 차이는 새 키트에 `picker*`·`seat`·`due*` 가 더해지고 `toast` 가 없다는 것뿐이다
- 새 부품(좌석 칸 고르기 `picker`, 미니맵 `picker-mini`, 기한 줄 `due`)은 `frontend/src/components/ui` 에 아직 없다
- REQ-002 시안에는 1280 데스크톱 배치가 있지만 지금 앱은 데스크톱에서도 모바일 폭 한 줄(`appMaxWidth`)이다 —
  이번에는 모바일 폭으로 가기로 했다(D41)

Phase 4 는 「화면을 띄워 시안과 같은가」로 판정한다(ADR-0022). 같은 화면에 시안이 둘이면 그 판정이 성립하지 않는다.

## 검토한 선택지

### A. REQ-002 시안을 `out/` 에 합친다

- 장점: 정본 폴더가 하나로 유지된다. ADR-0022 를 건드리지 않는다
- 단점: `out/` 은 30장이 한 여정·한 사실 표(`out/journey.md`)로 묶인 시안이다. 다른 사실 표와 범위를 가진 화면을 섞으면
  흐름 캔버스(`out/index.html`)의 갈래와 사실이 어긋난다. 요청마다 이 병합을 반복해야 하고, 승인된 시안을 옮기는 동안 사본이 생긴다

### B. 앱 전체 화면을 새 키트로 다시 그린다

- 장점: 정본이 다시 하나가 되고 부품 체계도 하나다
- 단점: 이미 구현된 로그인·홈·상세·주최자 화면을 이번 요청과 무관하게 다시 그려야 한다. REQ-002 범위(D1 최소 경로)를 크게 넘는다.
  토큰 값이 같아 얻는 것이 적다

### C. 정본을 화면 단위로 나눈다

- 장점: 각 화면에 정본이 하나뿐이라 Phase 4 판정이 그대로 성립한다. 승인된 요청 시안을 옮기지 않고 그 자리에서 쓴다.
  기존 화면은 손대지 않는다
- 단점: 정본이 두 곳에 있어 「이 화면의 정본은 어디인가」를 대응표로 찾아야 한다. 두 키트의 부품 모양이 조금씩 다를 수 있다

## 결정

**C — 화면 시안 정본은 화면 단위로 정한다.**

1. **기존 화면** — 정본은 계속 `out/screens/*.html` (ADR-0022)
2. **요청이 새로 만들거나 대체한 화면** — 정본은 그 요청 시안의 **모바일 화면** `workflow_design/01_brief/mockup/<REQ>/screens/*.html`.
   데스크톱 시안(`screens/desktop/`)은 보관(참고용)이고 정본이 아니다 — 앱은 모바일 폭 한 줄이다(D41)
3. **대체된 `out/` 화면은 지우지 않는다** — `design.md` §0 대응표에 「어느 화면으로 대체됐는가」를 적는다.
   REQ-002 가 대체: `seat`·`seat--error`·`checkout`·`booked`·`my-bookings`
4. **토큰 정본은 하나** — `docs/product/design-tokens.css`. REQ-002 시안의 `tokens.css` 는 같은 값이다(대조함, D42)
5. **새 부품은 공통 부품으로** — 요청 키트에만 있는 부품(REQ-002: `picker`·`picker-mini`·`due`)은 `frontend/src/components/ui` 에
   공통 부품으로 만든다. 화면 안에 개별로 구현하지 않는다

### 이유

A 는 사실 표가 다른 두 시안을 한 여정으로 합쳐 캔버스 자체를 틀리게 만들고, 요청마다 같은 병합을 치른다. B 는 이번 요청과
무관한 화면을 다시 그리는 비용이고, 토큰이 같아 얻는 것이 적다. C 는 「화면 하나에 정본 하나」라는 ADR-0022 의 핵심(시안과 같은가로 판정)을
지키면서 요청 시안 흐름(`ui-mockup`)과 맞는다.

## 결과

- 좋아지는 것:
  - 승인된 요청 시안을 그대로 정본으로 쓴다 — 옮기는 동안 생기는 사본이 없다
  - 기존 화면과 그 테스트는 그대로다
  - 새 부품이 공통 부품이 되어 다음 요청이 재사용한다
- 감수하는 것:
  - 정본을 찾으려면 대응표를 봐야 한다. 대응표가 낡으면 대체된 `out/` 화면을 정본으로 착각할 수 있다
  - 두 키트의 부품이 공존한다 — `out/` 의 `toast` 는 새 키트에 없고, 새 키트의 `picker*`·`seat`·`due*` 는 `out/` 에 없다
  - 데스크톱 시안은 만들어 두고 쓰지 않는다(D41). 앱 전체 데스크톱 배치는 별도 요청이 다시 본다
- 되돌리려면:
  - 정본을 다시 하나로 하려면 B 처럼 남은 `out/` 화면을 새 키트로 다시 그리는 요청을 만들고, 끝나면 `out/` 을 보관으로 돌린다.
    화면 수에 비례하는 비용이다
  - A 로 가려면 요청 시안의 모바일 화면을 `out/screens/` 로 옮기고 `out/journey.md`·`out/index.html` 을 다시 엮는다

## 검사 가능한 제약

- 없음 — 「화면이 정본 시안과 같다」는 Phase 4 화면 확인으로 본다. 「새 부품을 화면 안에 개별 구현하지 않는다」는 정적 검사로
  잡기 어렵다(Phase 4 리뷰). 기존 DESIGN-001·002·003 은 그대로 쓴다
