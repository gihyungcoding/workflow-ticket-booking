# ADR-0034: 공연 상세의 경미한 변종 두 건(시트 재진입 뒤 중복 history 칸, 시각 순서 미검증)은 고치지 않고 수용한다

- **상태**: 채택됨
- **날짜**: 2026-11-16
- **관련**: TASK-020 (VERIFY RC-2 변종 · RC-4 변종), ADR-0018, ADR-0024, ADR-0026, `frontend/src/pages/PerformanceDetailPage.tsx`, `frontend/src/api/performances.ts`

---

## 맥락

TASK-020 Phase 4 는 1회차에 코드 리뷰어의 `[correctness]` 3건으로 FAIL 했고, 시나리오(2a)로 돌아가 뿌리 4개의 변종을 한 번에 고쳤다.
2회차 리뷰는 이전 변종이 모두 해소됐다고 확인하면서, 같은 뿌리에서 **경미한 변종 두 건**을 더 재현했다.

1. **시트 재진입 뒤 중복 history 칸 (RC-2).** 구역 위치 시트를 열고(이 화면에서 눌러 연 칸) → 브라우저 뒤로 가기로 닫고 → 앞으로 가기로 시트 칸에
   다시 들어온 뒤 「확인」으로 닫으면, 화면은 그 칸이 「이 화면에서 눌러 연 것」인지 「열린 채 들어온 것」인지 구분할 수 없다
   (`pressed` 는 닫기 때 false 로 초기화된다). 그래서 열린 채 들어온 주소의 규칙(그 칸을 시트 없는 상세로 교체)을 따르고,
   결과 history 가 `[/, 상세, 상세]` 가 된다. 뒤로 가기를 한 번 눌러도 상세에 머문다. 장애는 아니다 — 한 칸이 더 남을 뿐이다.
2. **시각 순서 미검증 (RC-4).** `parseDetail` 은 `startAt`·`openAt`·`closeAt` 각각이 ISO 순간인지만 보고 `openAt ≤ closeAt ≤ startAt` 인지는 보지 않는다.
   서버는 등록·수정 때 이 순서를 DB CHECK 와 `InvalidTimeOrderException` 으로 보장하므로 정상 응답에서는 나오지 않는다.
   서버가 모순된 값을 주면 예정 → 예매 가능 전환 뒤에 이미 지난 시각의 「마감돼요」와 켜진 CTA 가 함께 뜬다.

둘 다 시나리오에 없는 동작이라 고치려면 시나리오(2a) → 독립검증 → Red 승인 → Green → 재검증을 한 바퀴 더 돌아야 한다.

## 검토한 선택지

### A. 두 건 모두 고친다 (Phase 2a 롤백)

- 장점: 변종이 0 이 되고 `check_root_causes` 가 예외 없이 통과한다.
- 단점: 시나리오에 시각 순서 계약과 앞으로 가기 재진입 규칙을 더하고 모든 단계를 다시 돈다. 시트 재진입은 history 항목의 출처를 알 수
  있어야 해서(예: 상태에 열기 표지를 심기) 구현이 커지고, 새 결정이 다시 PLAN 밖으로 늘어난다.

### B. 두 건 모두 수용한다 (이 결정)

- 장점: 이 태스크를 마무리할 수 있다. 두 건의 영향은 각각 「history 칸 하나」와 「서버 계약이 깨졌을 때의 표시」로 작다.
- 단점: 알려진 변종이 코드에 남는다.

### C. 한 건만 고친다

- 장점: 시각 순서 검사는 `parseDetail` 한 줄이라 싸다.
- 단점: 시나리오 밖 변경이라 2a 로 돌아가야 하는 것은 마찬가지다. 한 건만 고치려 한 바퀴를 도는 비용이 크다.

## 결정

위 두 변종을 **고치지 않고 수용한다.** 변종마다 이유를 남긴다.

### 이유

- **중복 history 칸:** 사용자가 겪는 것은 뒤로 가기를 한 번 더 눌러야 한다는 것뿐이며, 화면을 떠나거나 시트가 안 닫히는 일은 없다.
  재현에 「열기 → 뒤로 → 앞으로 → 닫기」라는 드문 순서가 필요하다. 구분하려면 history 항목마다 출처 표지를 심어야 하는데, 새로고침·복원 때
  표지가 어떻게 남는지까지 설계해야 해서 이득보다 복잡도가 크다.
- **시각 순서:** 서버가 DB CHECK 로 이미 막은 계약이다. 클라이언트가 같은 순서를 한 번 더 검사하면 서버 규칙이 바뀔 때 두 곳을 고쳐야 한다.
  모순 응답이 올 때의 증상(과거 시각 표시)도 데이터가 잘못된 것을 드러낼 뿐 화면이 깨지지는 않는다. ADR-0026 의 「상세 응답을 서버가 준 대로 믿는다」와 같은 방향이다.
- 탈락한 A·C 는 효과에 비해 되돌아가는 비용(시나리오 → 독립검증 → Red 승인 → Green → 재검증)이 크다.

## 결과

- 좋아지는 것: TASK-020 이 한 바퀴 더 돌지 않고 Phase 4 를 마친다. 시트 닫기 규칙은 「눌러 연 것은 한 칸 뒤로, 열린 채 들어온 것은 교체」 하나로 단순하게 남는다.
- 감수하는 것: ① 앞으로 가기로 시트 칸에 재진입한 뒤 닫으면 같은 상세 칸이 하나 더 남는다. ② 서버가 시각 순서를 어긴 응답을 주면 화면이 그대로 그린다.
  두 건 모두 테스트로 고정하지 않는다(고정하면 결함을 정상 동작으로 못 박게 된다).
- 되돌리려면: ① 시트를 열 때 history 상태에 열기 표지(예: 열린 칸의 `key`)를 심고, 닫을 때 현재 칸의 표지와 비교해 한 칸 뒤로/교체를 고른다 — 시나리오 SC-41 에 앞으로 가기 행을 더한다.
  ② `parseDetail` 에 `openAt ≤ closeAt ≤ startAt` 검사를 더하고 SC-04 에 행을 더한다. 둘 다 새 시나리오가 필요해 2a 부터 시작한다.
