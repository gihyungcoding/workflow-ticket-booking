# ADR-0022: 디자인 정본을 `out/` 시안으로 바꾸고, 토큰 값은 `out/tokens.css` 를 그대로 옮긴다

- **상태**: 채택됨
- **날짜**: 2026-11-04
- **관련**: ADR-0002, ADR-0011, `docs/product/design.md`, `docs/product/design-tokens.css`, `out/`

---

## 맥락

지금까지 디자인 정본은 `design.md` 의 「잉크 + 별색 1도」 방향이었다 — 채도 있는 색은
「예매가능」 하나, 공연명만 명조, 그림자 없음, 모서리 2px. 시안 없이 목록·상세 두 화면을
위해 정한 것이다 (TASK-002·003).

이번에 대규모 오픈 예매 PRD(`out/prd.md`)로 로그인부터 양도까지 30장의 모바일 시안을
만들었다 (`out/screens/`). 시안은 다른 토큰 체계를 쓴다 — 브랜드 블루 `#4154FF`,
Pretendard, 의미 배지 6종(성공·주의·정보·위험 포함), 모서리 6/12/20, 떠 있는 요소의 그림자.
기존 `design.md` §6 은 「상태를 여러 색으로」 「둥근 카드 + 그림자」를 하지 말라고 적고 있어
시안과 정면으로 부딪힌다. 사용자는 시안 그대로, 시안의 토큰 값 그대로 개발하기를 원한다.

## 검토한 선택지

### A. 기존 정본을 유지하고 시안의 구조만 가져온다

- 장점: TASK-002·003 화면을 다시 칠하지 않는다. 기존 대비 실측이 그대로 유효하다.
- 단점: 시안의 상태 배지 6종(입금 대기·예매 확정 등)을 별색 하나로 표현할 수 없다.
  화면을 띄워 시안과 대조할 때 모든 화면이 「다르다」로 나와 대조 자체가 의미를 잃는다.

### B. 정본을 시안으로 바꾸고, 토큰 값은 `out/tokens.css` 를 그대로 옮긴다

- 장점: 시안 HTML 과 실제 화면을 나란히 놓고 같은지 판정할 수 있다. 값이 한 출처에서 온다.
- 단점: 이미 끝난 목록·상세·로그인 화면을 다시 칠해야 한다. 배지 문구가 바뀐다
  (예매가능 → 예매 가능, 예매예정 → 예정, 예매마감 → 마감). 기존 테스트의 문구 단언이 깨진다.

### C. 시안 토큰을 기존 정본에 섞는다 (브랜드만 바꾸고 나머지 유지)

- 장점: 변경 폭이 작다.
- 단점: 어느 쪽 값이 정본인지 다시 모호해진다. 시안과도 기존과도 같지 않은 세 번째 모습이 된다.

## 결정

**B — 디자인 정본을 `out/` 시안으로 바꾼다.** `design-tokens.css` 는 `out/tokens.css` 의
값을 그대로 옮긴 것이고, 화면 코드는 `out/screens/<id>.html` 과 같아야 한다.

### 이유

사용자가 원하는 검증 방식이 「화면을 띄워 시안과 같은지 확인」이다. A·C 는 그 대조를
불가능하게 만든다. 기존 화면을 다시 칠하는 비용은 흐름별 태스크(booking-ux-01~05)가
그 화면을 다시 만들 때 함께 치른다 — 따로 치르지 않는다.

## 결과

- 좋아지는 것: Phase 4 의 디자인 확인이 「시안과 같은가」라는 판정 가능한 질문이 된다.
  토큰 밖 값(DESIGN-002·003)을 판정할 기준이 명확하다.
- 감수하는 것: 기존 화면 테스트의 문구·배지 단언을 흐름 태스크에서 고친다. 이전 방향의
  근거(명조 공연명 등)는 버린다 — git 이력과 이 ADR 에만 남는다.
- 되돌리려면: 시안을 다른 팔레트로 다시 만들면(`out/palettes.json` 에 대안 2개) 그 값을
  `design-tokens.css` 로 옮기면 된다. 정본 체계 자체를 되돌리려면 새 ADR 이 필요하다.

## 검사 가능한 제약

- 기존 DESIGN-001·002·003 을 그대로 쓴다. 새 토큰 파일도 `frontend/src/theme/**` 에 두어
  DESIGN-002 의 제외 경로를 바꾸지 않는다.
