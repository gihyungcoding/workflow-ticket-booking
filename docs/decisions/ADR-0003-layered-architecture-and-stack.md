# ADR-0003: 레이어드 아키텍처와 Java/Spring + React + PostgreSQL 스택을 쓴다

- **상태**: 채택됨
- **날짜**: 2026-09-02
- **관련**: `docs/architecture/architecture.md`, ADR-0002

---

## 맥락

프로젝트를 처음부터 구성해야 한다. 1인 개발이라 운영·유지보수 부담이 큰 구성(다중
서비스, 별도 인프라 운영 등)은 피해야 한다(`docs/product/product.md` §6). 도메인은
공연·좌석·예매(선점)로, 좌석 선점의 동시성 정합성이 핵심 요구사항이다.

## 검토한 선택지

### A. 마이크로서비스 / 다중 모듈

- 장점: 도메인별 독립 배포·확장이 가능하다.
- 단점: 1인 개발에서는 서비스 간 통신·배포 파이프라인·모니터링을 혼자 운영해야
  한다. 현재 규모(좌석 100~500석, 동시 접속 100명 이하 가정)에서는 얻는 이득보다
  운영 비용이 훨씬 크다.

### B. 단일 서비스, 레이어드 아키텍처 (Controller → Service → Repository → DB)

- 장점: 배포 단위가 하나라 1인 개발에 운영 부담이 가장 적다. Spring 생태계의
  표준적인 구조라 자료와 관례가 풍부하다. 계층 경계(§ARCH-001, ARCH-002)로
  트랜잭션 책임을 Service 에 고정할 수 있다.
- 단점: 서비스가 커지면 계층 내부가 비대해질 수 있다 — 지금 규모에서는 해당하지
  않는다.

## 결정

**B — 단일 서비스, 레이어드 아키텍처.** 백엔드는 Java/Spring, 프론트엔드는 React
(UI 라이브러리는 MUI, ADR-0002), 데이터베이스는 PostgreSQL.

### 이유

A(마이크로서비스)는 1인 개발이 감당하기 어려운 운영 비용을 요구하는 반면, 이 프로젝트의
현재 규모에서는 그 이득(독립 확장성)이 실현되지 않는다. PostgreSQL은 좌석 선점에
필요한 트랜잭션·유니크 제약을 표준적으로 지원하며 별도 인프라 학습 비용이 낮다.

## 결과

- 좋아지는 것: 배포·운영 단위가 하나로 단순하다. 계층 경계가 명확해 코드가 어디에
  있어야 하는지 판단하기 쉽다.
- 감수하는 것: 트래픽이 크게 늘면(§7 알려진 부채 참고) 단일 서비스 구조를 재검토해야
  한다. 지금은 그 비용을 감수하지 않는다.
- 되돌리려면: 계층 경계를 유지한 채로도 특정 도메인(예: 예매)을 별도 서비스로
  분리하는 것이 상대적으로 쉽다 — Service 계층이 이미 도메인 로직을 캡슐화하고
  있기 때문이다. 비용은 분리 대상 도메인의 크기에 비례한다.
