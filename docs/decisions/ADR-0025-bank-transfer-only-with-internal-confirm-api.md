# ADR-0025: 결제는 무통장 입금만 두고, 입금 확인은 쓰기 키로 보호한 내부 API 로 처리한다

- **상태**: 채택됨 (입금 확인 API 의 보호 수단 `X-Write-Key` 는 ADR-0029 로 대체됨 — 운영자 역할 + JWT 방향)
- **날짜**: 2026-11-04
- **관련**: ADR-0016, ADR-0017, `out/prd.md` FR-15~18·§5-3, `docs/product/product.md` §4

---

## 맥락

PRD 는 무통장 입금 예약·확정·자동 취소(FR-15~17)를 요구하고, 카드·네이버페이·카카오페이는
「추가 비용 없이 붙일 수 있을 때만」 넣기로 했다(FR-18, §5-3). 실제 연동은 모두 PG 수수료나
가맹 계약이 필요하다. 또 입금이 들어왔는지 누군가 확인해야 예매가 확정되는데, 운영자 기능은
이번 범위 밖이다.

## 검토한 선택지

### A. 무통장 입금만, 입금 확인은 보호된 내부 API

- 장점: 비용 0. 운영자 화면 없이도 확정 흐름(입금 대기 → 예매 확정)을 끝까지 만들 수 있다.
  ADR-0016 의 `X-Write-Key` 방식을 재사용한다.
- 단점: 입금 확인이 수동(또는 스크립트) 호출이다. 은행 연동은 다음 단계.

### B. 개발·시연용 가짜 입금 버튼

- 장점: 시연이 쉽다.
- 단점: 운영 빌드에서 끄는 장치가 따로 필요하고, 실수로 켜지면 무료 확정이 된다.

### C. 카드 등을 비활성 상태로 화면에 남긴다

- 장점: 시안 모습 그대로.
- 단점: 누를 수 없는 결제 수단은 관객에게 「왜 안 되지」만 남긴다. PRD 는 조건 불충족 시 「빼고」라고 했다.

## 결정

**A — 결제 수단은 무통장 입금 하나다. 카드·네이버페이·카카오페이는 화면에서 뺀다.
입금 확인은 `POST /internal/bookings/{id}/deposit-confirmed` 를 `X-Write-Key` 로 보호해 둔다.**

### 이유

C 는 PRD 의 조건을 어긴다. B 는 운영 위험이 있다. A 는 비용 없이 요구사항(FR-15~17)을 모두
충족하고, 은행 연동이 생기면 같은 내부 API 를 그 연동이 호출하면 된다.

## 결과

- 좋아지는 것: 확정 흐름을 운영자 화면 없이 끝까지 테스트할 수 있다.
- 감수하는 것: 시안 `checkout` 의 결제 수단 4개 중 3개를 그리지 않는다 — 화면 대조 시 이 차이는
  의도된 것이다. 입금 확인은 사람이 API 를 호출한다.
- 되돌리려면: 비용 없는 결제 수단이 생기면 결제 수단을 enum 으로 늘리고 화면에 행을 추가한다.
