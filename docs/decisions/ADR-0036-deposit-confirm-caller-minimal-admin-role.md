# ADR-0036: 입금 확인 API 의 호출자는 최소 ADMIN 역할로 한정하고, ADMIN 계정은 DB 로만 만든다

- **상태**: 채택됨
- **날짜**: 2026-11-25
- **관련**: ADR-0025 (입금 확인 경로를 대체), ADR-0029 (§결정 4 의 미정 항목을 정함), ADR-0013, `workflow_design/01_brief/BRIEF_REQ-002.json` D2·D18·D24·D25·D37·D38, `docs/product/product.md` §4

---

## 맥락

REQ-002 는 무통장 예약 → 입금 확인 → 예매 확정을 만든다(ADR-0025). 입금 확인은 화면 없는
내부 API 를 사람이 호출하는 방식이고, ADR-0029 는 그 보호 수단을 「운영자(ADMIN) 역할 + JWT」
방향으로 정하면서 **운영자 계정을 어떻게 만드는지는 그 API 를 만드는 기능에서 정한다**고 남겨 두었다.

지금 사실:

- `UserRole` 은 `AUDIENCE` · `ORGANIZER` 둘뿐이다. 운영자 역할이 없다
- 가입 API 두 곳(`SignUpRequest` · `CompleteSocialSignUpRequest`)이 요청 본문의 `role` 을 받는다.
  역할을 하나 더하면 가입으로 그 역할을 고를 수 있게 된다
- 프론트 `UserRole` 타입·`ROLES` 목록(`frontend/src/api/auth.ts`)도 두 값만 안다
- DB 의 `users.role` 은 `VARCHAR(20)` 이고 CHECK 제약이 없다(V3) — 값을 더해도 스키마는 그대로다
- 운영자 기능(주최자 승인·정산·신고)은 product.md §4 에서 이번 단계 범위 밖이다
- 역할은 JWT 클레임으로 믿고 요청마다 DB 에서 다시 읽지 않는다(ADR-0029 결정 1)

입금 확인은 돈이 들어왔다는 사실로 좌석을 확정 판매하는 쓰기라, 누가 부를 수 있는지가
이 흐름에서 가장 민감하다.

## 검토한 선택지

### A. ADMIN 역할을 최소로 추가한다

- 장점: ADR-0029 의 방향 그대로 보호 방식이 「JWT 역할」 하나로 유지된다. `/api/admin/**` 한 매처로
  운영 API 를 묶어 둘 수 있어, 나중에 운영자 기능이 생겨도 같은 자리에 붙는다
- 단점: 역할이 하나 늘면서 가입 경로에서 ADMIN 을 막는 일, 프론트 역할 타입 갱신, 계정을 만드는
  절차가 따라온다. 역할을 회수해도 이미 발급된 토큰은 만료까지 옛 역할을 가진다

### B. 그 공연의 주최자가 입금을 확인한다

- 장점: 새 역할이 필요 없다. 공연 소유권 검사(ADR-0029 결정 3)를 그대로 쓴다
- 단점: 입금 계좌가 서비스 쪽 계좌인지 주최자 계좌인지가 정해지지 않았다 — 주최자가 입금 내역을
  볼 수 있다는 전제가 없다. 예매 → 공연 → 주최자로 이어지는 소유권 경로를 입금 확인에 새로 깔아야 하고,
  주최자가 자기 공연 좌석을 입금 없이 확정할 수 있게 된다

### C. 공유 비밀 키(`X-Write-Key`)로 보호한다

- 장점: 역할·계정이 필요 없다. ADR-0025 의 원래 안이다
- 단점: ADR-0029 가 지운 쓰기 가드를 다시 들인다. 보호 방식이 「사용자 토큰」과 「공유 비밀」로
  갈리고, 누가 확정했는지 남길 수 없다. 키를 새로 발급·배포·회수하는 절차가 생긴다

## 결정

**A — `UserRole.ADMIN` 을 더하되, 쓰는 곳은 입금 확인 API 하나로 한정한다.**

1. **경로** — `POST /api/admin/bookings/by-number/{bookingNumber}/confirm-deposit`. `SecurityConfig` 에
   `/api/admin/**` → `hasRole("ADMIN")` 를 명시한다. 거절 응답은 기존 `FORBIDDEN_ROLE` 그대로,
   문구는 역할 중립으로 둔다(D24). 이미 확정된 예매에 다시 부르면 200 멱등(D18). 응답에 금액·예매자·좌석(D37)
2. **계정** — ADMIN 은 가입으로 만들 수 없다. 가입 API 두 곳에서 `role == ADMIN` 이면 400 으로 거절하고,
   ADMIN 계정은 DB 에서 직접 지정한다. 화면은 없다(D25). 프론트 `UserRole`·`ROLES` 에는 `'ADMIN'` 만
   더한다 — 서버가 돌려주는 값을 타입이 알게 하려는 것이다
3. **회수 지연과 감사** — 확정 시점에 DB 에서 호출자의 역할을 한 번 더 확인하고, `booking.confirmed_by` ·
   `booking.confirmed_at` 에 누가 언제 확정했는지 남긴다(D38)

ADR-0025 의 경로 `POST /internal/bookings/{id}/deposit-confirmed` 는 쓰지 않는다 — 운영 API 는
`/api/admin/` 접두로 모으고, 운영자가 손에 쥔 값(관객이 보는 예매번호)으로 부른다.

### 이유

C 는 ADR-0029 가 이유를 들어 없앤 공유 비밀을 되살리고, 확정한 사람을 남기지 못한다. B 는 입금
계좌의 주인이 정해지지 않은 상태에서 확정 권한을 판매 당사자에게 주는 것이고, 그 판단을 이번
요청에서 내릴 근거가 없다. A 는 ADR-0029 가 이미 고른 방향이고, 역할 추가로 생기는 위험(가입으로
ADMIN 을 얻는 권한 상승)은 가입 API 에서 막을 수 있으며 DB 스키마 변경이 없다.

## 결과

- 좋아지는 것:
  - 입금 확인을 누가 했는지 `confirmed_by` 로 남는다
  - 운영 API 의 자리(`/api/admin/**` + `hasRole(ADMIN)`)가 생겨, 운영자 기능이 범위에 들어오면 같은 매처에 붙인다
- 감수하는 것:
  - **역할 회수 지연** — ADMIN 을 DB 에서 빼도 이미 발급된 토큰은 만료까지 `ROLE_ADMIN` 을 가진다.
    매처는 통과하지만 확정 시점 DB 재확인(결정 3)에서 막힌다. 다른 `/api/admin/**` API 가 생기면
    같은 재확인을 각자 해야 한다
  - ADMIN 계정 생성·회수가 SQL 수작업이다. 운영 절차를 문서로 따로 두어야 한다
  - 동명이인·같은 금액 입금은 시스템이 구분하지 않는다 — 운영자가 예매번호로 확정한다(D23, 알려진 한계)
  - 가입 API 가 `role` 을 계속 받으므로, 역할이 더 늘 때마다 가입 허용 목록을 함께 고쳐야 한다
- 되돌리려면:
  - B 로 가려면 입금 확인 매처를 `ORGANIZER` + 소유권 검사로 바꾸고 `UserRole.ADMIN` 을 지운다.
    ADMIN 계정 행을 정리하고 가입 거절 분기·프론트 타입을 되돌린다 — 반나절 규모
  - 은행 연동이 생기면 같은 서비스 메서드를 연동이 호출하고, 사람 호출 경로는 그대로 두거나 닫는다

## 검사 가능한 제약

- `ARCH-` 제약으로 `/api/admin/**` 매처가 `SecurityConfig` 에 있는지는 `architecture-doc` 작업(REQ-002 dispatch)에서
  `constraints.yaml` 에 추가한다 — ID 는 그 작업 결과를 따른다
