# ADR-0018: 클라이언트 세션 상태는 세대로 직렬화하고, 늦게 온 복원 응답은 버린다

- **상태**: 채택됨
- **날짜**: 2026-10-22
- **관련**: ADR-0015, `docs/product/features/user-authentication.md`, TASK-010 (SC-33~35, Phase 4 RC-1)

---

## 맥락

새로고침해도 로그인이 유지되도록(ADR-0015) 앱은 시작할 때 저장된 토큰으로 `GET /api/auth/me`
를 보내 사용자를 복원한다. 이 요청은 서버 응답을 기다리는 동안 진행 중이고, 그 사이 사용자는
복원 중에도 열려 있는 `/login` 에서 로그인하거나 로그아웃할 수 있다. 복원 응답이 그 뒤에
도착하면 이미 바뀐 세션 위에 이전 토큰의 결과가 덮어써진다.

TASK-010 Phase 4 1차에서 실제로 나온 결과다 — 화면은 이전 사용자, 저장 토큰은 새 토큰 / 늦은 401 이
방금 저장한 새 토큰을 삭제 / 로그아웃 뒤 늦은 200 이 다시 로그인 상태로 되돌림 / 로그인 뒤에도 헤더가
복원을 기다려 비어 있음. 118개의 정상 흐름 테스트가 모두 통과한 채였다.

TASK-011~013(소셜 로그인 콜백·역할 선택)이 같은 세션 상태에 로그인 경로를 더 붙이므로, 경로마다
복원과의 겹침을 다시 정하지 않도록 규칙이 필요하다.

## 검토한 선택지

### A. 세션 세대 — 로그인·로그아웃이 카운터를 올리고, 시작 때의 세대와 다른 복원 응답은 버린다

- 장점: 판정이 한 지점(`stale()`)에 모인다. 취소(언마운트·StrictMode 정리)와 세션 변경을
  같은 조건으로 막고, 성공·401·그 밖의 모든 결과를 같은 가드로 지킨다. 요청 계층(`http.ts`)을
  바꾸지 않는다
- 단점: 응답 처리 코드가 세대를 확인하는 것을 잊으면 같은 결함이 다시 생긴다. 요청 자체는 서버까지
  가고 응답만 버린다

### B. `AbortController` 로 복원 요청을 취소한다

- 장점: 불필요한 네트워크 작업을 취소한다는 의도가 코드에 드러난다
- 단점: `request()` 가 `signal` 을 전달하도록 바꿔야 하고 abort 오류를 따로 분기해야 한다.
  취소 신호가 닿기 전에 이미 도착한 응답은 막지 못해 경쟁이 남는다. StrictMode 의 첫 요청 취소도
  오류 경로를 탄다

### C. 복원이 끝날 때까지 로그인·로그아웃 진입을 막는다

- 장점: 겹침 자체가 생기지 않아 규칙이 필요 없다
- 단점: 서버가 느리면 로그인 화면이 열리지 않거나 비활성이 돼 사용자가 막힌다. 라우트·버튼마다
  접근 제어가 필요하고 깊은 링크로 들어온 경우를 따로 다뤄야 한다

### D. 세션 이벤트를 리듀서의 상태 머신으로 모델링한다

- 장점: 가능한 상태 전이가 명시적이다
- 단점: 상태가 비로그인·복원 중·로그인 셋뿐이라 규모에 비해 과하다

## 결정

세션 세대(A)를 쓴다. 규칙은 네 가지다.

1. `login()`·`logout()` 은 세대를 올린다. 복원은 시작 시점의 세대를 기억하고, 취소됐거나 세대가
   다르면 그 응답의 모든 결과(`setUser`·토큰 삭제·`setRestoring`)를 버린다
2. `login()` 은 복원 대기를 끝낸 것으로 본다 — 헤더가 복원 응답을 기다리지 않는다
3. 토큰은 **401 일 때만** 삭제한다. 500·네트워크 오류·형식이 틀린 200 은 토큰을 지우지 않는다
4. 브라우저 저장소 접근이 실패해도 앱은 동작하고, 이번 방문 동안의 로그인 상태는 메모리로 유지한다

### 이유

겹침이 일어나는 곳은 "복원 결과를 적용하는 한 지점"이라 그 지점에서 막으면 변종 다섯(로그인 뒤 200·
401, 로그아웃 뒤 200, `restoring` 잔류, StrictMode 취소의 401)이 한 번에 닫힌다. B 는 요청 계층을
건드리면서도 이미 도착한 응답의 경쟁을 남기고, C 는 서버가 느린 날 사용자를 막는 비용이 크다.
D 는 이 크기의 상태에 과하다.

## 결과

- 좋아지는 것: 복원·로그인·로그아웃의 겹침 규칙이 한 곳에 있어 이후 로그인 경로(소셜 콜백 등)는
  `login()` 을 부르기만 하면 된다. 시나리오 SC-33~35 가 안전망이다
- 감수하는 것: 세대를 확인하지 않는 새 비동기 경로는 같은 결함을 만든다. 알려진 잔여 — `logout()` 만
  호출되면 `restoring` 이 남을 수 있고(현재 UI 로는 도달 불가), 로그인 요청 자체의 늦은 응답이 화면
  이동 뒤에 로그인·이동을 실행한다(TASK-010 OOS-2, 사용자가 수락). 요청은 서버까지 간다
- 되돌리려면: `AuthContext.tsx` 한 파일의 세대 확인을 바꾼다. 다른 방식(B·C)으로 바꿔도 SC-33~35 가
  같은 동작을 요구한다

## 검사 가능한 제약

- 없음 — 동작은 테스트(SC-33~35)가 지킨다
