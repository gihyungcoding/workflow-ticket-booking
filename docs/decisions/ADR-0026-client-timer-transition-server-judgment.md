# ADR-0026: 시간 제한 화면은 기한이 되면 다시 조회하지 않고 클라이언트가 전환하고, 판정은 다음 요청에서 서버가 한다

- **상태**: 채택됨
- **날짜**: 2026-11-10
- **관련**: ADR-0005, ADR-0023, ADR-0024, `docs/product/features/booking-ux-02-browse.md` §8, TASK-018 회고(ADR 후보 2)

---

## 맥락

시간 제한이 있는 화면이 이미 하나 있고 세 개가 더 생긴다.

| 화면 | 기한 | 기한에 바뀌는 것 | 흐름 |
|---|---|---|---|
| 역할 선택 | pendingToken 5분 | 만료 상태 | 흐름 1 (TASK-018, 구현됨) |
| 공연 상세 | 예매 오픈 시각 | 예매하기가 켜짐 | 흐름 2 |
| 대기열 | 내 차례 | 회차·매수 고르기로 | 흐름 3 |
| 확인·결제 수단 | 좌석 선점 7분 | 선점 만료 | 흐름 4 |

ADR-0024 는 카운트다운을 **어떻게 세는지**(서버 시각 오프셋)와 **누가 판정하는지**(서버 `Clock`)를
정했다. 그런데 **기한이 된 순간 화면이 무엇을 하는지**는 정하지 않았다. 바로 이 순간에 힘이 몰린다.

- 공연 오픈 순간 최대 10만 명이 같은 상세 화면을 열어 두고 있다 (`out/prd.md` §3).
  0초에 각 기기가 무엇을 하든 10만 번 동시에 일어난다
- 리뷰 불만 A2: "정시에 들어가봤자 로딩되는 동안 표가 다 나갑니다" (`out/conventions.json`)
- 화면 전환은 기기마다 같은 순간이어야 한다 (FR-1·2)
- TASK-018 에서는 「계속하기」를 누른 요청이 가는 도중에 화면 타이머가 0이 되면, 서버는 받아 준
  가입이 화면에서는 만료로 보이는 경합이 있었다 (CP-1.3 decisions)

## 검토한 선택지

### A. 기한이 되면 다시 조회해서 서버가 준 상태로 바꾼다

- 장점: 화면 상태가 항상 서버 계산(`PerformanceStatusRules`)과 같다. 클라이언트에 상태 규칙을
  두지 않는다.
- 단점: 0초에 10만 기기가 `GET /api/performances/{id}` 를 동시에 부른다. 이 순간의 부하가 곧
  진입 장애(A2)다. 응답이 늦은 기기는 늦게 켜져서 「같은 순간」(FR-2)이 깨진다.

### B. 기한 전후로 서버가 상태 변화를 밀어 준다 (SSE·WebSocket)

- 장점: 다시 조회하지 않고도 서버 상태를 받는다.
- 단점: 오픈 직전 10만 연결을 유지해야 한다. ADR-0024 가 B(매초 서버 시각)를 버린 이유와 같다.
  1인 개발에 운영 부담이 크다 (product.md §6).

### C. 기한이 되면 클라이언트가 이미 가진 데이터로 전환하고, 판정은 다음 요청에서 서버가 한다

- 장점: 0초에 서버 호출이 없다. 모든 기기가 같은 기준 시각(ADR-0024)으로 같은 순간 바뀐다.
  공정성은 다음 요청(대기열 진입·가입 완료·선점 확정)을 서버 `Clock` 이 판정해 지킨다.
- 단점: 전환 규칙(예정 → 예매 가능, 남은 좌석 0 이면 매진)이 클라이언트에 한 벌 더 생긴다.
  화면이 서버보다 잠깐 낙관적일 수 있다 — 켜진 버튼을 눌렀는데 서버가 거절할 수 있다.

## 결정

**C — 시간 제한 화면은 기한이 되면 다시 조회하지 않고, 이미 받은 데이터와 기준 시각으로 화면을
전환한다. 최종 판정은 그다음 요청에서 서버가 주입된 `Clock` 으로 한다.** 요청이 가는 중에
기한이 되면 화면은 전환하지 않고 서버 응답을 기다린다.

### 이유

A 는 0초 부하로 A2 를 스스로 만들고, 응답 지연이 기기 간 차이가 된다. B 는 ADR-0024 가 이미
버린 연결 유지 비용이다. C 는 0초에 아무것도 부르지 않으면서 표시를 맞추고, 공정성은 표시가
아니라 서버 판정이 지킨다는 ADR-0024 의 원칙을 기한 순간까지 넓힌다. 「요청 중엔 서버를
기다린다」는 TASK-018 경합(서버는 받았는데 화면은 만료)을 막는다.

## 결과

- 좋아지는 것: 기한 순간 서버 호출 0. 기기 간 같은 순간 전환. 흐름 1~4 의 시간 제한 화면이 한 규칙.
- 감수하는 것:
  - 클라이언트 전환 규칙이 서버 `PerformanceStatusRules` 와 어긋날 수 있다 — 전환은 「예정 →
    예매 가능/매진」 한 방향만 두고, 나머지 상태는 서버 응답을 그대로 쓴다
  - 켜진 버튼을 눌러도 서버가 거절할 수 있다(0초 직전 경계, 그사이 취소된 공연). 거절 응답을
    받는 화면(흐름 3 대기열 진입)이 그 문구를 가져야 한다
  - 역할 선택(TASK-018)은 기한을 기기 시계(`Date.now()`)로 센다. 기준 시각 훅(`useServerClock`,
    흐름 2)이 생긴 뒤 옮길지는 따로 정한다 — 5분 기한은 공정성이 걸리지 않아 몇 초 차이는 서버가 흡수한다
- 되돌리려면: A 로 바꾸려면 기한 콜백에서 재조회만 부르면 된다(화면 1곳당 몇 줄). 비용은
  코드가 아니라 0초 부하 — 그 전에 진입 보장(FR-5, 흐름 3)이 있어야 한다.

## 검사 가능한 제약

- 없음 — 「기한 콜백에서 API 를 부르지 않는다」는 정적 패턴으로 잡기 어렵다(콜백 모양이 화면마다
  다르다). 각 흐름의 시나리오에 「기한 순간 해당 API 호출 0회」 단언으로 확인한다
  (booking-ux-02 Task B 완료 조건)
