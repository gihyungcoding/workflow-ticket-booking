# ADR-0014: 이메일이 일치하고 검증된 경우에만 소셜 계정을 자동 연결한다

- **상태**: 채택됨
- **날짜**: 2026-10-14
- **관련**: ADR-0012, ADR-0013, `docs/product/features/user-authentication.md`

---

## 맥락

소셜 로그인(카카오/네이버/구글/애플) 사용자의 이메일이 기존 이메일 회원가입
계정과 같을 수 있다([user-authentication.md](../product/features/user-authentication.md)).
이 경우를 어떻게 처리할지 정해야, 같은 사람이 로그인 경로에 따라 서로 다른
계정으로 갈라지는 혼란을 막을 수 있다.

반대로, 이메일 일치만으로 무조건 계정을 연결하면 제공자가 실제로 이메일
소유권을 검증했는지에 전적으로 의존하게 된다 — 검증되지 않은 이메일을 그대로
내려주는 경로가 있다면, 타인의 이메일 주소를 아는 것만으로 그 계정에 소셜
로그인을 연결해버리는 계정 탈취 경로가 열린다.

## 검토한 선택지

### A. 자동 연결 (이메일이 같으면 기존 계정에 소셜 연결을 자동으로 추가)

- 장점: 사용자가 어떤 경로로 로그인하든 하나의 계정으로 수렴해, "분명 가입했는데
  로그인이 안 된다"는 혼란이 없다. 티켓 예매 서비스 특성상 과거 예매 내역이
  갈라지지 않는다
- 단점: 제공자가 이메일 소유권을 검증했다는 전제에 의존한다 — 검증되지 않은
  이메일로 자동 연결을 허용하면 계정 탈취 경로가 된다

### B. 별도 계정으로 충돌 처리 (이메일 유니크 제약에 걸려 409 반환)

- 장점: 구현이 가장 단순하고, 위 공격 벡터가 원천적으로 없다
- 단점: 사용자가 이메일로 먼저 가입한 뒤 같은 이메일의 소셜 계정으로 로그인을
  시도하면 거부당하고, 본인 소유의 이메일인데 왜 안 되는지 이해하기 어렵다

## 결정

자동 연결(A)을 쓰되, 제공자의 이메일 검증 플래그(`email_verified` 또는 동등
필드)가 **true인 경우에만** 연결한다. 검증 플래그가 false이거나 제공자가 아예
제공하지 않으면 자동 연결하지 않고 신규 가입과 동일하게 취급한다(역할 선택
화면으로 보낸다).

### 이유

같은 사람이 "이메일로 가입했다가 나중에 소셜로 로그인"하는 경로가 흔할 것으로
예상되고, 계정이 갈라지면 과거 예매 내역을 찾지 못하는 문제가 더 크다고
판단했다. 다만 이메일 검증 여부를 확인하지 않는 순수 자동 연결(A의 단순 버전)은
계정 탈취로 이어질 수 있어, `email_verified` 조건을 추가해 B의 안전성과 A의
사용자 경험을 함께 가져갔다. 카카오·네이버·구글·애플 4개 제공자 모두 이메일
스코프 승인 시 검증된 이메일(또는 동등한 플래그)을 제공하므로 이 조건을 적용할
수 있다.

## 결과

- 좋아지는 것: 사용자가 가입 경로를 기억하지 못해도 같은 계정으로 계속 로그인할
  수 있고, 검증되지 않은 이메일로는 연결되지 않아 계정 탈취 경로가 막힌다
- 감수하는 것: 제공자를 추가할 때마다 그 제공자가 이메일 검증 플래그를
  제공하는지, 어떤 조건에서 true가 되는지 확인해야 하는 의무가 생긴다.
  `email_verified`가 false인 사용자는 소셜 로그인으로 기존 계정에 접근하지
  못하고 별도 계정(또는 역할 선택 후 신규 계정)으로 남는다 — 드물지만 혼란의
  여지가 있다
- 되돌리려면: `OAuth2LoginSuccessHandler`의 자동 연결 분기를 제거하고 이메일
  충돌 시 409를 반환하도록 바꾸면 된다(B로 전환). 이미 자동 연결된 계정들은
  그대로 유지되므로 데이터 마이그레이션은 필요 없다 — 낮은 비용

## 검사 가능한 제약

- 없음. `email_verified=false`일 때 자동 연결을 수행하지 않는다는 조건은
  `CustomOAuth2UserService`/`OAuth2LoginSuccessHandler`의 단위 테스트로
  검증한다(`user-authentication.md` Task C 완료 조건).
